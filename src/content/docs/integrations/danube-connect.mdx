Danube Connect links Danube to the rest of your stack: IoT devices, webhooks, databases and data lakes. Each connector runs as its own process and talks to Danube over gRPC, so the broker stays small and a misbehaving connector can never take it down.

```bash
# Bridge MQTT devices into Danube with one container
docker run -d \
  -e DANUBE_SERVICE_URL=http://danube-broker:6650 \
  -e CONNECTOR_NAME=mqtt-bridge \
  -e CONNECTOR_CONFIG_PATH=/config/connector.toml \
  -v $(pwd)/config.toml:/config/connector.toml:ro \
  ghcr.io/danube-messaging/danube-source-mqtt:latest
```

## Why connectors run out of process

## Available connectors

**Sources** (into Danube)

- **[MQTT Source](https://github.com/danube-messaging/danube-connectors/tree/main/source-mqtt)**: IoT devices over MQTT 3.1.1.
- **[HTTP Webhook Source](https://github.com/danube-messaging/danube-connectors/tree/main/source-webhook)**: ingest webhooks from any service.

**Sinks** (out of Danube)

- **[Qdrant Sink](https://github.com/danube-messaging/danube-connectors/tree/main/sink-qdrant)**: vector embeddings for RAG and AI search.
- **[SurrealDB Sink](https://github.com/danube-messaging/danube-connectors/tree/main/sink-surrealdb)**: multi-model database storage.
- **[Delta Lake Sink](https://github.com/danube-messaging/danube-connectors/tree/main/sink-deltalake)**: ACID data lake tables on S3, Azure or GCS.

## Run your first connector

<Steps>

1. Start a broker and open a consumer on the target topic, so you see data as soon as it arrives:

   ```bash
   danube up standalone
   danube topic create /iot/sensors --intent event_stream
   danube consume /iot/sensors -s connector-check
   ```

2. Write `config.toml` (see [Configure a connector](#configure-a-connector) below).

3. Start the connector with the `docker run` command at the top of this page. Point `DANUBE_SERVICE_URL` at your broker, for example `http://host.docker.internal:6650` when the broker runs on your laptop.

4. Publish to the MQTT topic `sensors/...` and watch the records show up in the consumer.

</Steps>

<Aside type="note">
`danube up standalone` listens on `127.0.0.1:6650` by default. For a connector running in Docker, start the broker with `--listen 0.0.0.0:6650` so the container can reach it.
</Aside>

## How it fits together

```text
External systems (MQTT, databases, APIs)
          ↓
Your connector logic (implements a trait)
          ↓
danube-connect-core (SDK runtime)
          ↓
danube-client (gRPC)
          ↓
Danube cluster
```

- **Source connectors** poll or subscribe to an external system, turn events into `SourceRecord` values, and the runtime publishes them.
- **Sink connectors** receive deserialized `SinkRecord` batches from the runtime and write them to the target.

### What the SDK handles for you

`danube-connect-core` does everything except the external-system logic:

- Danube connection and producer/consumer lifecycle
- Schema-aware serialization (sources) and deserialization (sinks)
- Polling loops, streaming drains and sink batch flush timing
- Retries with exponential backoff
- Prometheus metrics and health checks
- Signal handling and graceful shutdown

## Configure a connector

One TOML file holds the core Danube settings and the connector-specific section:

```toml title="config.toml"
# Core (danube-connect-core)
danube_service_url = "http://danube-broker:6650"
connector_name = "mqtt-bridge"

[processing]
batch_size = 500
batch_timeout_ms = 1000
poll_interval_ms = 100
metrics_port = 9090

# Schema mappings (source connectors)
[[schemas]]
topic = "/iot/sensors"
subject = "sensor-data"
schema_type = "json_schema"
schema_file = "schemas/sensor.json"
version_strategy = "latest"

# Connector-specific
[mqtt]
broker_host = "mosquitto"
broker_port = 1883

[[mqtt.routes]]
from = "sensors/#"
to = "/iot/sensors"
partitions = 8
```

<Aside type="tip">
Override `DANUBE_SERVICE_URL`, `CONNECTOR_NAME` and secrets (passwords, API keys) with environment variables. Keep structural config such as `routes` and `schemas` in TOML.
</Aside>

## Schemas are handled for you

Connectors work with `serde_json::Value`; the runtime does the schema work.

- **Sources**: you build a `SourceRecord` from a JSON value. The runtime validates it, serializes it, registers the schema if needed and attaches the schema ID.
- **Sinks**: the runtime fetches the schema, deserializes the payload and hands you a typed `SinkRecord`. No manual byte parsing.

**Schema types**

- **`json_schema`**: JSON Schema validation, for structured events and APIs
- **`avro`**: Apache Avro, for compact high-performance schemas
- **`string`**: UTF-8 text, for logs
- **`bytes`**: raw binary
- **`number`**: numeric values, for metrics and counters

**Version strategies**

- **`"latest"`**: always the newest version. Good for development.
- **`{ pinned = 3 }`**: one exact version. Good for production stability.
- **`{ minimum = 2 }`**: this version or newer, for backward compatibility.

Inspect what a connector registered with `danube schema get --subject sensor-data`.

## Observe a connector

Every connector exposes, out of the box:

- **Prometheus metrics** at `/metrics`: records received and sent, errors, processing time.
- **Health checks** at `/health`: `healthy`, `degraded` or `unhealthy`.
- **Structured JSON logs**, with the level set by `LOG_LEVEL`.

## Errors drive behavior

Return the right error type and the runtime reacts:

- **`Retryable`**: temporary failure (network, rate limit). Retried with exponential backoff.
- **`InvalidData`**: malformed message. Logged and skipped.
- **`Fatal`**: unrecoverable (auth, bad config). The connector shuts down gracefully.
