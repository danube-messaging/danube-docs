Need Danube to talk to a system that has no connector yet? With `danube-connect-core` you write only the part that talks to that system. The runtime takes care of the Danube connection, schemas, retries, metrics and shutdown.

```rust
// A whole polling source fits in one method
async fn poll(&mut self) -> ConnectorResult<Vec<SourceEnvelope>> {
    let events = self.client.fetch().await?;
    Ok(events.into_iter()
        .map(|e| SourceRecord::from_json("/events/users", &e).unwrap().into())
        .collect())
}
```

## Who does what

<CardGrid>
  <Card title="You write" icon="pencil">
    - Connect to the external system
    - Map data to and from `SourceRecord` / `SinkRecord`
    - Topic routing logic
    - External checkpoints and offsets
    - Error classification
  </Card>
  <Card title="The runtime does" icon="setting">
    - Connect to the Danube broker
    - Schema serialization and deserialization
    - Producer and consumer lifecycle
    - Retries with exponential backoff
    - Metrics, health checks, graceful shutdown
  </Card>

You work with typed `serde_json::Value` data. Raw bytes, schemas and the Danube protocol stay inside the runtime.

## Build a source connector

Sources bring data **into** Danube.

```rust title="SourceConnector trait"
#[async_trait]
pub trait SourceConnector: Send + Sync {
    async fn initialize(&mut self, config: ConnectorConfig) -> ConnectorResult<()>;
    async fn producer_configs(&self) -> ConnectorResult<Vec<ProducerConfig>>;

    fn mode(&self) -> SourceConnectorMode {
        SourceConnectorMode::Polling
    }

    async fn start_streaming(&mut self, sender: SourceSender) -> ConnectorResult<()>;
    async fn poll(&mut self) -> ConnectorResult<Vec<SourceEnvelope>>;

    async fn commit(&mut self, offsets: Vec<Offset>) -> ConnectorResult<()> { Ok(()) }
    async fn shutdown(&mut self) -> ConnectorResult<()> { Ok(()) }
    async fn health_check(&self) -> ConnectorResult<()> { Ok(()) }
}
```

You must implement `initialize`, `producer_configs`, and either `poll` or `start_streaming`.

### Pick polling or streaming

<Tabs>
  <TabItem label="Polling (default)">

For pull-based systems such as databases and REST APIs. The runtime calls `poll()` on an interval; return new records, or an empty `Vec` when there is nothing.

```rust
async fn poll(&mut self) -> ConnectorResult<Vec<SourceEnvelope>> {
    let events = self.client.fetch().await?;

    let records = events.into_iter().map(|event| {
        SourceRecord::from_json("/events/users", &event)
            .unwrap()
            .with_attribute("source", "api")
            .into()
    }).collect();

    Ok(records)
}
```

  </TabItem>
  <TabItem label="Streaming">

For event-driven systems such as MQTT and websockets. Return `Streaming` from `mode()` and push records through the `SourceSender`.

```rust
fn mode(&self) -> SourceConnectorMode {
    SourceConnectorMode::Streaming
}

async fn start_streaming(&mut self, sender: SourceSender) -> ConnectorResult<()> {
    let client = self.client.clone();
    tokio::spawn(async move {
        while let Some(event) = client.next_event().await {
            let record = SourceRecord::from_json("/events/users", &event)
                .unwrap()
                .with_attribute("source", "stream");
            if sender.send(record).await.is_err() { break; }
        }
    });
    Ok(())
}
```

  </TabItem>
</Tabs>

### Create records

```rust
// From a JSON value
SourceRecord::new("/topic", json!({"key": "value"}))

// From a serializable struct
SourceRecord::from_json("/topic", &my_struct)?

// From a string, number or bytes
SourceRecord::from_string("/topic", &text)
SourceRecord::from_number("/topic", 42.0)?
SourceRecord::from_bytes("/topic", &bytes)

// Add attributes and a routing key
record.with_attribute("device_id", "sensor-42")
      .with_key(&partition_key)

// Attach an offset for checkpointing
SourceEnvelope::with_offset(record, Offset::new("partition-0", 42))
```

### Track offsets (optional)

Implement `commit()` when you need to resume where you left off. The runtime calls it after a batch is published successfully.

```rust
async fn commit(&mut self, offsets: Vec<Offset>) -> ConnectorResult<()> {
    for offset in offsets {
        self.checkpoint_store.save(&offset.partition, offset.value).await?;
    }
    Ok(())
}
```

Skip it when your source is stateless or at-least-once is fine.

## Build a sink connector

Sinks move data **out of** Danube.

```rust title="SinkConnector trait"
#[async_trait]
pub trait SinkConnector: Send + Sync {
    async fn initialize(&mut self, config: ConnectorConfig) -> ConnectorResult<()>;
    async fn consumer_configs(&self) -> ConnectorResult<Vec<ConsumerConfig>>;
    async fn process_batch(&mut self, records: Vec<SinkRecord>) -> ConnectorResult<()>;

    async fn shutdown(&mut self) -> ConnectorResult<()> { Ok(()) }
    async fn health_check(&self) -> ConnectorResult<()> { Ok(()) }
}
```

You must implement `initialize`, `consumer_configs` and `process_batch`.

### Declare what to consume

```rust
async fn consumer_configs(&self) -> ConnectorResult<Vec<ConsumerConfig>> {
    Ok(vec![ConsumerConfig {
        topic: "/events/users",
        consumer_name: "my-sink-1",
        subscription: "my-sink-group",
        subscription_type: SubscriptionType::Shared,
        expected_schema_subject: Some("user-events-v1"),
    }])
}
```

- **`Shared`**: load-balanced across sink replicas. The usual choice for parallel processing.
- **`Exclusive`**: one consumer, strict order. For sequential processing.
- **`FailOver`**: active-passive. Ordered and highly available.

### Process batches

The runtime buffers messages and calls `process_batch()` when `batch_size` or `batch_timeout_ms` is reached. Records arrive already deserialized:

```rust
async fn process_batch(&mut self, records: Vec<SinkRecord>) -> ConnectorResult<()> {
    for record in &records {
        let payload = record.payload();        // &serde_json::Value
        let topic = record.topic();            // &str
        let attrs = record.attributes();       // &HashMap<String, String>

        // Or deserialize into a struct
        let event: MyEvent = record.as_type()?;

        // Schema metadata, if present
        if let Some(schema) = record.schema() {
            println!("{} v{}", schema.subject, schema.version);
        }
    }

    self.database.bulk_insert(&records).await?;
    Ok(())
}
```

Batching is set in the shared `[processing]` section, not in connector settings:

```toml
[processing]
batch_size = 1000
batch_timeout_ms = 1000
```

## Configure your connector

Flatten `ConnectorConfig` into your own config struct so one TOML file holds both:

```rust
#[derive(Deserialize)]
pub struct MyConfig {
    #[serde(flatten)]
    pub core: ConnectorConfig,
    pub my_connector: MySettings,
}
```

<Tabs>
  <TabItem label="Source TOML">

```toml
danube_service_url = "http://danube-broker:6650"
connector_name = "my-source"

[processing]
poll_interval_ms = 100
metrics_port = 9090

[[schemas]]
topic = "/iot/sensors"
subject = "sensor-data"
schema_type = "json_schema"
schema_file = "schemas/sensor.json"
version_strategy = "latest"

[my_connector]
external_host = "system.example.com"

[[my_connector.routes]]
from = "input/*"
to = "/iot/sensors"
partitions = 4
```

  </TabItem>
  <TabItem label="Sink TOML">

```toml
danube_service_url = "http://danube-broker:6650"
connector_name = "my-sink"

[processing]
batch_size = 500
batch_timeout_ms = 1000
metrics_port = 9090

[my_connector]
target_url = "http://database.example.com"

[[my_connector.routes]]
from = "/events/users"
subscription = "sink-group-1"
subscription_type = "Shared"
to = "users_table"
expected_schema_subject = "user-events-v1"
```

  </TabItem>
</Tabs>

<Aside type="note">
Sources define `[[schemas]]` to control serialization. Sinks usually skip it, because the runtime deserializes automatically.
</Aside>

## Classify errors

Return the right result from your trait methods and the runtime reacts:

- **`Retryable`**: temporary failure (network, rate limit, timeout). Retried with exponential backoff.
- **`InvalidData`**: a record that can never succeed. Logged and skipped.
- **`Fatal`**: unrecoverable (auth failure, bad config). Graceful shutdown.
- **`Ok(())` / `Ok(vec![])`**: success, or no data right now. Keep going.

<Aside type="tip">
For partial batch failures in a sink, handle skippable records inside `process_batch()` and only return an error for the part that really failed.
</Aside>

## Test it end to end

<Steps>

1. **Start Danube.**

   ```bash
   # A local standalone broker
   danube up standalone

   # Or the 3-broker cluster from the danube repo
   cd docker && docker compose up -d --build
   ```

2. **Create the topic** your connector uses.

   ```bash
   danube topic create /your/topic --intent event_stream
   ```

3. **Point to your config and run the connector.**

   ```bash
   export CONNECTOR_CONFIG_PATH=./config/connector.toml
   cargo run
   ```

4. **Verify a source**: open a consumer before the connector publishes, then watch records arrive.

   ```bash
   danube consume /your/topic -s test-sub
   ```

5. **Verify a sink**: publish a test message (`-r` because the topic is reliable), then check the target system.

   ```bash
   danube produce /your/topic -r -m '{"test":"data"}'
   ```

</Steps>

For unit tests, exercise transformation and routing logic in isolation, mock external systems and cover the error paths.
