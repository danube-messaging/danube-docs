The Load Manager decides which broker owns each topic. It places new topics on the least-loaded broker, reassigns topics when a broker dies, and can move topics on its own to keep the cluster even. You tune it live with `danube cluster load-manager`, no restart needed.

```bash
# Score brokers on CPU, memory and topic load, and turn on automated rebalancing
danube cluster load-manager --assignment-strategy balanced --rebalance true --profile balanced

# Print the current live cluster config (including load_manager)
danube cluster load-manager
```

<Aside type="note">
This page covers internals. For day-to-day operations see [CLI: Cluster & Brokers](/admin/cli-cluster/).
</Aside>

## What it does

<CardGrid>
  <Card title="Topic assignment" icon="rocket">
    Picks the owning broker for every new topic.
  </Card>
  <Card title="Load monitoring" icon="magnifier">
    Collects a load report from every broker on a fixed interval.
  </Card>
  <Card title="Automated rebalancing" icon="random">
    Detects imbalance and moves one topic at a time to fix it.
  </Card>
  <Card title="Failover" icon="warning">
    Redistributes the topics of a crashed broker to healthy ones.
  </Card>
</CardGrid>

Only the Raft leader runs placement logic. Followers publish load reports and act on assignment changes, but never decide placement themselves.

## Load reports

Every broker writes a load report to the Raft metadata store every `load_report_interval_seconds` (default 30). The leader turns these reports into broker rankings.

**System metrics**

- **CPU usage**: processor utilization, 0-100%
- **Memory usage**: memory utilization, 0-100%
- **Disk I/O**: disk throughput in bytes/s
- **Network I/O**: network throughput in bytes/s

**Per-topic metrics**

- **Message rate and byte rate**: messages/s and throughput
- **Producers, consumers, subscriptions**: connection counts
- **Backlog**: unconsumed messages

## Pick an assignment strategy

Rankings are a list of `(broker_id, load_score)` pairs sorted least-loaded first. The assignment strategy decides how the score is computed. Set it with `--assignment-strategy fair|balanced|weighted_load`.

<CardGrid>
  <Card title="fair" icon="list-format">
    Counts topics only: `score = topic_count`. Lowest overhead and fully predictable. Good for development, testing and clusters with uniform topics.
  </Card>
  <Card title="balanced (default)" icon="approve-check">
    Mixes topic load with CPU and memory. The best accuracy-to-overhead ratio, and it accounts for brokers on different hardware. Recommended for production.
  </Card>
  <Card title="weighted_load" icon="setting">
    Finds the resource under the most pressure and weights it heavier. Best for workloads whose bottleneck shifts over time.
  </Card>
</CardGrid>

### How `balanced` scores a broker

```text title="balanced"
weighted_topic_load = (topic_count × 0.2) + (throughput_mbps × 0.3)
                    + (connections × 0.3) + (backlog / 10000 × 0.2)

score = (weighted_topic_load × 0.3) + (CPU × 0.35) + (Memory × 0.35)
```

### How `weighted_load` scores a broker

<Steps>

1. Normalize CPU, memory, disk, network, throughput and topic load to 0.0-1.0 against the busiest broker.
2. Find the bottleneck: the metric with the highest utilization.
3. If the bottleneck is above 70%, it gets 50% of the weight, a related metric gets 20%, and two others get 15% each. For example a CPU bottleneck scores `cpu × 0.5 + memory × 0.2 + throughput × 0.15 + topics × 0.15`.
4. Otherwise the score is spread out: topics, CPU and memory 25% each, throughput 15%, network 10%.

</Steps>

## How a new topic gets placed

<Steps>

1. **Unassigned marker.** The broker that creates the topic writes `/cluster/unassigned/{namespace}/{topic}`.
2. **Leader notices.** The leader watches `/cluster/unassigned/` and starts the assignment.
3. **Rank brokers.** The leader scores every active broker with the configured strategy.
4. **Select a broker.** It takes the least-loaded broker. Brokers within 10% of the minimum score (exactly equal when scores are below 10) are rotated round-robin so topics spread out.
5. **Write the assignment** to `/cluster/brokers/{broker_id}/{namespace}/{topic}`.
6. **Load the topic.** The target broker sees the new key under its prefix, creates the topic and starts serving clients.
7. **Clean up.** The leader deletes the marker and updates its in-memory usage, so the next placement already counts this topic.

</Steps>

### Special cases

- **Manual unload**: the marker carries a `from_broker` hint, and the leader excludes that broker as a target. Unload needs at least two active brokers.
- **Broker failure**: when a broker's registration disappears, the leader removes its assignments and writes an unassigned marker per topic. The normal pipeline spreads them over healthy brokers.
- **Equal loads**: identical scores are rotated round-robin, so an idle cluster does not pile every topic on one node.

## Automated rebalancing

Over time topic load drifts. When rebalancing is enabled, the leader checks balance on a timer and moves topics to restore it. It is off by default: turn it on with `--rebalance true`.

### Detect imbalance

The key metric is the **coefficient of variation** (CV) of broker scores:

```text title="CV"
CV = standard_deviation / mean_load
```

- **0**: perfectly balanced
- **Above the profile threshold** (0.2, 0.3 or 0.4): rebalancing kicks in

Brokers above `mean + std_dev` are overloaded and below `mean - std_dev` are underloaded. When CV is above 0.3 the band narrows to half a standard deviation for faster convergence. A floor of `max(mean × 0.2, 2)` on the standard deviation keeps idle clusters from being flagged.

### Choose a rebalancing profile

A profile is a preset for the CV threshold, check interval, move budget and cooldown. Set it with `--profile`; any of its values can be overridden with the matching flag.

<CardGrid>
  <Card title="conservative" icon="information">
    - Triggers at CV above 40%
    - Checks every 10 min (600s)
    - Max 5 moves per hour
    - 120s cooldown between moves

    For stable production with large topics.
  </Card>
  <Card title="balanced (default)" icon="approve-check">
    - Triggers at CV above 30%
    - Checks every 4 min (240s)
    - Max 10 moves per hour
    - 60s cooldown between moves

    For general production.
  </Card>
  <Card title="aggressive" icon="rocket">
    - Triggers at CV above 20%
    - Checks every 2 min (120s)
    - Max 20 moves per hour
    - 30s cooldown between moves

    For fast-changing workloads and testing.
  </Card>
</CardGrid>

### Pick which topic moves

<Steps>

1. **Source broker**: overloaded brokers donate topics. If none are overloaded but some are underloaded and the max-min gap is significant, brokers above the mean donate instead.
2. **Blacklist**: topics matching `blacklist_topics` are skipped. Patterns are an exact topic name (`/default/payments`) or a whole namespace (`/system/*`).
3. **Recently moved**: a topic moved within the longest of `min_topic_age_seconds`, `min_topic_age_before_move_secs` and `topic_move_cooldown_secs` is skipped.
4. **Lightest first**: the remaining topic with the lowest load score moves, because small topics are the least disruptive.
5. **Target**: the least-loaded active broker that is not the source.

</Steps>

```text title="Per-topic load score"
load_score = (byte_rate_MBps × 0.5) + (producers + consumers) × 0.3
           + (backlog / 10000 × 0.2)
```

### Execute the move

<Steps>

1. Write an unassigned marker with `reason: rebalance`, `from_broker` and a `to_broker` hint.
2. Delete the source assignment. The source broker seals the topic, drains in-flight messages and unloads it.
3. The leader honors the `to_broker` hint if that broker is still active and writes the new assignment.
4. The target broker loads the topic and starts serving.
5. The move is recorded at `/cluster/rebalancing_history/{timestamp}` for rate limiting, cooldowns and audit.

</Steps>

For reliable topics, steps 2 and 4 follow the [reliable topic move](/architecture/reliable-topic-move/) protocol so offsets stay continuous.

## Safety mechanisms

- **One move per cycle**: imbalance is recomputed before the next move, which prevents overshooting.
- **Rate limit**: `max_moves_per_hour` is enforced from move history.
- **Cooldown**: `cooldown_seconds` pause between moves, plus a per-topic re-move cooldown.
- **Minimum cluster size**: no rebalancing below `min_brokers_for_rebalance` (default 2) brokers.
- **Blacklist**: protected topics never move.
- **Leader only**: placement decisions are made in one place.
- **Active brokers only**: draining or drained brokers are never targets.
- **Graceful unload**: seal, drain, unload, the same path as a manual move.

## Configure the Load Manager

Settings live in Raft at `/cluster/config/load_manager` and every broker hot-reloads them. There are no startup flags for them.

<Tabs>
  <TabItem label="Live (CLI)">

```bash
danube cluster load-manager \
  --assignment-strategy balanced \
  --load-report-interval-seconds 30 \
  --rebalance true \
  --profile balanced \
  --min-brokers 2 \
  --min-topic-age-seconds 300 \
  --blacklist-topics "/system/*,/default/payments" \
  --replace-blacklist
```

- **`--assignment-strategy`**: `fair`, `balanced` or `weighted_load`
- **`--load-report-interval-seconds`**: how often brokers publish load reports
- **`--rebalance true|false`**: turn automated rebalancing on or off
- **`--profile`**: `conservative`, `balanced` or `aggressive` preset
- **`--check-interval-seconds`, `--max-moves-per-hour`, `--cooldown-seconds`**: override single values; they win over `--profile` in the same command
- **`--min-brokers`**: minimum active brokers before rebalancing runs
- **`--min-topic-age-seconds`**: re-move protection window
- **`--blacklist-topics`**: comma-separated patterns, added to the list
- **`--replace-blacklist`**: replace the list instead of adding (use with an empty list to clear)

Run `danube cluster load-manager` with no flags to print the current live config.

  </TabItem>
  <TabItem label="Declarative (apply)">

```yaml title="desired_state.yaml"
load_manager:
  assignment_strategy: balanced        # fair | balanced | weighted_load
  load_report_interval_seconds: 30

  rebalancing:
    enabled: false                     # start disabled, enable after testing
    aggressiveness: balanced           # conservative | balanced | aggressive
    check_interval_seconds: 300
    max_moves_per_hour: 10
    cooldown_seconds: 60
    min_brokers_for_rebalance: 2
    min_topic_age_seconds: 300
    min_topic_age_before_move_secs: 60
    topic_move_cooldown_secs: 120
    blacklist_topics:
      - "/system/*"
      - "/default/payments"
```

```bash
danube apply -f desired_state.yaml --dry-run   # preview
danube apply -f desired_state.yaml
```

  </TabItem>
</Tabs>

### Check balance and rebalance by hand

You do not need automated rebalancing to fix a skewed cluster. Inspect the numbers, preview the moves, then run them:

```bash
danube broker balance                    # CV and per-broker load
danube broker rebalance --dry-run        # show proposed moves
danube broker rebalance --max-moves 3    # execute up to 3 moves
danube topic unload /default/orders      # move one specific topic
```

<Aside type="tip">
Start with `balanced` placement and rebalancing off. Watch `danube_cluster_imbalance_cv` for a while, then enable the `conservative` profile before trying anything faster.
</Aside>

## Observe balance

Prometheus metrics exposed by brokers:

- **`danube_cluster_imbalance_cv`** (gauge): current CV, set by the leader each check. Lower is better.
- **`danube_rebalancing_moves_total`** (counter, label `reason`): topic moves executed.
- **`danube_rebalancing_failures_total`** (counter): failed move attempts.
- **`danube_rebalancing_cycle_duration_seconds`** (histogram): time spent per rebalancing cycle.
- **`danube_broker_topics_owned`** (gauge): topics owned by each broker.
