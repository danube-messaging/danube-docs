Key-Shared gives you per-key ordering and multi-consumer parallelism at once. Every message with the same routing key goes to one consumer, in order, while different keys run on different consumers concurrently. This page shows how the broker pulls that off safely.

```bash
# Try it: two terminals, same subscription, Key-Shared
danube consume /default/orders -s workers -t key-shared
danube consume /default/orders -s workers -t key-shared

# Only receive keys that match a glob
danube consume /default/orders -s workers -t key-shared --key-filter "eu-*"
```

<Aside type="note">
This page covers internals. For the client API see [Key-Shared Subscriptions](/client-libraries/key-shared/).
</Aside>

## Design goals

- **Per-key ordering**: one consumer per key, in order. Never two messages of the same key in flight.
- **Multi-key parallelism**: throughput grows with the number of distinct keys.
- **Stable affinity**: adding or removing a consumer remaps about 1/N of keys, not all of them.
- **Cursor safety**: the persisted cursor never passes an unacked message, so restarts replay from the right spot.
- **Key-level fault isolation**: a poison message on one key never blocks other keys.

## Building blocks

Each reliable Key-Shared subscription is made of:

- **`KeySharedConsumerState`**: maps keys to consumers with a consistent hash ring and optional key filters.
- **`InFlightWindow`**: tracks in-flight and blocked messages, enforces one-message-per-key and contiguous cursor advancement.
- **Dispatch loop**: a `tokio::select!` over a command channel (acks, nacks, consumer changes) and a heartbeat timer.
- **Heartbeat watchdog**: every 500ms handles timeouts, retries, eviction and WAL polling.
- **`SubscriptionEngine`**: owns the WAL cursor, failure policy and debounced cursor persistence.
- **Poison handler**: applies `Drop`, `DeadLetter` or `Block` to retry-exhausted messages.

<Aside type="tip">
The non-reliable variant keeps only `KeySharedConsumerState`. No window, acks, retries or cursor: messages are routed inline and dropped if the target consumer's channel is full.
</Aside>

## Consistent hashing

Each consumer gets 100 virtual nodes on a 32-bit hash ring. A virtual node's position is `FNV-1a("{consumer_id}-{vnode_idx}")` with a murmur3 finalizer for good bit mixing. A routing key is hashed the same way, and a binary search finds the first virtual node at or after it (wrapping at the end).

- **Stable**: one consumer joining or leaving remaps about 1/N of keys. Tests over 1,000 keys see 15-55% remapped going from 2 to 3 consumers.
- **Deterministic**: a key always maps to the same consumer for a given consumer set.
- **Filter-aware**: when some consumers declare key filters, the ring is projected onto eligible consumers only. Without filters the full ring is used with zero allocation.

### Key filters

Consumers can declare glob patterns at subscribe time to limit which keys they receive:

- **`payment`**: exact match only
- **`ship*`**: `shipping`, `shipment`, ...
- **`eu-west-?`**: `eu-west-1`, `eu-west-2`, ...
- **`*`**: everything, same as no filter

Matching uses iterative backtracking, no regex. A key that matches no consumer is skipped and its offset is treated as acked so the cursor keeps moving.

## The in-flight window

Exclusive and Shared dispatchers track one pending delivery at a time. Key-Shared needs many in parallel, so it uses a window.

**The invariant**: at most one message per routing key is in flight. Further messages for that key wait in a blocked queue until the in-flight one is acked, nacked or timed out.

The window keeps these structures in sync:

- **Dispatched entries** (by WAL offset): in flight, awaiting ack
- **Active key set**: enforces one-per-key
- **Blocked queue**: messages waiting for their key to free up
- **Acked offsets set**: out-of-order acks, used to compute the cursor
- **Per-consumer counters**: in-flight count per consumer for backpressure

### Contiguous cursor advancement

The `safe_cursor` only moves forward across a contiguous run of acked offsets. That matters because the `SubscriptionEngine` persists it and replays from it after a restart.

```text title="Out-of-order acks"
Dispatched: 10, 11, 12, 13
Acked:      10, 12, 13      (11 still in flight)
safe_cursor = 10            (blocked by 11)

Ack 11 arrives:
safe_cursor = 13            (10..13 contiguous)
```

Out-of-order acks are normal here, since keys are processed independently. Future acks wait in the acked set, and `advance_safe_cursor()` drains contiguous entries as soon as the gap closes.

### Backpressure

- **Window size**: in-flight plus blocked messages are capped at the subscription's `max_unacked_messages` (cluster default 10, overridable per subscription). When full, the heartbeat stops polling the WAL, which pushes back on storage naturally.
- **Per-consumer cap**: a consumer holds at most 1,000 in-flight messages; extra messages for it go to the blocked queue. One slow consumer cannot take over the window.
- **Fair compute cost**: a message can carry an `x-danube-compute-cost-units` attribute (default 1). The window shares a cost budget (10× the window size) fairly across active keys, so one expensive key cannot starve the rest.

## Dispatch loop

```text title="Loop structure"
loop {
    select! {
        cmd = control_rx.recv() => handle_command(cmd)
        _   = heartbeat.tick()  => handle_heartbeat()
    }
}
```

- **Commands** come from the consumer handler and subscription engine: consumer add or remove, ack, nack, poll-and-dispatch triggers and flush requests.
- **Heartbeat** fires every 500ms and runs the five maintenance phases below.

## What the heartbeat does every 500ms

<Steps>

1. **Ack timeouts.** In-flight entries past their `ack_timeout` are marked for retry.

2. **Poison handling.** Entries that exhausted their retry budget go to the poison handler (see below).

3. **Retry re-dispatch.** Messages whose backoff has elapsed are dispatched again, using the hash ring. A retry can land on a different consumer if the ring changed, for example after an eviction.

4. **Evict inactive consumers.** The gRPC handler flips a status flag when a client disconnects. After 6 inactive ticks (3 seconds) the consumer is evicted: its in-flight offsets are marked acked, it leaves the ring, freed keys go to the remaining consumers via `dispatch_unblocked`, and the cursor is persisted if it moved.

5. **Lag-driven polling.** If the window has room and the WAL has unread entries, new messages are polled so throughput keeps up with fast producers.

</Steps>

### Poison policies

<CardGrid>
  <Card title="Drop" icon="random">
    Skip the message for this subscription. Its offset counts as acked, blocked messages for the key are released, and the message stays in the WAL for other subscriptions.
  </Card>
  <Card title="DeadLetter" icon="document">
    Publish the message to the DLQ topic (usually `<topic>-dlq`), then behave like Drop.
  </Card>
  <Card title="Block" icon="warning">
    Leave the message in place. Its key stays active and stops, but every other key keeps flowing.
  </Card>
</CardGrid>

Set the policy per subscription with `danube topic subscription failure-policy set`, or get a sensible default from the topic's [stream intent](/concepts/stream-intents/).

<Aside type="caution" title="Eviction trades a few messages for liveness">
Offsets held by an evicted consumer are treated as acked, so those specific messages may be lost (at-most-once for that consumer's in-flight work). Keeping them pending forever would leave a permanent gap and stall the cursor. Danube chooses subscription liveness during consumer failure.
</Aside>

<Aside type="note">
Key-Shared advances its own cursor instead of delegating to the engine, because contiguous tracking across many in-flight messages needs the `InFlightWindow`.
</Aside>

## How it compares

- **Exclusive**: 1 consumer, total order, single-slot tracking, sequential cursor, failover on consumer loss.
- **Shared**: N consumers, no ordering, single-slot tracking, sequential cursor, round-robin.
- **Key-Shared**: N consumers, per-key order, multi-message window, contiguous-ack cursor, hash ring with glob filters, per-consumer plus window backpressure, about 1/N keys remapped on change.
