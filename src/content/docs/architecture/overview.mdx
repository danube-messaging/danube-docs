Danube is a distributed pub/sub and streaming system written in Rust, shipped as one `danube` binary. Brokers coordinate through embedded Raft, so there is no ZooKeeper, etcd or external database to run. This page maps the moving parts and the design choices behind them.

```bash
# Every node runs the same binary; the mode decides the shape
danube up standalone                                  # one node, everything local
danube up cluster --data-dir /var/lib/danube --seed-nodes n1:7650,n2:7650,n3:7650
```

<Aside type="note">
This section is for advanced users and contributors. For usage, start with the [Quickstart](/getting-started/quickstart/) and [Concepts](/concepts/topics/).
</Aside>

## Brokers

Brokers are the core component. Each broker:

- Accepts client gRPC connections on `--listen` (default `127.0.0.1:6650`).
- Serves client pub/sub, the Schema Registry and the admin gRPC API on that same port, unless you split admin out with `--admin-listen`.
- Routes messages from producers to matching subscriptions.
- Owns topics and manages their lifecycle.
- Takes part in Raft as a voter or learner on `--raft-port` (default `7650`).

Any broker can become the Raft leader. The leader coordinates metadata writes, while every broker serves reads from its local replica.

## Metadata store (Raft)

Danube embeds a Raft group across all brokers using [openraft](https://github.com/databendlabs/openraft), with [redb](https://github.com/cberner/redb) for the durable log. The replicated state machine holds:

- Broker registration and health
- Topic ownership (which broker owns which topic)
- Live cluster configuration under `/cluster/config/*` (storage, write buffer, WAL, load manager)
- Namespaces and their policies
- Schema Registry subjects, versions and compatibility settings
- Load reports and topic metadata
- Cluster audit entries under `/cluster/audit/*`

**Why it works this way**

- **No external metadata store**: consensus is built in, which removes an operational dependency.
- **Writes through Raft**: every mutation (topic creation, schema registration, broker registration) goes through the leader for strong consistency.
- **Reads from local state**: each broker keeps the full state machine in memory, so topic lookups, schema fetches and broker lists cost zero network hops.

<Aside type="tip">
Cluster-wide settings live in Raft, not in startup flags. Change them live with `danube cluster ...` or declaratively with `danube apply -f desired_state.yaml`. See [Configuration workflow](/getting-started/configuration-workflow/).
</Aside>

## Storage layer

Storage only matters for reliable topics; non-reliable topics never touch it.

- **Write-ahead log (WAL)**: low-latency, append-only log on the owning broker. Messages land here before the producer gets an ack.
- **Valkey write buffer (optional)**: messages are also written to Valkey Redis Streams, giving RPO=0 crash recovery without making brokers stateful.
- **Durable segments**: immutable files created when WAL segments seal. Used for replay, broker recovery and topic moves.

Pick a storage backend for the cluster with `danube cluster storage`:

<CardGrid>
  <Card title="local" icon="laptop">
    WAL and durable segments on the local filesystem. For single nodes and development.
  </Card>
  <Card title="shared-fs" icon="open-book">
    Local WAL staging, segments on a shared filesystem (NFS, EFS). For multi-node clusters with shared storage.
  </Card>
  <Card title="object-store" icon="star">
    Local WAL staging, segments in S3, GCS or Azure Blob. For cloud-native deployments.
  </Card>
</CardGrid>

The Valkey buffer is optional with every backend (`danube cluster write-buffer enable`).

**Tiered reads**: consumers read recent data from the local WAL. For older data, the broker reads from Valkey (warm) and durable segments (cold), then chains them into the WAL tail.

Read more in [Persistence & Storage](/concepts/persistence/) and [Durability & Storage](/durability/overview/).

## Dispatch strategies

Each topic picks a dispatch strategy at creation, usually through a [stream intent](/concepts/stream-intents/).

<CardGrid>
  <Card title="Non-reliable" icon="rocket">
    Producers to consumers with no persistence. Zero storage overhead, lowest latency, at-most-once. For live metrics and telemetry (`--intent realtime`).
  </Card>
  <Card title="Reliable" icon="approve-check">
    Persisted before ack, at-least-once with replay. For events, tasks and audit logs (`--intent event_stream`, `task_queue`, `audit_log`).
  </Card>
</CardGrid>

The reliable pipeline:

1. The producer sends to the owning broker.
2. The broker appends to its local WAL.
3. The broker acks the producer.
4. Sealed WAL segments are flushed to durable storage.
5. Consumers read from the WAL (recent) or durable segments (historical).

Raft tracks segment descriptors, durable frontiers and sealed topic state, so a topic recovers correctly after a broker failure. See [Dispatch Strategies](/concepts/dispatch-strategies/).

## Topic ownership and load balancing

Each topic is owned by exactly one broker at a time, recorded in Raft. A client can connect to any broker: it serves the topic if it owns it, or redirects the client to the owner.

The [Load Manager](/architecture/load-manager/) scores brokers, places new topics on the least-loaded one and can rebalance automatically when the coefficient of variation (CV) of broker load passes a threshold.

Moving a reliable topic is coordinated: the source seals its WAL and flushes durable storage, then the target resumes from durable segments at the same offset. No messages are lost. See [Reliable Topic Move](/architecture/reliable-topic-move/) and [CLI: Cluster & Brokers](/admin/cli-cluster/).

## Data layout on disk

<FileTree>
- danube-data/ (`--data-dir`, default `./danube-data` in standalone)
  - danube-node.json (records the mode; reuse with another mode is refused)
  - raft/
    - raft-log.redb (Raft log and state, redb)
    - node_id (stable node identity)
  - wal/ (per-topic `wal.log` and rotated `wal.<seq>.log`; override with `--wal-dir`)
</FileTree>

With `shared-fs` or `object-store` storage, sealed durable segments are exported to `{root}/storage/topics/{namespace}/{topic}/segments/`.
