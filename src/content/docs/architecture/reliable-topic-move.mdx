When a reliable topic changes broker (rebalancing, maintenance, a node leaving), nothing should look different to clients. Producers keep writing at the next offset, consumers keep reading the same history, and subscription cursors stay valid. This page explains the handoff protocol that guarantees it.

```bash
# Move one topic to another broker, or drain a whole broker
danube topic unload /default/orders
danube broker unload --broker-id 12345678 --dry-run
```

<Aside type="note">
This page covers internals. For operational commands see [CLI: Cluster & Brokers](/admin/cli-cluster/).
</Aside>

## The idea in one paragraph

Danube never ships an in-memory topic object between brokers. The old owner **seals** the topic and makes its history durable, then the new owner **rebuilds** the topic from metadata. Two boundaries are preserved: the **last committed offset** on the old owner and the **durable history frontier** readers can rely on. Everything else (cache, local WAL files, producer connections) is transient and rebuilt.

## State a move touches

  <Card title="Local WAL" icon="laptop">

  <Card title="Durable segments" icon="document">

  </Card>
  <Card title="Raft metadata" icon="setting">

  </Card>
  <Card title="Subscription cursors" icon="approve-check">
    Stored separately from the WAL, so consumers resume at the same logical offset after a move.
  </Card>
</CardGrid>

The persistence metadata for a topic looks like this (under the `/danube` storage prefix):

<FileTree>
- /danube/storage/topics/default/my-topic/
  - segments/
    - 00000000000000000000 (SegmentDescriptor, offsets 0-511)
    - 00000000000000000512 (SegmentDescriptor, offsets 512-1023)
    - cur (padded start offset of the latest segment)
  - state (StorageStateSealed marker)
</FileTree>

## Step 1: the old broker seals the topic

<Steps>

1. Stop accepting writes on the topic's storage instance.
2. Capture `last_committed_offset`.
3. Shut down the WAL cleanly.
4. Stop the background segment exporter and deleter.
5. Export any local WAL history that is not durable yet.
6. Clear the broker-local WAL directory.
7. Write the sealed marker into metadata.

</Steps>

```text title="Sealed marker at /danube/storage/topics/{ns}/{topic}/state"
StorageStateSealed {
  sealed: true,
  last_committed_offset: N,
  broker_id: <old broker>,
  timestamp: <seal time>
}
```

It means: "the old owner accepted offsets through `N`; the next owner resumes at `N + 1`".

### How the remaining history is exported

<Steps>

1. Read the current WAL checkpoint.
2. Select eligible WAL files.
3. Trim each file to the last safe frame boundary.
4. Extract the segment's offset range.
5. Upload the safe prefix as a durable segment.
6. Write its `SegmentDescriptor` to metadata.
7. Move the `segments/cur` pointer.

</Steps>

This is the history the new owner and late readers depend on.

## Step 2: the new broker recovers the topic

`StorageFactory::for_topic()` builds a fresh storage instance. The key decision is the first WAL offset, made by `resolve_recovery_start()`. First match wins:

<Steps>

1. **Sealed marker present**: resume at `last_committed_offset + 1`. This is the path for every planned move.
2. **Local WAL still on disk**: the WAL recovers from its own checkpoint (a normal restart).
3. **Valkey write buffer has data**: replay buffered, not-yet-exported messages into a fresh WAL (crash recovery).
4. **Durable segment catalog** (`shared-fs` / `object-store` only): resume at the latest segment's `end_offset + 1`.
5. **Nothing found**: start an empty topic at offset `0`.

</Steps>

### Hot cutover

A topic resumed from a sealed marker runs in **hot cutover** mode. Durable history is authoritative for everything before the takeover, and the new owner's WAL is authoritative only for the tail it writes itself. The new owner never claims history it does not hold locally.

## What clients see

<CardGrid>
  <Card title="Producers" icon="rocket">
    Reconnect to the new owner and keep writing. If the old broker sealed at 21, the next message gets offset 22.
  </Card>
  <Card title="Consumers" icon="magnifier">
    Resume from their subscription cursor. Acked through 13? They ask for 14, wherever it lives.
  </Card>
</CardGrid>

The tiered storage orchestrator serves the consumer's request in one of two ways:

- **Offset is in the hot WAL window**: read straight from the new broker's WAL.
- **Offset is older**: a tiered reader streams from durable history first, then hands off to the new WAL.

```text title="One logical stream"
Offsets 14..21  -> durable history
Offsets 22..N   -> new broker's hot WAL
```

No cursor translation is needed, because the offset space never broke.

<Aside type="note" title="Valkey is not involved in planned moves">
The old broker stops producers and exports everything before handing off, so there is no gap to fill. Valkey only matters for **unplanned** failures. See [Crash Recovery](/durability/crash-recovery/).
</Aside>

## How storage modes differ

The protocol is the same in every mode. What changes is when durable history gets written.

- **`local`**: no background export loop. Segments are exported during the seal, so this mode leans hardest on the seal step.
- **`shared-fs`**: WAL is staged locally and a background loop keeps publishing sealed segments. At move time most history is already shared; the seal exports only the tail.
- **`object-store`**: like `shared-fs`, but segments go to S3, GCS or Azure Blob via OpenDAL. History is broker-independent before the move even starts.

Switch modes live with `danube cluster storage local|shared-fs|object-store`.

## Walkthrough: moving a topic at offset 21

Start: broker A accepted offsets `0..21`, a consumer acked through `13`, durable history covers `0..21`.

<Steps>

1. **Broker A seals**: records `last_committed_offset = 21`, exports any remaining history, clears local WAL files and writes `StorageStateSealed`.
2. **Broker B loads**: reads the sealed marker and creates its WAL with `initial_offset = 22`.
3. **Producers reconnect**: new messages get `22, 23, 24, ...`.
4. **Consumers reconnect**: resume at `14`, read `14..21` from durable history and `22..` from B's hot WAL.

</Steps>

Both boundaries hold:

- **Write boundary**: `21 -> 22`, no gap and no overlap, thanks to the sealed marker.
- **Read boundary**: durable history chains into the hot WAL through the tiered reader.

## Code map

Components in `danube-persistent-storage`:

- **`StorageStateSealed`**: takeover marker with the last committed offset.
- **`SegmentDescriptor` + `segments/cur`**: the durable history catalog.
- **`StorageFactory::resolve_recovery_start()`**: picks the next correct WAL offset.
- **`TieredStorage::with_hot_cutover()`**: keeps historical and hot reads aligned after takeover.
