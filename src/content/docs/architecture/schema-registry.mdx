The Schema Registry is built into every broker: no extra service to run. Schemas live in Raft, so every broker answers schema lookups from memory and every write is consistent cluster-wide. This page explains how that works under the hood.

```bash
# Register a schema, bind it to a topic, and enforce it
danube schema register orders --schema-type json_schema --file orders.json
danube topic schema configure /default/orders --subject orders --validation-policy enforce
```

<Aside type="note">
This page covers internals. For usage see [Client Libraries: Schema Registry](/client-libraries/schema-registry/) and [CLI: Resources](/admin/cli-resources/).
</Aside>

## Three parts, three jobs

<CardGrid>
  <Card title="Registry (in the broker)" icon="puzzle">
    Registers, versions and compatibility-checks schemas over the broker's gRPC port. Any broker serves reads; writes go to the Raft leader.
  </Card>
  <Card title="Raft metadata store" icon="document">
    Persistent, replicated home for subjects, versions, compatibility modes and the global schema ID counter. Every broker holds a full in-memory copy.
  </Card>
  <Card title="Enforcement layer" icon="approve-check">
    Checks each incoming message against the topic's schema config before routing it. Separate from registration-time compatibility checks.
  </Card>
</CardGrid>

## Storage model

Schemas and topic bindings are stored as a tree in the Raft state machine.

<FileTree>
- /schemas/
  - \{subject\}/
    - metadata (compatibility mode, created_at, created_by)
    - compatibility (backward, forward, full, none)
    - versions/
      - 1 (definition, type, fingerprint, description, tags)
      - 2
  - \_global/
    - next_schema_id (monotonic, cluster-wide)
  - \_index/
    - by_id/
      - \{schema_id\} (reverse lookup to subject)
- /topics/
  - \{namespace\}/\{topic\}/
    - schema_config (subject, validation_policy, enable_payload_validation)
</FileTree>

### Why it is shaped this way

- **Global schema IDs**: every version gets a cluster-unique ID from `_global/next_schema_id`. A consumer resolves any schema with a single ID lookup through `_index/by_id/`.
- **Fingerprint deduplication**: registering a schema whose SHA-256 fingerprint already exists in the subject returns the existing version instead of creating a new one.
- **Compatibility on the subject, policy on the topic**: evolution rules are subject-wide, but dev, staging and production topics can enforce the same schema with different strictness. See [Subject vs. Topic Policies](/concepts/messages/#subject-vs-topic-policies).

## Raft replication

<Steps>

1. A client sends a registration or compatibility change to any broker.
2. A non-leader forwards the request to the Raft leader.
3. The leader proposes a log entry with the mutation.
4. A majority of voters acknowledges and the entry commits.
5. Every broker applies the entry to its local state machine.

</Steps>

Every broker sees the same schema state in the same order. Once a write is acknowledged it is visible everywhere, with no eventual-consistency window. Schema ID allocation happens inside the Raft proposal, so IDs are strictly monotonic and never reused.

## Read path: always local

- **No network hops**: lookups by ID, subject or version are answered from the broker's in-memory replica.
- **No invalidation protocol**: applying a Raft entry updates memory directly.
- **Cached topic binding**: a topic stores its resolved schema ID, so per-message checks never query the registry.

The result: the consistency of a central registry with the speed of a local cache.

## What happens when you register a schema

<Steps>

1. **Parse.** The definition is parsed for its type (JSON Schema Draft 7, Avro, Protobuf). Malformed schemas fail before touching Raft.
2. **Fingerprint.** A SHA-256 hash of the normalized content is computed. A match in the subject returns the existing ID and version.
3. **Compatibility check.** Unless the mode is `none`, the new schema is checked against the latest version: `backward` (new reads old data), `forward` (old reads new data) or `full` (both).
4. **Raft proposal.** The new version, its allocated ID, metadata and the updated counter go into one log entry.
5. **Commit and reply.** All brokers apply the entry and the leader returns the schema ID and version.

</Steps>

## Where messages get validated

<CardGrid>
  <Card title="Producer (client library)" icon="laptop">
    A producer created with `with_schema_subject("orders")` resolves the latest (or pinned) version, caches it and serializes against it. Errors surface before the network.
  </Card>
  <Card title="Broker (topic policy)" icon="setting">
    The enforcement layer applies the topic's `validation_policy` to every message.
  </Card>
  <Card title="Consumer (optional)" icon="magnifier">
    Every message carries its `schema_id`, so consumers can fetch and verify it themselves.
  </Card>
</CardGrid>

### Broker validation policies

- **`none`**: no checks.
- **`warn`**: checks that a `schema_id` is present and matches the topic's subject. Mismatches are logged, the message is accepted.
- **`enforce`**: rejects messages with a missing or mismatched `schema_id`.

The common check is an integer comparison against the cached ID, so it adds negligible latency. With `--enable-payload-validation` in `enforce` mode the broker also deserializes and validates the payload itself. That costs more CPU, so keep it for topics where data quality is critical.

```bash
danube topic schema validation-policy /default/orders --policy enforce --enable-payload-validation
```

### Consumer options

- **Trust the broker**: on `enforce` topics, deserialize directly.
- **Fetch and validate**: look up the schema by ID (served locally by the connected broker) and validate before processing.
- **Cache at startup**: fetch once, reuse for every message. Recommended when the topic uses `warn` or `none`.

## Topic-schema binding rules

- **First producer wins**: the first producer that creates a topic with a schema subject sets the binding. Later producers must use the same subject or get an error.
- **Admin override**: `danube topic schema configure` changes a topic's subject, intended for controlled migrations.
- **One subject, many topics**: topics can share a subject, the usual way to give dev, staging and production one evolution path.
- **Immutable versions**: a version never changes once created. Deletion is admin-only.

<Aside type="tip" title="Got JSON but no schema?">
Sample recent messages and get a Draft-07 JSON Schema back. AI agents can do the same through [MCP](/ai-agents/overview/).

```bash
danube topic schema infer /default/user-events --sample-size 100
```
</Aside>

## Observe validation

Prometheus counters emitted by the enforcement layer:

- **`danube_schema_validation_total`**: validation attempts, labeled `topic` and `policy` (`warn`, `enforce`).
- **`danube_schema_validation_failures_total`**: failures, labeled `topic` and `reason` (`missing_schema_id`, `subject_mismatch`, `payload_invalid`).

Use them to track schema adoption, alert on failure spikes after a schema update, and find misconfigured `enforce` topics.
