A producer publishes messages to one topic. Build it, call `create()` once to register with the broker, then `send()` as often as you like.

## Send your first message

<Tabs syncKey="client-lang">
<TabItem label="Rust">

```rust title="Create a producer and send"
use danube_client::DanubeClient;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let client = DanubeClient::builder()
        .service_url("http://127.0.0.1:6650")
        .build()
        .await?;

    let mut producer = client
        .new_producer()
        .with_topic("/default/my-topic")
        .with_name("my-producer")
        .build()?;

    producer.create().await?;

    let seq = producer.send(b"Hello Danube!".to_vec(), None).await?;
    println!("sent, sequence id {seq}");

    Ok(())
}
```

</TabItem>
<TabItem label="Go">


If the topic does not exist yet, `create()` auto-creates it (on by default): non-reliable unless the producer asks for reliable dispatch. For anything that must not lose data, create the topic first with an intent (see [Publish to an intent topic](#publish-to-an-intent-topic)).

## Rust builder methods

Required:

- **with_topic(name)**: target topic, for example `/default/orders`.
- **with_name(name)**: producer name, unique within the topic.

Optional:

- **with_reliable_dispatch()**: make the topic reliable if this producer auto-creates it. On an existing topic the topic's strategy wins, and only a reliable request on a non-reliable topic is rejected.
- **with_partitions(n)**: create the topic with `n` partitions if it does not exist yet. `0` is rejected.
- **with_schema_subject(subject)**: use the latest version of a registered schema.
- **with_schema_version(subject, v)**: pin to schema version `v`.
- **with_schema_min_version(subject, v)**: use version `v` or newer.
- **with_schema_reference(SchemaReference)**: low-level form of the three schema methods above.
- **with_options(ProducerOptions)**: retry and backoff settings.

Producer methods:

- **create()**: register with the broker. Discovers partitions of existing topics.
- **send(payload, attributes)**: publish bytes, returns the message sequence id (`u64`).
- **send_with_key(payload, attributes, key)**: publish with a routing key.

## Common tasks

### Add attributes

Attributes are string key-value pairs that travel with the message: trace ids, content types, routing hints.

<Tabs syncKey="client-lang">
<TabItem label="Rust">

```rust title="Send with attributes"
use std::collections::HashMap;

let attributes = HashMap::from([
    ("source".to_string(), "app-1".to_string()),
    ("priority".to_string(), "high".to_string()),
]);

producer.send(b"Important message".to_vec(), Some(attributes)).await?;
```

</TabItem>

```go title="Send with attributes"
attributes := map[string]string{
```

### Publish to an intent topic

Stream intents pick delivery, durability and retry settings for you. Create the topic once with the CLI:

```bash
danube topic create /default/orders --intent event_stream --partitions 3
```

`event_stream`, `task_queue` and `audit_log` create **reliable** topics. The existing topic's strategy wins, so the producer attaches with reliable dispatch either way. Calling `with_reliable_dispatch()` is optional here. It documents intent, and makes the topic reliable if the producer ever auto-creates it. Leave out `with_partitions()`: `create()` looks up the existing partitions and attaches to all of them.

<Tabs syncKey="client-lang">
<TabItem label="Rust">

```rust title="Producer for a reliable intent topic"
let mut producer = client
    .new_producer()
    .with_topic("/default/orders")
    .with_name("orders-producer")
    .with_reliable_dispatch()
    .build()?;

producer.create().await?;
```

</TabItem>
<TabItem label="Go">

```go title="Producer for a reliable intent topic"
producer, err := client.NewProducer().
    WithName("orders-producer").
    WithTopic("/default/orders").
    WithDispatchStrategy(danube.NewReliableDispatchStrategy()).
    Build()

producer.Create(ctx)
```

</TabItem>
<TabItem label="Java">

```java title="Producer for a reliable intent topic"
Producer producer = client.newProducer()
        .withTopic("/default/orders")
        .withName("orders-producer")
        .withDispatchStrategy(DispatchStrategy.RELIABLE)
        .build();

producer.create();
```

</TabItem>
<TabItem label="Python">

```python title="Producer for a reliable intent topic"
from danube import DispatchStrategy

producer = (
    client.new_producer()
    .with_topic("/default/orders")
    .with_name("orders-producer")
    .with_dispatch_strategy(DispatchStrategy.RELIABLE)
    .build()
)
await producer.create()
```

</TabItem>
</Tabs>

<Aside type="caution" title="Reliable producer on a non-reliable topic">
A producer without `with_reliable_dispatch()` can attach to a reliable topic. The reverse is rejected: a reliable producer on a non-reliable topic fails `create()` with `FailedPrecondition: Producer requested reliable dispatch, but topic '<topic>' is non-reliable`. For `realtime` topics, leave `with_reliable_dispatch()` out.
</Aside>

Check the topic end to end from two terminals. Start the consumer first: a new subscription on a reliable topic starts at the end.

```bash
# terminal 1
danube consume /default/orders -s smoke-test

# terminal 2 (the topic is already reliable, so no -r is needed)
danube produce /default/orders -m "order 1001"
```

See [Stream Intents](/concepts/stream-intents/) for what each intent configures and [Dispatch Strategies](/concepts/dispatch-strategies/) for reliable versus non-reliable delivery.

### Create a partitioned topic from code

Partitions spread one topic over several brokers. If you are not pre-creating the topic with the CLI, ask the producer to create it with `n` partitions:

<Tabs syncKey="client-lang">
<TabItem label="Rust">

```rust title="Partitioned producer"
let mut producer = client
    .new_producer()
    .with_topic("/default/high-throughput")
    .with_name("partitioned-producer")
    .with_partitions(3)
    .build()?;

producer.create().await?;
```

</TabItem>
<TabItem label="Go">

```go title="Partitioned producer"
producer, err := client.NewProducer().
    WithName("partitioned-producer").
    WithTopic("/default/high-throughput").
    WithPartitions(3).
    Build()

producer.Create(ctx)
```

</TabItem>
<TabItem label="Java">

```java title="Partitioned producer"
Producer producer = client.newProducer()
        .withTopic("/default/high-throughput")
        .withName("partitioned-producer")
        .withPartitions(3)
        .build();

producer.create();
```

</TabItem>
<TabItem label="Python">

```python title="Partitioned producer"
producer = (
    client.new_producer()
    .with_topic("/default/high-throughput")
    .with_name("partitioned-producer")
    .with_partitions(3)
    .build()
)
await producer.create()
```

</TabItem>
</Tabs>

The topic becomes `-part-0`, `-part-1` and `-part-2` internally. How messages are spread:

- **send()**: round-robin across partitions.
- **send_with_key()**: FNV-1a hash of the key picks the partition, so one key always lands on the same partition.

### Route messages by key

`send_with_key()` keeps all messages for one key (an order, a user, a device) in order and on the same consumer of a Key-Shared subscription:

```rust
producer.send_with_key(data, None, &format!("order-{order_id}")).await?;
```

The [Key-Shared guide](/client-libraries/key-shared/) covers the consumer side and key filters in every language.

### Attach a schema

Link the producer to a registered schema subject and the broker can validate every message:

```rust
let mut producer = client
    .new_producer()
    .with_topic("/default/user-events")
    .with_name("events-producer")
    .with_schema_subject("user-events")
    .build()?;
```

Registration, version pinning and validation policies are in the [Schema Registry guide](/client-libraries/schema-registry/).

### Tune retries (Rust)

`create()` and `send()` retry transient failures with exponential backoff. When `send()` runs out of retries, the client looks up the topic owner again and recreates the producer, which handles topics moving between brokers.

```rust title="Producer retries and backoff"
use danube_client::ProducerOptions;

let options = ProducerOptions::new(
    5,      // max_retries
    200,    // base_backoff_ms
    10_000, // max_backoff_ms
);

let mut producer = client
    .new_producer()
    .with_topic("/default/orders")
    .with_name("resilient-producer")
    .with_reliable_dispatch()
    .with_options(options)
    .build()?;
```

### Send a request and wait for the reply (Rust)

`DanubeClient::request_reply` handles RPC over topics: it stamps the request with `x-danube-correlation-id` and `x-danube-reply-to`, listens on the reply topic and returns the matching reply or a timeout error.

```rust title="Correlated request-reply"
use std::collections::HashMap;
use std::time::Duration;

let attrs = HashMap::from([("tool".to_string(), "sql_query".to_string())]);

let reply = client
    .request_reply(
        "/agents/tool-requests",
        "/agents/tool-replies",
        br#"{"query":"SELECT count(*) FROM orders"}"#.to_vec(),
        Some(attrs),
        Duration::from_secs(10),
    )
    .await?;

println!("reply: {}", String::from_utf8_lossy(&reply.payload));
```

The reply topic is a non-reliable topic, created on demand. See [Danube for AI Agents](/ai-agents/overview/) for the responder side.

## Topic names

Topics are `/{namespace}/{topic}`. The topic part may contain more `/` segments and dots.

- `/default/orders`: `orders` in the `default` namespace.
- `/production/user-events.v2`: dots are kept as part of the name.
- `/agents/team-a/tasks`: namespace `agents`, topic `team-a/tasks`.
