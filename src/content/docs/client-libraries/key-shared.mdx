description: Route messages by key for per-key ordering with many parallel consumers, plus glob key filters.

import { Card, CardGrid, LinkCard, Steps, Tabs, TabItem, Aside } from '@astrojs/starlight/components';

Key-Shared gives you the parallelism of a Shared subscription and the ordering of an Exclusive one, per key. Every message with the same routing key goes to the same consumer, in order, while different keys spread across all consumers.

Use it when events for one entity (an order, a user, a device) must be processed in sequence, but you still want many workers.

## Try it from the CLI

<Steps>

1. Create a reliable topic:

   ```bash
   danube topic create /default/orders --intent task_queue
   ```

2. Start two consumers on the same subscription, in two terminals:

   ```bash
   danube consume /default/orders -s orders_sub -t key-shared
   ```

3. Publish a few keyed messages from a third terminal:

   ```bash
   danube produce /default/orders -m "Payment for #1001" -k payment
   danube produce /default/orders -m "Order #1001 shipped" -k shipping
   danube produce /default/orders -m "Payment for #1002" -k payment
   ```

   Both `payment` messages land on the same consumer, in order.

</Steps>

## Send with a routing key

`send_with_key(payload, attributes, key)` tags each message with its key.

<Tabs syncKey="client-lang">
<TabItem label="Rust">

```rust title="Send with routing keys"
let mut producer = client
    .new_producer()
    .with_topic("/default/orders")
    .with_name("orders_producer")
    .with_reliable_dispatch()
    .build()?;

producer.create().await?;

producer.send_with_key(b"Payment for #1001".to_vec(), None, "payment").await?;
producer.send_with_key(b"Order #1001 shipped".to_vec(), None, "shipping").await?;
producer.send_with_key(b"Payment for #1002".to_vec(), None, "payment").await?;
```

</TabItem>

</TabItem>
</Tabs>

- **Any string works as a key**: order ids, user ids, device ids, event types.
- **Partitioned topics**: the client hashes the key (FNV-1a) to pick the partition, so one key always lands on the same partition.
- **Plain send()**: messages go round-robin across partitions, and the broker uses the producer name as the key.

## Consume with automatic key assignment

With no filters, the broker spreads keys over all consumers of the subscription using consistent hashing.

<Tabs syncKey="client-lang">
<TabItem label="Rust">

```rust title="Key-Shared consumer"
let mut consumer = client
    .new_consumer()
    .with_topic("/default/orders")
    .with_consumer_name("worker_1")
    .with_subscription("orders_sub")
    .with_subscription_type(SubType::KeyShared)
    .build()?;

consumer.subscribe().await?;
let mut stream = consumer.receive().await?;

while let Some(message) = stream.recv().await {
    let key = message.routing_key.as_deref().unwrap_or("<none>");
    println!("key={key:<10} | '{}'", String::from_utf8_lossy(&message.payload));
    consumer.ack(&message).await?;
}
```

</TabItem>
<TabItem label="Go">

```go title="Key-Shared consumer"
consumer, _ := client.NewConsumer().
    WithConsumerName("worker_1").
    WithTopic("/default/orders").
    WithSubscription("orders_sub").
    WithSubscriptionType(danube.KeyShared).
    Build()

consumer.Subscribe(ctx)
stream, _ := consumer.Receive(ctx)

for msg := range stream {
    fmt.Printf("key=%s payload=%s\n", msg.GetRoutingKey(), string(msg.GetPayload()))
    consumer.Ack(ctx, msg)
}
```

</TabItem>
<TabItem label="Java">

```java title="Key-Shared consumer"
Consumer consumer = client.newConsumer()
        .withTopic("/default/orders")
        .withConsumerName("worker_1")
        .withSubscription("orders_sub")
        .withSubscriptionType(SubType.KEY_SHARED)
        .build();
consumer.subscribe();

consumer.receive().subscribe(new Flow.Subscriber<>() {
    @Override public void onSubscribe(Flow.Subscription s) { s.request(Long.MAX_VALUE); }

    @Override
    public void onNext(StreamMessage msg) {
        String key = msg.routingKey() != null ? msg.routingKey() : "";
        System.out.printf("key=%s payload=%s%n", key, new String(msg.payload()));
        consumer.ack(msg);
    }

    @Override public void onError(Throwable t) {}
    @Override public void onComplete() {}
});
```

</TabItem>
<TabItem label="Python">

```python title="Key-Shared consumer"
consumer = (
    client.new_consumer()
    .with_topic("/default/orders")
    .with_consumer_name("worker_1")
    .with_subscription("orders_sub")
    .with_subscription_type(SubType.KEY_SHARED)
    .build()
)
await consumer.subscribe()
queue = await consumer.receive()

while True:
    message = await queue.get()
    key = message.routing_key if message.HasField("routing_key") else ""
    print(f"key={key} payload={message.payload.decode()}")
    await consumer.ack(message)
```

```text title="Two consumers, same subscription"
# worker_2

key=payment    | 'Payment for #1002'

```

## Pick keys with filters

Filters let a consumer declare exactly which keys it handles. It only receives messages whose key matches one of its glob patterns.

<Tabs syncKey="client-lang">
<TabItem label="Rust">

```rust title="Filtered consumer"
// Only "payment" and "invoice" messages
let mut consumer = client
    .new_consumer()
    .with_topic("/default/orders")
    .with_consumer_name("payments_worker")
    .with_subscription("orders_filtered")
    .with_subscription_type(SubType::KeyShared)
    .with_key_filter("payment")
    .with_key_filter("invoice")
    .build()?;

// Same thing in one call:
// .with_key_filters(vec!["payment".into(), "invoice".into()])
```

</TabItem>

From the CLI, repeat `--key-filter`:

```bash
danube consume /default/orders -s orders_filtered -t key-shared --key-filter payment --key-filter invoice
```

Pattern syntax:

- `payment`: exact match only.
- `ship*`: `*` matches any sequence, so `shipping`, `shipment`.
- `eu-west-?`: `?` matches one character, so `eu-west-1`, `eu-west-2`.
- `*`: everything, same as no filter.

When several consumers match the same key, consistent hashing picks one of them.

## How it behaves

- **One in-flight message per key** (reliable topics): the next message for a key waits until the previous one is acked. Other keys keep flowing.
- **Smooth rebalancing**: when a consumer joins or leaves, only about 1/N of keys move. The rest stay where they are.
- **Unmatched keys are skipped**: if no consumer's filters match a key, this subscription skips the message and moves on. Other subscriptions still see it.
- **Same ack and nack rules** as any other subscription, see the [Consumer guide](/client-libraries/consumer/#reject-a-message-nack).

## Typical keys

- **Order processing**: `order-{id}` keeps every event of one order in sequence.
- **Multi-tenant**: key `tenant-a-{id}` and give a dedicated consumer `with_key_filter("tenant-a-*")`.
- **IoT**: `device-{id}` keeps per-device state on one worker.

```rust
producer.send_with_key(data, None, &format!("order-{order_id}")).await?;
```
