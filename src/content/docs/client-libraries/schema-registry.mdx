The Schema Registry turns raw bytes into typed, validated messages. Register a schema once, point producers at its subject, and the broker can reject anything that does not match.

## The workflow

<Steps>

1. **Register** a schema under a subject, for example `user-events`.
2. **Link** a producer to the subject. Messages carry the schema id and version.
3. **Enforce** (optional): bind the subject to a topic with a validation policy.
4. **Consume** and decode, using the schema id on each message if you need it.

</Steps>

## Quick start

Save a JSON Schema as `user-events.json`:

```json title="user-events.json"
{
  "type": "object",
  "properties": {
    "user_id":   { "type": "string" },
    "event":     { "type": "string" },
    "timestamp": { "type": "integer" }
  },
  "required": ["user_id", "event", "timestamp"]
}
```

Register it and bind it to a topic with the CLI:

```bash
# Register the schema under the subject "user-events"
danube schema register user-events --schema-type json_schema --file user-events.json

# Reject messages on this topic that don't match the schema
danube topic schema configure /default/user-events --subject user-events --validation-policy enforce --enable-payload-validation
```

Then produce typed messages:

<TabItem label="Rust">

```rust title="Schema-linked producer"

    user_id: "user-123".into(),
    event: "login".into(),
    timestamp: 1_700_000_000,
})?;
producer.send(event, None).await?;
```

## Register schemas from code

Every client exposes a schema client on the same connection. Registering identical content again returns the existing id, so it is safe to run at startup.

<Tabs syncKey="client-lang">
<TabItem label="Rust">

```rust title="Register JSON Schema and Avro"
use danube_client::SchemaType;

let schema_client = client.schema();

let json_schema = std::fs::read("user-events.json")?;
let schema_id = schema_client
    .register_schema("user-events")
    .with_type(SchemaType::JsonSchema)
    .with_schema_data(json_schema)
    .with_description("User activity events")
    .execute()
    .await?;

let avro_schema = r#"{
    "type": "record",
    "name": "UserEvent",
    "namespace": "com.example",
    "fields": [
        {"name": "user_id", "type": "string"},
        {"name": "event", "type": "string"},
        {"name": "timestamp", "type": "long"},
        {"name": "metadata", "type": ["null", "string"], "default": null}
    ]
}"#;
let avro_id = schema_client
    .register_schema("user-events-avro")
    .with_type(SchemaType::Avro)
    .with_schema_data(avro_schema.as_bytes())
    .execute()
    .await?;
```

</TabItem>

Rust registration builder:

- **with_type(SchemaType)**: `JsonSchema`, `Avro`, `Protobuf`, `String`, `Number` or `Bytes`.
- **with_schema_data(bytes)**: the schema definition.
- **with_description(text)**, **with_created_by(name)**, **with_tags(vec)**: optional metadata.
- **execute()**: registers and returns the schema id (`u64`).

## Choose a schema version on the producer

- **with_schema_subject("user-events")**: always the latest version. The usual choice.
- **with_schema_version("user-events", 2)**: pinned to version 2, even after v3 exists. Good for legacy apps and staged rollouts.
- **with_schema_min_version("user-events", 2)**: version 2 or newer. Requires a minimum feature set but still upgrades.

<TabItem label="Rust">


## Consume and decode

The payload is still bytes: decode it with the library that matches the schema type.

<Tabs syncKey="client-lang">
<TabItem label="Rust">

```rust title="Decode JSON messages"
#[derive(serde::Deserialize, Debug)]
struct UserEvent { user_id: String, event: String, timestamp: i64 }

let mut stream = consumer.receive().await?;
while let Some(message) = stream.recv().await {
    let event: UserEvent = serde_json::from_slice(&message.payload)?;
    println!("{event:?} (schema v{:?})", message.schema_version);
    consumer.ack(&message).await?;
}
```

</TabItem>
<TabItem label="Go">

```go title="Decode JSON messages"
for msg := range stream {
    var event Event
    if err := json.Unmarshal(msg.GetPayload(), &event); err != nil {
        log.Printf("decode failed: %v", err)
        continue
    }
    fmt.Printf("Event: %+v\n", event)
    consumer.Ack(ctx, msg)
}
```

</TabItem>
<TabItem label="Java">

```java title="Decode JSON messages"

```

</TabItem>

## Evolve a schema safely

Each subject has a compatibility mode that every new version must pass:

- **backward** (default): the new schema can read data written with the old one. Upgrade consumers first.
- **forward**: the old schema can read data written with the new one. Upgrade producers first.
- **full**: both directions. For critical, long-lived data.
- **none**: no checks. Development only.

Check a candidate before you register it:

<Tabs syncKey="client-lang">
<TabItem label="Rust">

```rust title="Check compatibility"
let new_schema = std::fs::read("user-events-v2.json")?;

let result = schema_client
    .check_compatibility("user-events", new_schema, SchemaType::JsonSchema, None) // None = subject's mode
    .await?;

if result.is_compatible {
    println!("safe to register");
} else {
    eprintln!("incompatible: {:?}", result.errors);
}
```

</TabItem>
<TabItem label="Java">

```java title="Check compatibility"
CompatibilityCheck result = schemaClient.checkCompatibility(
        "user-events", newSchema.getBytes(), SchemaType.JSON_SCHEMA);

if (result.compatible()) {
    System.out.println("Safe to register!");
} else {
    System.out.println("Incompatible: " + result.errors());
}
```

</TabItem>
<TabItem label="Python">

```python title="Check compatibility"
is_compatible, errors = await schema_client.check_compatibility(
    "user-events",
    new_schema.encode(),
    SchemaType.JSON_SCHEMA,
    None,
)
print("Safe to register!" if is_compatible else f"Incompatible: {errors}")
```

</TabItem>
</Tabs>

Or from the CLI, together with changing the mode:

```bash
# Dry-run a new version against the subject's rules
danube schema check user-events --schema-type json_schema --file user-events-v2.json

# Change the subject's compatibility mode
danube schema set-compatibility user-events --mode full
```

Changing the mode needs the `ManageSchema` permission when auth is on. In Rust, `schema_client.set_compatibility_mode(subject, CompatibilityMode::Full)` does the same.

## Enforce schemas on the broker

A topic's validation policy decides what happens to messages that do not match its subject:

- **none**: no checks.
- **warn**: the broker logs a warning and accepts the message.
- **enforce**: the broker rejects messages with a missing, unknown or mismatched schema id.

`--enable-payload-validation` goes further and checks the payload itself against the schema, not just the id.

```bash
# Bind a subject and set the policy
danube topic schema configure /default/user-events --subject user-events --validation-policy enforce --enable-payload-validation

# Change only the policy later
danube topic schema validation-policy /default/user-events --policy warn

# See what a topic is bound to
danube topic schema show /default/user-events
```

## Infer a schema from live traffic

Already producing JSON without a schema? Sample recent messages and get a Draft-07 JSON Schema to start from:

```bash
danube topic schema infer /default/user-events --sample-size 100
```

Review the result, save it to a file and register it with `danube schema register`.

## Schema types

- **JSON Schema** (`json_schema`): JSON payloads, web APIs, general purpose.
- **Avro** (`avro`): compact binary records, data pipelines.
- **Protobuf** (`protobuf`): `.proto` definitions, cross-language RPC.
- **String** and **Bytes**: simple typed payloads without a structured schema.
