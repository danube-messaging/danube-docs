This page shows where a reliable message goes after it is produced, and where a consumer's read is served from. Knowing this tells you which tiers you need and what each one costs.

## The three tiers at a glance

<CardGrid>
  <Card title="Hot: WAL" icon="rocket">
    Local disk plus an in-memory cache. Pruned by the retention deleter: default 48 hours or 20 GiB per topic, checked every 5 minutes.
  </Card>
  <Card title="Warm: Valkey" icon="star">
    Redis Streams. Trimmed with `XTRIM` to the last N closed segments (default 5).
  </Card>
  <Card title="Cold: object storage" icon="open-book">
    S3, GCS, Azure Blob or a shared filesystem. Written by the segment exporter and kept indefinitely.
  </Card>
</CardGrid>

The tiers are independent. Their retention differs and their offset ranges overlap, which is what makes reads cheap.

## Write path

Every reliable message follows the same path, whatever you have enabled:

<Steps>

1. **Hot (always)**: the broker appends the message to the local WAL and assigns the next topic offset.

2. **Warm (if enabled)**: the broker also writes it to a Valkey stream with `XADD`, then calls `WAIT` until the configured number of replicas confirm.

3. **Ack**: the producer gets its acknowledgment.

4. **Cold (later, in the background)**: when a WAL file rotates, the exporter uploads the sealed segment as an immutable object. This is never on the producer's critical path.

</Steps>

```text
Producer -> Broker
              |- 1. WAL append (local disk)
              |- 2. XADD + WAIT to Valkey (if enabled)
              '- 3. ACK to producer
                     ...later...
              '- 4. Export sealed segment (if shared_fs or object_store)
```

<Aside type="tip">
The `WAIT` in step 2 is the durability guarantee. With `on_wait_timeout: fail` the producer is not acknowledged until Valkey replicas have the message. See [Configure durability](/durability/configuration/#add-the-valkey-write-buffer).
</Aside>

## Read path

One component, the tiered reader, decides where each read comes from.

### Live tail

A consumer that starts from the latest position reads straight from the WAL's in-memory broadcast. No Valkey call, no download: this is the common case for real-time work.

### Historical reads

A consumer that asks for an older offset gets one continuous stream stitched from the tiers. Each tier serves its own slice:

<Steps>

1. **Cold** serves `[start, warm_start - 1]`.
2. **Warm** serves `[warm_start, hot_start - 1]`.
3. **Hot** serves `[hot_start, ...)` through to live data.

</Steps>

- **hot_start**: the oldest offset still in the local WAL.
- **warm_start**: the oldest offset still in the Valkey stream.

## Three rules that keep it fast and safe

- **The WAL always wins.** If the WAL still holds an offset (on disk or in cache), it serves it. No network call.
- **The WAL usually holds more than Valkey.** Both get the same writes, but the WAL keeps hours or days while Valkey keeps a few segments. In normal operation Valkey is never read.
- **WAL files are never deleted before export.** The deleter only removes a rotated file once its whole offset range is in the durable store, so there is never a gap.

```text
WAL (Hot):     [-----offsets 0 to 5000---------]   (24h of data)
Valkey (Warm):          [--offsets 3000 to 5000-]   (last 5 segments)
Object (Cold): [-----offsets 0 to 4000---------]   (all exported segments)
```

A consumer asking for offset 1000 reads entirely from local disk.

## How each setup behaves

### WAL only

Cluster storage `local`, write buffer disabled. All reads come from the WAL. Once a file is pruned, that data is gone. Good for development, tests and edge nodes.

### WAL + object storage

Cluster storage `shared_fs` or `object_store`, write buffer disabled.

```text
Cold: [---offsets 0 to 800------]
WAL:       [---offsets 500 to 1000--]
```

- **Offset 200**: cold serves 200 to 499, then the WAL takes over.
- **Offset 600 or 950**: WAL only.

History is always available. Messages not yet exported are lost if the disk is lost.

### WAL + Valkey

Cluster storage `local`, write buffer enabled.

```text
WAL:    [---offsets 0 to 1000---]
Valkey:      [---offsets 700 to 1000-]
```

Reads go to the WAL. Valkey earns its keep after a crash: if the WAL is lost, the new owner replays buffered messages from Valkey into a fresh WAL. See [Crash recovery](/durability/crash-recovery/).

### WAL + Valkey + object storage

The full production setup. Right after startup every read is served by the WAL. After the deleter has pruned old WAL files:

```text
Cold:   [---offsets 0 to 4000---------]
Valkey:          [--offsets 3000 to 5000-]
WAL:               [--offsets 4000 to 5000-]
```

- **Offset 2000**: cold serves 2000 to 2999, Valkey 3000 to 3999, then the WAL.
- **Offset 3500**: Valkey serves 3500 to 3999, then the WAL.
- **Offset 4200**: WAL only.

## The role of each tier

- **Hot (WAL)**: source of truth for every write and the preferred source for every read it can serve.
- **Warm (Valkey)**: crash safety net for data not yet exported. Rarely read in normal operation.
- **Cold (object storage)**: long-term archive and the source of history after WAL and Valkey have rotated it out.
