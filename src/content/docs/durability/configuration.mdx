Durability in Danube is a cluster setting, not a config file. You change it live with `danube cluster ...` (stored in Raft and applied by every broker without a restart) or declare it once in a manifest with `danube apply`. The only per-node choice is where the WAL lives on disk.

## Quick start: S3 in two commands

```bash
# Export sealed WAL segments to S3 (uses the node's IAM role)
danube cluster storage object-store --backend s3 --root my-danube-bucket/prod --option region=us-east-1

# Check what the cluster is now running with
danube cluster storage show
```

`danube cluster storage show` prints the effective cluster configuration as YAML: storage mode, WAL settings and write buffer. It is the same document as `danube cluster export-config`, so it can include credentials and the JWT secret: avoid pasting it into tickets or logs.

## Put the WAL on a fast disk (per node)

Each node keeps its WAL in `<data-dir>/wal` by default, next to the Raft log. To move it to a dedicated NVMe volume, pass `--wal-dir` when you start the node:

```bash
danube up cluster --data-dir /var/lib/danube --wal-dir /mnt/nvme-wal --seed-nodes broker1:7650,broker2:7650,broker3:7650
```

This is the only storage path you set per node. Everything else on this page is cluster-wide.

## Choose a storage mode

The storage mode decides where sealed WAL segments are exported. Changes are written to Raft and picked up by every broker.

<CardGrid>
  <Card title="local" icon="laptop">
    Segments stay on each broker. Single node, development, edge. This is the default.
  </Card>
  <Card title="shared_fs" icon="document">
    A POSIX path every broker mounts (NFS, EFS, Lustre). On-prem clusters.
  </Card>
  <Card title="object_store" icon="star">
    S3 or S3-compatible, GCS or Azure Blob. Cloud clusters.
  </Card>
</CardGrid>

### Local or shared filesystem

```bash
# Local WAL only (default)
danube cluster storage local

# Shared filesystem: every broker must mount the same path
danube cluster storage shared-fs --root /mnt/shared-danube/storage
```

### Object storage

Pass the backend, a `bucket/prefix` root, and any number of `--option KEY=VALUE` pairs:

<Tabs>
<TabItem label="Amazon S3">

```bash
# IAM role or instance profile
danube cluster storage object-store \
  --backend s3 \
  --root my-danube-bucket/cluster-prod \
  --option region=us-east-1
```

```bash
# MinIO or another S3-compatible endpoint
danube cluster storage object-store \
  --backend s3 \
  --root danube-wal \
  --option endpoint=http://minio:9000 \
  --option region=us-east-1 \
  --option access_key=minioadmin \
  --option secret_key=minioadmin \
  --option virtual_host_style=false
```

S3 options: `region`, `endpoint`, `access_key`, `secret_key`, `session_token`, `anonymous`, `profile`, `role_arn`, `session_name`, `virtual_host_style`.

</TabItem>
<TabItem label="Google Cloud Storage">

```bash
danube cluster storage object-store \
  --backend gcs \
  --root my-gcs-bucket/danube \
  --option credentials_path=/etc/danube/gcs-sa.json
```

GCS options: `credentials_path` (or `credential_file`), `credentials_json`, `endpoint`.

</TabItem>
<TabItem label="Azure Blob">

```bash
danube cluster storage object-store \
  --backend azblob \
  --root my-container/danube \
  --option account_name=mystorageaccount \
  --option account_key=BASE64_ACCOUNT_KEY
```

Azure options: `account_name`, `account_key`, `endpoint`.

</TabItem>
<TabItem label="Local test store">

```bash
# Object-store code path on a local directory, for tests without cloud credentials
danube cluster storage object-store --backend filesystem --root /tmp/danube-object-store
```

</TabItem>
</Tabs>

<Aside type="caution">
While any topic is `cloud_tiered`, Danube refuses to switch back to `local` or to replace the active durable store. Add `--force` to `local`, `shared-fs` or `object-store` only when you have planned for it.
</Aside>

## Tier a topic to the durable store

Pick durability per topic with a [stream intent](/concepts/stream-intents/), then mark the topic `cloud_tiered` once the cluster has a `shared_fs` or `object_store` backend:

```bash
# Reliable topic with fsync'd batches
danube topic create /default/orders --intent audit_log

# Tier it to the durable store, live
danube topic storage-mode /default/orders --mode cloud_tiered

# Go back to local only (needs --force)
danube topic storage-mode /default/orders --mode local --force
```

Setting `cloud_tiered` fails if the cluster has no durable store yet.

## Tune the WAL

`danube cluster wal` updates rotation, flushing, cache and retention on every broker live. Flags you leave out keep their current value. Run it with no flags to print the current settings.

```bash
danube cluster wal \
  --retention-time-minutes 2880 \
  --retention-size-mb 20480 \
  --rotate-max-bytes 536870912 \
  --flush-interval-ms 5000

# Stop the background deleter from pruning old WAL files
danube cluster wal --clear-retention
```

**Retention** (default on a new cluster)

- **`--retention-time-minutes`**: maximum age of rotated WAL files. Default `2880` (48 hours).
- **`--retention-size-mb`**: size cap before the oldest files are pruned. Default `20480` (20 GiB).
- **`--check-interval-minutes`**: how often the deleter runs. Default `5`.
- **`--clear-retention`**: remove the retention limits and disable the deleter.

**Rotation**

- **`--rotate-max-bytes`**: rotate the WAL file after this many bytes. Default `536870912` (512 MiB).
- **`--rotate-max-hours`**: also rotate after this many hours. Off by default.

**Buffering**

- **`--cache-capacity`**: in-memory cache size, in entries. Default `1024`.
- **`--flush-interval-ms`**: background flush interval. Default `5000`.
- **`--flush-max-batch-bytes`**: force a flush once this much is buffered. Default `10485760` (10 MiB).

<Aside type="note">
How hard each write hits the disk is decided per topic by its intent: `event_stream` flushes to the OS page cache, `task_queue` and `audit_log` also `fdatasync` each batch. See [Crash recovery](/durability/crash-recovery/#how-hard-each-write-hits-the-disk).
</Aside>

## Add the Valkey write buffer

For near-zero loss on ephemeral disks (Kubernetes `emptyDir`, spot instances), double-write every message to Valkey before the producer is acknowledged.

```bash
# Production preset
danube cluster write-buffer enable \
  --endpoints redis://valkey-0:6379,redis://valkey-1:6379,redis://valkey-2:6379 \
  --profile ha

# Single Valkey for development
danube cluster write-buffer enable --endpoints redis://valkey:6379 --profile dev

# Turn it off again
danube cluster write-buffer disable
```

### Presets

<CardGrid>
  <Card title="ha" icon="approve-check">
    `wait_replicas: 1`, `wait_timeout_ms: 100`, `on_wait_timeout: fail`, `max_cached_closed_segments: 10`.
  </Card>
  <Card title="dev" icon="laptop">
    `wait_replicas: 0`, `wait_timeout_ms: 50`, `on_wait_timeout: ack`, `max_cached_closed_segments: 2`.
  </Card>
</CardGrid>

Override any field on its own or on top of a preset:

```bash
danube cluster write-buffer enable \
  --endpoints redis://valkey-0:6379,redis://valkey-1:6379 \
  --wait-replicas 1 \
  --wait-timeout-ms 150 \
  --on-wait-timeout fail \
  --max-cached-segments 5
```

### Write buffer flags

- **`--endpoints`** (`endpoints`): comma-separated Valkey or Redis URLs. Required.
- **`--profile`** (`profile`): `ha` or `dev`.
- **`--wait-replicas`** (`wait_replicas`): replicas that must confirm each write. Default `1`.
- **`--wait-timeout-ms`** (`wait_timeout_ms`): how long to wait for them. Default `100`.
- **`--on-wait-timeout`** (`on_wait_timeout`): `fail` rejects the write, `ack` accepts it anyway. Default `fail`.
- **`--max-cached-segments`** (`max_cached_closed_segments`): closed WAL segments kept in Valkey before `XTRIM`. Default `5`.

### Pick your values

- **wait replicas**: `0` for a single Valkey (survives a broker crash, not a Valkey crash). `1` once Valkey has a replica or runs as a cluster.
- **on wait timeout**: `fail` in production so you never lose the guarantee silently. `ack` only when availability matters more than strict durability.
- **wait timeout**: about 50 to 100 ms on the same host, 100 to 200 ms in one datacenter, 200 to 500 ms across zones.
- **cached segments**: each segment is up to `--rotate-max-bytes` (512 MiB by default), so 5 segments is roughly 2.5 GiB of Valkey memory per topic. 5 to 10 suits most clusters.

<Aside type="caution">
`--on-wait-timeout ack` acknowledges writes even if no replica confirmed them. Use it only when you mean to trade durability for availability.
</Aside>

## Declare it all in a manifest

For GitOps and CI, put storage, write buffer, namespaces and topics in one file. Always preview first:

```bash
danube apply -f desired_state.yaml --dry-run
danube apply -f desired_state.yaml
```

<Tabs>
<TabItem label="Dev: shared FS + one Valkey">

```yaml title="desired_state.yaml"
namespaces:
  - dev

shared_fs:
  root: /mnt/shared-danube/storage

write_buffer:
  enabled: true
  endpoints:
    - "redis://valkey:6379"
  profile: dev

topics:
  - name: /dev/events
    intent: event_stream
    partitions: 3
```

</TabItem>
<TabItem label="Production: S3 + Valkey HA">

```yaml title="desired_state.yaml"
namespaces:
  - production

object_store:
  backend: s3
  root: my-danube-bucket/cluster-prod
  options:
    region: us-east-1

write_buffer:
  enabled: true
  endpoints:
    - "redis://valkey-0.valkey-headless:6379"
    - "redis://valkey-1.valkey-headless:6379"
    - "redis://valkey-2.valkey-headless:6379"
  profile: ha

topics:
  - name: /production/orders
    intent: audit_log
    partitions: 6
    storage_mode: cloud_tiered
  - name: /production/telemetry
    intent: event_stream
    storage_mode: cloud_tiered
```

</TabItem>
</Tabs>

WAL tuning is not part of the manifest: use `danube cluster wal` for it.
