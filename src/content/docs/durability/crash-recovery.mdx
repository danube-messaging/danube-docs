A broker crash should cost you nothing you were not willing to lose. This page shows exactly what survives in each setup, how Danube recovers on its own, and the break-glass path for when the cluster itself is broken.

## The short version

- **Same disk comes back** (process crash, OOM kill, pod restart on the same volume): nothing is lost. The broker replays its local WAL and carries on.
- **Disk is gone** (spot instance reclaimed, diskless pod): messages that were already exported are safe. Messages that were not yet exported survive only if the Valkey write buffer is on.

The gap Valkey closes is small but real: by default a WAL file is exported when it rotates at 512 MiB, so on a busy topic that window can be minutes of data.

## How hard each write hits the disk

Each reliable topic gets a WAL sync mode from its [stream intent](/concepts/stream-intents/). It decides what has happened before the producer is acknowledged.

<CardGrid>
  <Card title="os_cache_flush" icon="rocket">
    Used by `event_stream`, and by reliable topics created without an intent. The batch is flushed to the OS page cache before the ack. Survives a broker process crash; a power loss can drop the last moments.
  </Card>
  <Card title="fsync_batch" icon="approve-check">
    Used by `task_queue` and `audit_log`. The batch is flushed and `fdatasync`'d before the ack. Survives a power loss of the host.
  </Card>
</CardGrid>

Writes are group-committed, so many concurrent messages share one flush or one `fdatasync`. The `realtime` intent has no WAL at all.

```bash
# Strongest local durability: fsync per batch, poison messages block
danube topic create /payments/ledger --intent audit_log
```

## Recovery with Valkey

When a broker takes ownership of a topic, it checks Valkey for buffered messages that the durable store does not cover yet, and replays them.

<Steps>

1. **Claim the topic**: the broker takes ownership through the metadata store.

2. **Look in Valkey**: it reads the topic's stream for offsets beyond what object storage already holds.

3. **Replay**: buffered messages are downloaded with `XRANGE` and written into a fresh local WAL.

4. **Resume**: new writes continue from the right offset. Consumers reconnect and see an unbroken offset sequence.

</Steps>

From a consumer's point of view nothing happened.

## Recovery without Valkey

The cluster relies on the WAL and the durable store only:

- **Already exported**: always recoverable.
- **Still only in the WAL**: lost if the disk is lost.

The exposure window depends on WAL rotation (`--rotate-max-bytes`, default 512 MiB, and optionally `--rotate-max-hours`) because a segment is exported once it is sealed. Lower the rotation size or add an age limit with `danube cluster wal` to shrink the window.

## Planned topic moves are different

When a topic moves between brokers on purpose (rebalancing, draining a node), no data is at risk:

<Steps>

1. **Seal**: the old owner stops accepting writes, records the last committed offset and exports the remaining WAL data.

2. **Load**: the new owner creates a fresh WAL starting at `last_committed_offset + 1`.

3. **No Valkey needed**: producers were paused during the seal and everything was exported. Valkey only matters for unplanned failures.

4. **Reconnect**: consumers resume from their cursor. History comes from the durable store, then live data from the new WAL.

</Steps>

Details: [Reliable Topic Move](/architecture/reliable-topic-move/).

## What each setup survives

- **WAL only**: survives a restart on the same disk. Loses unexported data if the disk dies.
- **WAL + object storage**: same, plus everything sealed is safe forever. Recommended on persistent volumes.
- **WAL + Valkey**: survives losing the node and its disk (replayed from Valkey). If Valkey itself fails at the same time, in-flight data is lost.
- **WAL + Valkey + object storage**: survives losing the node and its disk, with full history in object storage. Recommended on spot or diskless compute.

**RPO** (recovery point objective) is how much recent data you can lose. Valkey with `on_wait_timeout: fail` takes it close to zero.

## Break glass: recover a broken cluster

Cluster settings live in Raft. If a cluster loses quorum and you need to restart nodes with known-good settings, use a recovery file.

<Steps>

1. **Export the config while the cluster is healthy.** Do this ahead of time and keep the file somewhere safe. A recovery file needs real secrets, so add `--include-secrets`:

   ```bash
   danube cluster export-config --include-secrets --broker-id 1 --output recovery.yaml
   ```

   `--broker-id` adds that node's listen and admin addresses. Use `--format json` for JSON. Without `--include-secrets`, secrets are written as `<redacted>` and `--recovery-config` rejects the file.

2. **Edit what has to change**, for example `seed_nodes` to point at the surviving members.

3. **Start the node with the override:**

   ```bash
   danube up cluster --data-dir /var/lib/danube --recovery-config recovery.yaml
   ```

   The broker logs a warning that a break-glass override was applied.

</Steps>

A recovery file can set `seed_nodes`, `super_admins`, `auto_create_topics`, `policies`, `storage`, `load_manager`, `auth`, `broker_addr` and `admin_addr`. Fields you leave out keep their normal values. An edge node started with `--recovery-config` does not need `--cloud-endpoint`.

<Aside type="danger">
By default `export-config` replaces the JWT secret, object-store credentials and Valkey URL passwords with `<redacted>`. With `--include-secrets` the file holds the real JWT signing secret and storage credentials: it is written with `0600` permissions and a warning is printed. Treat it like a private key and store it in a secrets manager.
</Aside>
