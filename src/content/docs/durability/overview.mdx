Danube keeps brokers light: every reliable message lands in a fast local write-ahead log (WAL), and long-term safety is handed to systems built for it. You pick how much durability you need, from a single disk up to Valkey plus S3, and change it live without restarting brokers.

## Make a topic durable

Durability applies to **reliable** topics. Pick a [stream intent](/concepts/stream-intents/) and Danube sets the right WAL behaviour for you:

```bash
# Reliable topic, fsync'd in batches, 10 retries, poison messages block
danube topic create /default/orders --intent audit_log

# Tier it to the cluster's durable store (needs shared_fs or object_store mode)
danube topic storage-mode /default/orders --mode cloud_tiered
```

<Aside type="note">
Non-reliable topics (the `realtime` intent) skip the WAL entirely. Messages go straight from producers to consumers with zero disk I/O, so nothing on this page applies to them.
</Aside>

## The three storage tiers

Each tier has its own backing store and retention. They are independent: turn each one on or off as you need.

<CardGrid>
  <Card title="Hot: local WAL" icon="rocket">
    Always on for reliable topics. Every message is appended here first and gets a monotonic offset. Serves almost all reads. Kept for hours to days (default 48 hours or 20 GiB).
  </Card>
  <Card title="Warm: Valkey" icon="star">
    Optional write buffer on Redis Streams. Messages are double-written so a replacement broker can recover them if a node and its disk vanish. Keeps the last N closed segments.
  </Card>
  <Card title="Cold: object storage" icon="open-book">
    Optional S3, GCS, Azure Blob or shared filesystem. A background exporter uploads sealed WAL segments as immutable objects. Kept indefinitely and readable by any broker.
  </Card>
</CardGrid>

## Pick a combination

- **WAL only**: development, tests, edge nodes with a persistent disk.
- **WAL + object storage**: production on persistent volumes (PVCs, local NVMe). No extra services, full history in the bucket.
- **WAL + Valkey**: crash safety on ephemeral nodes when you do not need long-term history.
- **WAL + Valkey + object storage**: production on spot or diskless compute with full history.

<Aside type="tip" title="Do I need Valkey?">
On **persistent volumes**: no. The local WAL survives process crashes and pod restarts on the same volume, so WAL + object storage is enough.

On **ephemeral compute** (spot VMs, `emptyDir`): yes. Valkey holds an off-node copy of messages that were not yet exported, so losing a node loses nothing.
</Aside>

## Choose a cluster storage mode

The storage mode decides where sealed WAL segments go. It is a cluster-wide setting stored in Raft, so you change it once and every broker follows.

<CardGrid>
  <Card title="local" icon="laptop">
    Segments stay on each broker's disk. Single node, development and edge. Default.
  </Card>
  <Card title="shared_fs" icon="document">
    Segments are published to a POSIX mount every broker shares (NFS, EFS). On-prem clusters.
  </Card>
  <Card title="object_store" icon="star">
    Segments are uploaded to S3, GCS or Azure Blob. Cloud-native clusters.
  </Card>
</CardGrid>

```bash
danube cluster storage local
danube cluster storage shared-fs --root /mnt/shared-danube/storage
danube cluster storage object-store --backend s3 --root my-bucket/danube --option region=us-east-1
```

In every mode the local WAL still handles new writes and live reads. In `shared_fs` and `object_store`, a background exporter publishes sealed segments so any broker can replay history. See the [configuration guide](/durability/configuration/) for every option.

## Why Danube does it this way

Many streaming systems replicate message data between brokers, so each broker needs fast persistent disks and every scale event moves data around. Danube keeps cross-node durability out of the broker:

- **Brokers stay light**: they write a local WAL and hand history to object storage.
- **Scaling up is quick**: a new broker reads history from the durable store instead of waiting for a rebalance.
- **Scaling down is quick**: sealed segments are already in the durable store, so a broker can simply stop.
- **Fewer moving parts**: an optional Valkey instance is the only extra service, and many teams already run one.

When a topic moves between brokers, the new owner reads its history from the durable store. In `local` mode only the offset sequence carries over. The full protocol is in [Reliable Topic Move](/architecture/reliable-topic-move/).

## What each layer adds

- **WAL alone**: messages survive broker restarts as long as the disk survives.
- **Add Valkey**: near-zero loss (RPO close to 0) when a node and its disk disappear, plus fast failover by replaying buffered messages into a fresh WAL.
- **Add object storage**: unlimited retention, replay from any offset, and history that any broker can serve after a topic move.
