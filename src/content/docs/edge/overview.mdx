Danube Edge brings MQTT devices into your Danube cluster without losing messages when the network drops. One command on a gateway box accepts MQTT, writes every message to a local WAL and replicates it to the cloud cluster in the background.

```bash
danube up edge --data-dir /var/lib/danube-edge --name plant-7 \
  --cloud-endpoint https://danube.example.com:6650
```

Devices publish to `plant-7` on port `1883`. Consumers in the cloud read everything from `/plant-7/ingest`.

## When to use edge

<CardGrid>
  <Card title="Factory floors" icon="setting">
    PLCs and sensors that already speak MQTT.
  </Card>
  <Card title="Flaky links" icon="warning">

## Connect a site to your cluster

<Steps>
1. **Create the edge namespace on the cloud cluster.** The namespace has the same name as the edge node.

   ```bash
   danube namespace create plant-7 --endpoint https://danube.example.com:6650
   ```

2. **Start the edge node on the gateway.**

   ```bash
   danube up edge --data-dir /var/lib/danube-edge --name plant-7 \
     --cloud-endpoint https://danube.example.com:6650 \
     --cloud-token "$DANUBE_CLOUD_TOKEN" \
     --mqtt-listen 0.0.0.0:1883
   ```

   On start, the edge registers with the cluster, which creates the reliable topic `/plant-7/ingest`.

3. **Start a consumer in the cloud.**

   ```bash
   danube consume /plant-7/ingest -s plant-7-reader --endpoint https://danube.example.com:6650
   ```

4. **Publish from a device.**

   ```bash
   mosquitto_pub -h <gateway-ip> -p 1883 \
     -t "line-a/sensor-1/temp" \
     -m '{"temperature": 25.5}'
   ```

   The consumer receives the message within a couple of seconds.
</Steps>

### Edge flags

- **`--data-dir`** (required): local WAL, node identity and replication checkpoints.
- **`--name`** (required): unique edge name. It is also the namespace of all its topics. Env: `DANUBE_EDGE_NAME`.
- **`--cloud-endpoint`** (required): gRPC address of the cloud cluster. Env: `DANUBE_CLOUD_ENDPOINT`. Optional only when a `--recovery-config` file provides it.
- **`--cloud-token`**: JWT used to authenticate to the cloud cluster. Env: `DANUBE_CLOUD_TOKEN`.
- **`--mqtt-listen`**: MQTT address for devices (default `0.0.0.0:1883`).

The edge node also accepts the shared node flags such as `--listen` (default `127.0.0.1:6650`) and `--raft-port` (default `7650`). When you test an edge node on the same machine as a cluster node, move it to free ports, for example `--listen 127.0.0.1:6660 --raft-port 7660`.

## What arrives in the cloud

By default every MQTT topic (`#`) goes to one Danube topic, `/<name>/ingest`. Thousands of device topics stay out of the cluster metadata, and the original topic travels with each message as attributes:

- **`mqtt.topic`**: the MQTT topic the device published to, for example `line-a/sensor-1/temp`.
- **`edge.node_id`**: the edge name, for example `plant-7`.
- **MQTT 5 properties**: a content type becomes `mqtt.content_type`, a response topic becomes `mqtt.response_topic`, and each user property `k` becomes `mqtt.user.k`.

Consumers filter or route on these attributes without the devices knowing anything about Danube.

## How a message travels

<Steps>
1. **MQTT gateway.** Devices connect with MQTT 3.1.1 or 5.0. Each publish is matched against the topic mappings (first match wins) and buffered per topic.

2. **Local WAL.** Batches are written to the WAL in `--data-dir` before anything leaves the box. The WAL survives restarts.

3. **Replicator.** One background task per topic tails the WAL and sends batches to the cluster over gRPC. After each acknowledged batch it saves a checkpoint.

4. **Offline and back.** If the cluster is unreachable, messages pile up locally. The replicator retries with exponential backoff and jitter, forever, and resumes from the last checkpoint when the link returns.
</Steps>

## Split traffic into several topics

For custom routing, schema validation or batching, pass a recovery file with an `edge:` block. It replaces the default `#` mapping:

```bash
danube up edge --data-dir /var/lib/danube-edge --name plant-7 \
  --recovery-config ./edge-mappings.yaml
```

```yaml title="edge-mappings.yaml"
edge:
  edge:
    edge_name: plant-7
    cluster_url: https://danube.example.com:6650
    heartbeat_interval_ms: 30000
  replicator:
    batch_size: 100
    batch_timeout_ms: 1000
  mqtt:
    listener: "0.0.0.0:1883"
    max_payload_size: 262144
    max_connections: 10000
    ingestion:
      batch_size: 100
      batch_timeout_ms: 500
    topic_mappings:
      - mqtt_pattern: "device/+/telemetry"
        danube_topic: "/plant-7/telemetry"
        schema_subject: "telemetry-v1"
        validation_policy: "enforce"
        extract_attributes:
          device_id: "$1"
      - mqtt_pattern: "#"
        danube_topic: "/plant-7/ingest"
```

A publish to `device/sensor-42/telemetry` matches the first rule, goes to `/plant-7/telemetry` and carries `device_id=sensor-42` next to `mqtt.topic` and `edge.node_id`. A `--cloud-token` passed on the command line still wins over the file.

Mapping fields:

- **`mqtt_pattern`** (required): MQTT filter with `+` (one level, captured as `$1`, `$2`, ...) and `#` (all remaining levels, must be last).
- **`danube_topic`** (required): target topic. It must start with `/<edge_name>/`, otherwise the edge refuses to start.
- **`schema_subject`**: schema from the cluster registry, pulled at registration.
- **`validation_policy`**: `none` (default, stamp the schema id only) or `enforce` (reject payloads that fail validation before they reach the WAL).
- **`extract_attributes`**: map attribute names to captures such as `$1`.

Other settings and their defaults:

- **`edge.heartbeat_interval_ms`**: `30000`. The heartbeat also syncs schema changes from the cluster.
- **`replicator.batch_size`** / **`batch_timeout_ms`**: `100` messages / `1000` ms per replication call.
- **`mqtt.ingestion.batch_size`** / **`batch_timeout_ms`**: `100` messages / `500` ms per WAL flush.
- **`mqtt.max_payload_size`**: `262144` bytes (256 KiB).
- **`mqtt.max_connections`**: `10000`.

## Topic readiness and schema sync

A topic accepts MQTT messages only when its local WAL exists, the cluster confirmed the topic, and its schema (if any) was resolved. For a topic that is not ready, the edge withholds the QoS 1 acknowledgement, so devices retry on their own.

A payload that fails `enforce` validation is dropped. MQTT 5 devices get a PUBACK with reason code `0x99` (payload format invalid); MQTT 3.1.1 devices get a normal PUBACK so they stop retrying. Publishes that match no mapping are acknowledged and dropped.

If registration fails because the network is down, the heartbeat retries it on the next interval. When a schema changes in the cluster, the heartbeat brings the new version and the edge recompiles its validator without a restart. If a schema or topic is removed, the topic stops accepting messages.

## Edge node vs cluster node

<Tabs>
  <TabItem label="Edge node">
    - Speaks MQTT to devices.
    - Does not vote in Raft or own cluster topics.
    - Local WAL only, store and forward.
    - Replicates one way, edge to cluster.
    - Caches schemas pulled from the cluster.
  </TabItem>
  <TabItem label="Cluster node">
    - Speaks Danube gRPC to client libraries.
    - Votes in Raft and owns topics.
    - Local WAL plus optional tiered storage.
    - Replicates metadata through Raft.
    - Hosts the schema registry.
  </TabItem>
</Tabs>
