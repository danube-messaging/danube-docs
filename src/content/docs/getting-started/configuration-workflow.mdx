Danube has no broker config file. Each setting lives where it belongs: node flags on the node, cluster settings in Raft, topic behavior on the topic. You change cluster settings live, and every node picks them up.

```bash
danube up cluster --data-dir /var/lib/danube --single-node   # 1. start a node
danube cluster wal --retention-time-minutes 1440              # 2. change a cluster setting live
danube apply -f desired_state.yaml --dry-run                  # 3. preview a manifest
danube topic create /orders/events --intent event_stream      # 4. create a topic by purpose
```

## The layered model

<Steps>
1. **Start nodes with `danube up`.**

   Startup flags only cover what is local to one machine: data directory, listen addresses, TLS, node role and how the node joins the cluster.

   ```bash
   danube up cluster --data-dir /var/lib/danube \
     --wal-dir /mnt/nvme/danube-wal \
     --listen 0.0.0.0:6650 \
     --advertised-addr broker1.danube.internal:6650 \
     --seed-nodes broker1.danube.internal:7650,broker2.danube.internal:7650,broker3.danube.internal:7650 \
     --auth auto-tls
   ```

   See [Node Modes](/getting-started/broker-modes/) for every flag.

2. **Change cluster-wide settings in Raft with `danube cluster`.**

   Storage, write buffer, WAL and load manager settings are stored in the Raft log and replicated to every node. Change them once, from any machine, while the cluster runs.

3. **Describe the whole state in a manifest with `danube apply`.**

   Keep namespaces, topics and cluster settings in a YAML file in Git. `danube apply` shows the plan, then applies only what is missing.

4. **Create topics with explicit structure and an implicit intent.**

   You state what the topic looks like (name, partitions, schema). The `--intent` says what it is for and Danube picks delivery, durability, retries and dead-letter handling.

5. **Keep a break-glass copy with `export-config` and `--recovery-config`.**

   Export the live settings to a file. If Raft quorum is ever lost, start a node with that file as a local override.
</Steps>

## Change cluster settings live

All `danube cluster` commands talk to port `6650` on `127.0.0.1` by default. Use `--endpoint` or a saved [context](/getting-started/the-danube-cli/) to reach a remote cluster.

<Tabs>
  <TabItem label="Storage">
    ```bash
    # Show the active storage mode
    danube cluster storage show

    # Tier sealed segments to S3
    danube cluster storage object-store \
      --backend s3 \
      --root s3://danube-tiered-prod/segments \
      --option region=us-east-1

    # Or use a shared filesystem (NFS, EFS)
    danube cluster storage shared-fs --root /mnt/shared-danube

    # Back to local WAL only (--force if cloud-tiered topics exist)
    danube cluster storage local --force
    ```

    Backends for `object-store`: `s3`, `gcs`, `azblob` or `filesystem`. See [Tiered Storage](/durability/tiered-storage/).
  </TabItem>
  <TabItem label="Write buffer">
    ```bash
    # Enable the Valkey warm write buffer
    danube cluster write-buffer enable \
      --endpoints redis://valkey-0:6379,redis://valkey-1:6379 \
      --profile ha

    # Turn it off
    danube cluster write-buffer disable
    ```

    `--profile ha` waits for one replica (100 ms timeout, fail on timeout). Override with `--wait-replicas`, `--wait-timeout-ms`, `--on-wait-timeout fail|ack` and `--max-cached-segments`.
  </TabItem>
  <TabItem label="WAL">
    ```bash
    # No flags: print the current cluster config
    danube cluster wal

    # Keep one day or 10 GiB, rotate segments at 256 MiB
    danube cluster wal \
      --retention-time-minutes 1440 \
      --retention-size-mb 10240 \
      --rotate-max-bytes 268435456

    # Remove retention limits
    danube cluster wal --clear-retention
    ```
  </TabItem>
  <TabItem label="Load manager">
    ```bash
    # No flags: print the current cluster config
    danube cluster load-manager

    # Weighted placement with balanced automatic rebalancing
    danube cluster load-manager \
      --assignment-strategy weighted_load \
      --rebalance true \
      --profile balanced
    ```

    Strategies: `fair`, `balanced` (default) and `weighted_load`. Profiles: `conservative`, `balanced` and `aggressive`. See [Load Manager](/architecture/load-manager/).
  </TabItem>
</Tabs>

## Apply a declarative manifest

Write the state you want into one file:

```yaml title="desired_state.yaml"
namespaces:
  - agents
  - telemetry

topics:
  - name: /agents/tasks
    intent: task_queue
    partitions: 8

  - name: /agents/tool-audit
    intent: audit_log
    schema_subject: tool-invocation-v1

  - name: /telemetry/tokens
    intent: realtime
    partitions: 4

load_manager:
  assignment_strategy: weighted_load
  rebalancing:
    enabled: true
    aggressiveness: balanced
```

Preview the plan, then apply it:

```bash
danube apply -f desired_state.yaml --dry-run   # print the plan, change nothing
danube apply -f desired_state.yaml             # print the plan and apply it
```

Apply is additive. It creates missing namespaces and topics and updates the cluster blocks you list, but never deletes anything unless you ask:

```bash
danube apply -f desired_state.yaml --prune           # also delete unlisted, idle topics
danube apply -f desired_state.yaml --prune --force   # also delete unlisted topics that are in use
cat desired_state.json | danube apply -f -           # JSON works too, from stdin
```

Topics under `/system/` are never pruned.

### Manifest keys

Top level:

- **`namespaces`**: list of namespace names.
- **`topics`**: list of topics (fields below).
- **`shared_fs`**: `root`, optional `force`. Same as `danube cluster storage shared-fs`.
- **`object_store`**: `backend`, `root`, optional `options` map and `force`. Same as `danube cluster storage object-store`.
- **`write_buffer`**: `enabled`, `endpoints`, optional `profile`, `wait_replicas`, `wait_timeout_ms`, `on_wait_timeout`, `max_cached_closed_segments`.
- **`load_manager`**: `assignment_strategy`, `load_report_interval_seconds` and a `rebalancing` block (`enabled`, `aggressiveness`, `check_interval_seconds`, `max_moves_per_hour`, `cooldown_seconds`, `min_brokers_for_rebalance`, `min_topic_age_seconds`, `blacklist_topics`).

Each topic:

- **`name`** (required): full path such as `/agents/tasks`. Its namespace is created if missing.
- **`intent`**: `realtime`, `event_stream`, `task_queue` or `audit_log`.
- **`partitions`**: number of partitions. Leave it out for a non-partitioned topic.
- **`schema_subject`**: bind the topic to the latest version of a registered schema.
- **`dispatch_strategy`**: `reliable` or `non_reliable`, when you do not use an intent.
- **`storage_mode`**: `cloud_tiered` to tier the topic to the cluster object store.

<Aside type="note">
  WAL retention is not part of the manifest. Set it with `danube cluster wal`.
</Aside>

## Create topics by purpose

Structure stays explicit, behavior comes from the intent:

```bash
danube topic create /orders/events \
  --partitions 6 \
  --schema-subject order-event-v2 \
  --intent event_stream
```

<CardGrid>
  <Card title="realtime" icon="rocket">
    Non-reliable, in memory, zero disk I/O. For telemetry and token streams.
  </Card>
  <Card title="event_stream" icon="list-format">
    Reliable, WAL flushed to the OS cache. 3 retries from 500 ms with exponential backoff, then `<topic>-dlq`.
  </Card>
  <Card title="task_queue" icon="approve-check">
    Reliable, batched fsync. 5 retries from 1000 ms, then `<topic>-dlq`.
  </Card>
  <Card title="audit_log" icon="document">
    Reliable, batched fsync. 10 retries from 500 ms, then the subscription blocks on a poison message. No DLQ.
  </Card>
</CardGrid>

Move a topic to tiered storage once an object store is configured:

```bash
danube topic storage-mode /orders/events --mode cloud_tiered
```

See [Stream Intents](/concepts/stream-intents/) for the full settings and aliases.

## Keep a break-glass copy

Export the live cluster settings regularly:

```bash
danube cluster export-config --output cluster-backup.yaml
danube cluster export-config --format json --broker-id <BROKER_ID> --output broker1.json
```

`--broker-id` also records that node's listen and admin addresses. If Raft quorum is lost and you must start a node with known settings, pass the file as a local override:

```bash
danube up cluster --data-dir /var/lib/danube \
  --recovery-config ./cluster-backup.yaml
```

The recovery file can override seed nodes, super admins, storage, load manager, auth, listen addresses and (for edge nodes) the edge block.

<Aside type="caution">
  Use `--recovery-config` only for incidents. In normal operation, change settings with `danube cluster` or `danube apply` so every node stays in sync through Raft.
</Aside>
