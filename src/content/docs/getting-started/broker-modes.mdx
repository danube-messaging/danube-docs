Every Danube node starts with one command: `danube up <mode>`. Pick the mode that matches where the node runs, and Danube picks safe defaults for everything else.

```bash
danube up standalone                                   # laptop, CI, one server
danube up cluster --data-dir /var/lib/danube --single-node   # production, start small
danube up edge --data-dir /var/lib/edge --name plant-7 \
  --cloud-endpoint https://danube.example.com:6650     # factory or IoT gateway
```

There are no config files to write. Clients, the schema registry and admin commands all share port `6650`.

## Choose a mode

<CardGrid>
  <Card title="Standalone" icon="laptop">
    One node, no consensus traffic. Best for development, CI and single-box deployments. Starts with zero flags.
  </Card>
  <Card title="Cluster" icon="setting">
    Raft-replicated metadata across nodes. Best for production and high availability. Start with one node and grow later.
  </Card>
  <Card title="Edge" icon="random">
    Accepts MQTT from devices, stores messages locally and replicates them to a cloud cluster. Best for factories, gateways and IoT.
  </Card>
</CardGrid>

<Aside type="tip">
  Not sure? Use `standalone` to learn Danube and `cluster` for anything you plan to grow. A standalone node cannot be converted into a cluster node later, so pick `cluster` if you expect to add nodes.
</Aside>

## Start a standalone node

```bash
danube up standalone
```

That's it. The node listens on `127.0.0.1:6650` and keeps its data in `./danube-data`, relative to the directory you start it from.

Pass `--data-dir` to keep the data in a fixed place, and `--listen` to accept remote connections:

```bash
danube up standalone --data-dir ~/danube --listen 0.0.0.0:6650
```

## Start a cluster node

Cluster mode needs one thing standalone does not: an explicit `--data-dir`. Then tell the node how it joins, with at most one membership flag.

<Tabs>
  <TabItem label="One node (--single-node)">
    Bootstrap a brand-new cluster with a single member. You can [grow it later](#grow-from-one-to-three-nodes).

    ```bash
    danube up cluster --data-dir /var/lib/danube --single-node
    ```
  </TabItem>
  <TabItem label="Several nodes (--seed-nodes)">
    Start every node with the same list of Raft addresses (port `7650` by default). The peers find each other and the node with the lowest id bootstraps the cluster.

    ```bash
    danube up cluster --data-dir /var/lib/danube \
      --listen 0.0.0.0:6650 \
      --advertised-addr broker1:6650 \
      --seed-nodes broker1:7650,broker2:7650,broker3:7650
    ```

    Run the same command on `broker2` and `broker3`, changing only `--advertised-addr`.
  </TabItem>
  <TabItem label="Join a running cluster (--join)">
    Start the node and wait until an operator adds it with `danube cluster node add`.

    ```bash
    danube up cluster --data-dir /var/lib/danube --join \
      --admin-listen 0.0.0.0:50051
    ```

    A joining node only opens its client port after it becomes a member, so give it a separate `--admin-listen` that the add command can reach.
  </TabItem>
</Tabs>

If you pass no membership flag, a fresh data directory bootstraps a single-node cluster and prints a warning. Add `--single-node` to confirm that choice and silence the warning.

<Aside type="note">
  Raft uses port `7650` on the same IP as `--listen`. When you run several nodes on one machine, give each node its own `--listen` port and `--raft-port`.
</Aside>

## Start an edge node

An edge node needs a data directory, a unique name and the address of the cloud cluster it replicates to:

```bash
danube up edge --data-dir /var/lib/danube-edge --name plant-7 \
  --cloud-endpoint https://danube.example.com:6650 \
  --cloud-token "$DANUBE_CLOUD_TOKEN"
```

Devices publish over MQTT on `0.0.0.0:1883` (change it with `--mqtt-listen`). Every message lands on `/plant-7/ingest` in the cloud cluster. See [Danube Edge](/edge/overview/) for topic mappings and offline buffering.

## Required flags per mode

<CardGrid>
  <Card title="standalone" icon="laptop">
    Nothing. `--data-dir` is optional and defaults to `./danube-data`.
  </Card>
  <Card title="cluster" icon="setting">
    `--data-dir`, plus at most one of `--single-node`, `--seed-nodes` or `--join`.
  </Card>
  <Card title="edge" icon="random">
    `--data-dir`, `--name` and `--cloud-endpoint`. `--cloud-token` and `--mqtt-listen` are optional.
  </Card>
</CardGrid>

All modes share the same node flags:

- **`--listen`**: client and admin gRPC address (default `127.0.0.1:6650`).
- **`--admin-listen`**: serve admin gRPC on its own address instead of sharing `--listen`.
- **`--metrics-listen`**: Prometheus exporter address (off by default).
- **`--advertised-addr`**: host and port that clients and peers use to reach this node.
- **`--connect-url`**: external proxy or ingress URL handed to clients.
- **`--raft-port`**: Raft transport port (default `7650`).
- **`--wal-dir`**: put the write-ahead log on a different disk than `--data-dir`.
- **`--role`**: `broker`, `lakehouse` or `all` (default `all`). See [Danube Iceberg](/lakehouse/overview/).
- **`--auth`**: `none` (default), `tls` or `auto-tls`, with `--tls-cert`, `--tls-key`, `--ca-cert`, `--jwt-secret` and `--super-admin`. See [Security](/security/overview/).
- **`--recovery-config`**: break-glass override file, used only when Raft quorum is lost.
- **`--dry-run`**: print the resolved configuration and exit.

The most common flags also read environment variables: `DANUBE_DATA_DIR`, `DANUBE_LISTEN`, `DANUBE_ADVERTISED_ADDR`, `DANUBE_SEED_NODES`, `DANUBE_AUTH`, `DANUBE_JWT_SECRET`, `DANUBE_EDGE_NAME`, `DANUBE_CLOUD_ENDPOINT` and `DANUBE_CLOUD_TOKEN`.

## Keep your data safe

Danube refuses to do surprising things with a data directory.

- **Each directory remembers its mode.** The first start writes `danube-node.json` into the data directory. Starting the same directory with another mode is refused, so a standalone directory is never silently reused by a cluster node.
- **Reusing a directory resumes the node.** A directory that already holds Raft state always resumes its node identity and membership. `--seed-nodes` is only used on first boot; on later starts Danube prints a warning and ignores it.
- **The default directory is announced.** When standalone creates a new node in the default `./danube-data`, it warns you, because starting from another directory would create a different, empty node.

If you start a directory with the wrong mode, Danube stops with a message like this:

```text
Error: data directory /var/lib/danube was initialised by a `danube up standalone` node; refusing to start it as `cluster`.
Reusing it would mix incompatible metadata. Either run `danube up standalone --data-dir /var/lib/danube` or choose a different --data-dir.
```

## Preview a node with --dry-run

Every start prints a short summary of what the node will do. Add `--dry-run` to see it without starting anything:

```bash
danube up cluster --data-dir /var/lib/danube --dry-run
```

```text
Danube 0.16.0 | cluster node (dry run)
  data dir      /var/lib/danube  [new node]
  wal dir       /var/lib/danube/wal
  role          all
  listen        127.0.0.1:6650
  admin         127.0.0.1:6650 (shared with listen)
  advertised    http://127.0.0.1:6650
  raft port     7650
  auth          none
  membership    single-node (implicit)

  warning: no membership flag given; bootstrapping a NEW single-node cluster.
           Pass --seed-nodes to form a multi-node cluster, --join to join a running one,
           or --single-node to confirm and silence this warning.
```

The `[new node]` tag tells you whether the node is fresh or resuming. Use the dry run to check addresses before you open a firewall or write a container spec.

## Grow from one to three nodes

Start small with `--single-node` and add voters when you need high availability. This example runs all three nodes on one machine, so each one gets its own ports.

<Steps>
1. **Start the first node.**

   ```bash
   danube up cluster --data-dir ./data/node1 --single-node
   ```

2. **Start two more nodes in join mode.** Each one gets its own client port, Raft port and admin port.

   ```bash
   danube up cluster --data-dir ./data/node2 --join \
     --listen 127.0.0.1:6651 --raft-port 7651 --admin-listen 127.0.0.1:50052

   danube up cluster --data-dir ./data/node3 --join \
     --listen 127.0.0.1:6652 --raft-port 7652 --admin-listen 127.0.0.1:50053
   ```

3. **Add them to the cluster as learners.** The command asks the new node for its id and Raft address, then tells the leader to add it.

   ```bash
   danube cluster node add --node-addr http://127.0.0.1:50052
   danube cluster node add --node-addr http://127.0.0.1:50053
   ```

4. **Find each node id and promote the learners to voters.**

   ```bash
   danube cluster status --endpoint http://127.0.0.1:50052   # shows "Self Node ID"
   danube cluster node promote --node-id <NODE2_ID>
   danube cluster node promote --node-id <NODE3_ID>
   ```

5. **Check the result.** You should see three voters and one leader.

   ```bash
   danube cluster status
   danube broker list
   ```
</Steps>

To take a node out later, run `danube cluster node remove --node-id <ID>`.
