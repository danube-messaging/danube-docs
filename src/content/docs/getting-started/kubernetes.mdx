Danube fits Kubernetes naturally: a StatefulSet gives each broker a stable name and its own volume, and `danube up cluster` turns those names into a Raft cluster. No ConfigMap is needed, because every setting is a flag.

This guide uses a local [Kind](https://kind.sigs.k8s.io/) cluster. The same manifest works on EKS, GKE, AKS or any other Kubernetes.

## Prerequisites

- [kubectl](https://kubernetes.io/docs/tasks/tools/)
- A Kubernetes cluster, for example `kind create cluster`
- Optional: the [danube](https://github.com/danube-messaging/danube/releases) binary on your machine

## Deploy a three-node cluster

<Steps>
1. **Create a namespace.**

   ```bash
   kubectl create namespace danube
   ```

2. **Save the manifest below as `danube.yaml` and apply it.**

   ```bash
   kubectl apply -n danube -f danube.yaml
   ```

3. **Wait for the three pods.**

   ```bash
   kubectl get pods -n danube -w
   ```

   ```text
   NAME       READY   STATUS    AGE
   danube-0   1/1     Running   1m
   danube-1   1/1     Running   1m
   danube-2   1/1     Running   1m
   ```

4. **Check the cluster.** The image contains the `danube` CLI, so you can run it inside any pod.

   ```bash
   kubectl exec -n danube danube-0 -- danube cluster status
   kubectl exec -n danube danube-0 -- danube broker list
   ```
</Steps>

```yaml title="danube.yaml"
# Headless service: gives every pod a stable DNS name (danube-0.danube, ...)
apiVersion: v1
kind: Service
metadata:
  name: danube
spec:
  clusterIP: None
  publishNotReadyAddresses: true   # peers must find each other before they are ready
  selector:
    app: danube
  ports:
    - name: grpc
      port: 6650
    - name: raft
      port: 7650
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: danube
spec:
  serviceName: danube
  replicas: 3
  podManagementPolicy: Parallel    # start all pods together so the seeds can meet
  selector:
    matchLabels:
      app: danube
  template:
    metadata:
      labels:
        app: danube
    spec:
      containers:
        - name: danube
          image: ghcr.io/danube-messaging/danube:latest
          env:
            - name: POD_NAME
              valueFrom:
                fieldRef:
                  fieldPath: metadata.name
            - name: RUST_LOG
              value: danube_broker=info,openraft=warn
          args:
            - up
            - cluster
            - --data-dir=/danube-data
            - --listen=0.0.0.0:6650
            - --metrics-listen=0.0.0.0:9040
            - --advertised-addr=$(POD_NAME).danube:6650
            - --seed-nodes=danube-0.danube:7650,danube-1.danube:7650,danube-2.danube:7650
          ports:
            - name: grpc
              containerPort: 6650
            - name: raft
              containerPort: 7650
            - name: metrics
              containerPort: 9040
          readinessProbe:
            tcpSocket:
              port: grpc
            periodSeconds: 5
          volumeMounts:
            - name: data
              mountPath: /danube-data
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 10Gi
```

### What the flags do

- **`--data-dir=/danube-data`**: the Raft log, node identity and WAL live on the pod's own volume. A restarted pod resumes the same node.
- **`--listen=0.0.0.0:6650`**: accept client, schema registry and admin traffic from other pods.
- **`--advertised-addr=$(POD_NAME).danube:6650`**: the stable DNS name of the pod. Kubernetes expands `$(POD_NAME)`, and Danube derives the Raft address (`danube-0.danube:7650`) from it.
- **`--seed-nodes=...`**: the same list on every pod. The peers find each other and the lowest node id bootstraps the cluster. On later restarts the list is ignored and each pod resumes its membership.

<Aside type="tip">
  Add `--dry-run` to the `args` of a test pod to print the resolved configuration in its log without starting the node.
</Aside>

## Produce and consume

Clients look up which broker owns a topic and then connect to that broker's advertised address. Pod DNS names resolve inside the cluster, so the easiest test runs the CLI in a pod:

```bash title="Terminal 1: consume"
kubectl exec -it -n danube danube-0 -- danube consume /default/test -s test-sub
```

```bash title="Terminal 2: produce"
kubectl exec -n danube danube-0 -- danube produce /default/test -m "Hello from Kubernetes" --count 5
```

Applications running in the cluster connect to `http://danube-0.danube.danube.svc:6650` (or any other pod) the same way.

## Manage the cluster from your machine

Admin commands only need one broker, so a port-forward is enough:

```bash
kubectl port-forward -n danube danube-0 6650:6650
```

```bash title="In another terminal"
danube cluster status
danube apply -f desired_state.yaml --dry-run
danube apply -f desired_state.yaml
```

See [Configure Cluster & Topics](/getting-started/configuration-workflow/) for storage, WAL, load manager and manifest settings.

## Expose Danube to clients outside the cluster

External clients cannot resolve pod DNS names. Put a gRPC proxy (for example Envoy) in front of the brokers and tell every broker to hand out the proxy address:

```text
--connect-url=https://danube.example.com:443
```

Each broker keeps advertising its pod address internally. Danube clients connect to the proxy and automatically add an `x-danube-broker-url` header with the owning broker's address, so the proxy can route each call to the right pod.

<Aside type="note">
  Helm charts for Danube and an Envoy proxy live in the [danube_helm](https://github.com/danube-messaging/danube_helm) repository. Check that the chart version matches your Danube release, since older charts start brokers with a mounted config file instead of `danube up` flags.
</Aside>

## Production checklist

- **Security**: add `--auth tls` with certificates mounted from a Secret (`--tls-cert`, `--tls-key`, `--ca-cert`), or `--auth auto-tls`. See [Securing a Cluster](/security/securing-a-cluster/).
- **Tiered storage**: run `danube cluster storage object-store` after the cluster is up so sealed segments move to S3, GCS or Azure.
- **Fast disks**: mount a second volume and pass `--wal-dir` to keep the WAL on NVMe.
- **Metrics**: scrape port `9040` on each pod with Prometheus.

## Clean up

```bash
kubectl delete namespace danube   # removes the pods and their volumes
kind delete cluster
```
