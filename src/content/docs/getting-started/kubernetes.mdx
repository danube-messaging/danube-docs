Deploy a Danube messaging cluster on Kubernetes and verify it with `danube ctl`. This guide uses a local [Kind](https://kind.sigs.k8s.io/) cluster for simplicity, but the same Helm charts work on any Kubernetes cluster (EKS, GKE, AKS, etc.).

## Overview

A Danube Kubernetes deployment consists of two Helm charts:

| Chart | What it deploys |
|-------|----------------|
| **danube-envoy** | An [Envoy](https://www.envoyproxy.io/) gRPC proxy that routes client requests to the broker owning the target topic |
| **danube-core** | Danube brokers (StatefulSet running the single `danube` binary) with embedded Raft consensus |

When running behind Envoy, the proxy is installed first so brokers advertise its external **`connectUrl`** (`--connect-url`) to outside clients while keeping internal pod traffic routed via `--advertised-addr`.

<Aside type="note">
  **Envoy Proxy vs. Direct Access (`--advertised-addr`)**: Install `danube-envoy` and set `connectUrl` when clients connect from outside the cluster through a single gateway endpoint. For in-cluster clients reaching StatefulSet headless DNS directly, each broker advertises its pod DNS address via `--advertised-addr` without needing the proxy tier.
</Aside>

## Prerequisites

- [Docker](https://docs.docker.com/get-docker/)
- [Kind](https://kind.sigs.k8s.io/docs/user/quick-start/#installation) (for local testing)
- [kubectl](https://kubernetes.io/docs/tasks/tools/)
- [Helm 3.0+](https://helm.sh/docs/intro/install/)
- [danube](https://github.com/danube-messaging/danube/releases) binary (`danube ctl` CLI)

## Deploy Danube

<Steps>
1. **Create a Kubernetes cluster** (skip if you already have one)

   ```bash title="Create Kind cluster"
   kind create cluster
   kubectl cluster-info --context kind-kind
   ```

2. **Add the Danube Helm repository**

   ```bash
   helm repo add danube https://danube-messaging.github.io/danube_helm
   helm repo update
   ```

   This makes two charts available: `danube/danube-envoy` and `danube/danube-core`.

3. **Install the Envoy proxy**

   The Envoy proxy is the single entry point for external client traffic, reading the broker routing header so requests reach the pod owning each topic.

   ```bash
   kubectl create namespace danube
   helm install danube-envoy danube/danube-envoy -n danube
   ```

   Wait for the proxy pod to be ready:

   ```bash
   kubectl get pods -n danube -w
   ```

4. **Discover the proxy address**

   The proxy service is exposed as a Kubernetes [NodePort](https://kubernetes.io/docs/concepts/services-networking/service/#type-nodeport):

   ```bash title="Get proxy address"
   PROXY_PORT=$(kubectl get svc danube-envoy -n danube \
     -o jsonpath='{.spec.ports[?(@.name=="grpc")].nodePort}')
   NODE_IP=$(kubectl get nodes \
     -o jsonpath='{.items[0].status.addresses[?(@.type=="InternalIP")].address}')
   echo "Proxy address: ${NODE_IP}:${PROXY_PORT}"
   ```

   Save this address for the next step and for connecting clients.

   :::tip
   On managed Kubernetes (EKS, GKE, AKS), change the proxy service type to `LoadBalancer` in the `danube-envoy` values and use the external IP instead of NodePort.
   :::

5. **Install Danube core**

   In Danube v2, brokers boot **zero-YAML** via `danube up` flags in Helm values (no `danube_broker.yml` ConfigMap is required—pass `--recovery-config` only for break-glass overrides). Cluster policies (`storage`, `write-buffer`, `wal`, `load-manager`) and topics are configured post-deploy in Raft via `danube ctl cluster` or `danube ctl apply`.

   ```bash title="Install Danube core"
   helm install danube-core danube/danube-core -n danube \
     -f values-minimal.yaml \
     --set broker.externalAccess.connectUrl="${NODE_IP}:${PROXY_PORT}"
   ```

   :::note
   Check the [danube_helm repository](https://github.com/danube-messaging/danube_helm) for chart values such as `values-minimal.yaml` (`broker.externalAccess.connectUrl`, node roles, security `--auth-mode`, and StatefulSet persistence).
   :::

   This deploys **3 broker pods** (StatefulSet) with persistent storage and embedded Raft consensus (plus optional Prometheus monitoring if enabled in values). Wait for all pods to be ready:

   ```bash
   kubectl get pods -n danube -w
   ```

   Expected output:

   ```text title="Expected pods"
   NAME                                      READY   STATUS    AGE
   danube-core-broker-0                      1/1     Running   2m
   danube-core-broker-1                      1/1     Running   2m
   danube-core-broker-2                      1/1     Running   2m
   danube-envoy-xxxxxxxxx                    1/1     Running   5m
   ```

6. **Verify the deployment**

   Check that the brokers registered in proxy mode:

   ```bash
   kubectl logs danube-core-broker-0 -n danube | grep "broker registered"
   ```

   You should see each broker reporting its internal `--advertised-addr` pod DNS name alongside the shared `connect_url` (the Envoy proxy address).
</Steps>

## Produce and Consume Messages

Use `danube ctl` to send messages through the proxy:

```bash title="Terminal 1: Produce messages"
danube ctl produce \
  -s http://${NODE_IP}:${PROXY_PORT} \
  -t /default/test_topic \
  -m "Hello from Danube" -c 5
```

```bash title="Terminal 2: Consume messages"
danube ctl consume \
  -s http://${NODE_IP}:${PROXY_PORT} \
  -t /default/test_topic \
  --subscription test_sub
```

Now produce more messages in Terminal 1—the consumer receives them in real time.

## How Proxy Mode Works

In a multi-broker cluster, each topic is owned by a specific broker. When an external client connects:

<Steps>
1. The client connects to the **Envoy proxy** (`connectUrl` / `--connect-url`)

2. It sends a **topic lookup** request, which Envoy round-robins to any broker

3. The broker responds with the owning broker's internal `--advertised-addr` (`broker_url`)

4. On subsequent requests, the client attaches an `x-danube-broker-url` gRPC metadata header with the owning broker's internal address

5. Envoy's **Dynamic Forward Proxy** reads this header, resolves the pod DNS name, and routes the request directly to the owning broker
</Steps>

This means external clients only need a single external address regardless of how many broker pods run behind Envoy.

## Configure & Inspect Cluster State

Because Danube multiplexes Client gRPC, Schema Registry, and Admin gRPC onto port **`6650`** by default, forwarding port `6650` gives immediate access to both admin commands and `danube ctl apply`:

```bash title="Port-forward port 6650 and manage the cluster"
# Port-forward the multiplexed gRPC/Admin port of any broker
kubectl port-forward danube-core-broker-0 6650:6650 -n danube

# In another terminal (DANUBE_ADMIN_ENDPOINT defaults to http://127.0.0.1:6650)
danube ctl cluster status
danube ctl brokers list

# Provision cluster policies and intent-driven topics declaratively into Raft
danube ctl apply -f desired_state.yaml --dry-run
danube ctl apply -f desired_state.yaml
```

:::note[Dedicated Admin Port (`--admin-addr`)]
If your Helm deployment isolates Admin gRPC by setting `--admin-addr 0.0.0.0:50051`, forward `50051:50051` instead and pass `--endpoint http://127.0.0.1:50051` (or set `DANUBE_ADMIN_ENDPOINT=http://127.0.0.1:50051`).
:::

See [Configuration Workflow](/getting-started/configuration-workflow/) for managing tiered storage (`S3`/`GCS`/`Azure`), WAL policies, write buffers, and break-glass exports (`danube ctl cluster export-config`).

## Observability & Metrics

Even without Prometheus deployed, every Danube broker keeps a 1-hour in-memory telemetry ring buffer (`GetMetricsSnapshot`) and a 5,000-entry structured log ring buffer (`GetBrokerLogs`) queryable over port `6650` using `danube mcp`.

If Prometheus is enabled in your Helm release:

```bash
kubectl port-forward svc/danube-core-prometheus 9090:9090 -n danube
```

Open [http://localhost:9090](http://localhost:9090) in your browser to query Danube metrics.

## Cleanup

```bash title="Remove everything"
helm uninstall danube-core -n danube
helm uninstall danube-envoy -n danube
kubectl delete namespace danube
kind delete cluster
```

This removes all Kubernetes resources including PersistentVolumeClaims.
