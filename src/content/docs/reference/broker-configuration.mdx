Danube does not require a static per-node YAML configuration file (`danube_broker.yml`) to run. Instead, configuration is split across four clear surfaces:

1. **Per-node startup flags (`danube up`)** — process-local addresses, directories, workload role, and bootstrap security
2. **Live cluster configuration (`danube ctl cluster ...`)** — cluster-wide storage, WAL, write buffer, and load manager settings stored in Raft and hot-reconciled across all brokers
3. **Declarative desired-state manifest (`danube ctl apply`)** — GitOps YAML/JSON spec for namespaces, topics, storage, write buffer, and load manager
4. **Break-glass recovery file (`--recovery-config`)** — emergency disaster-recovery overrides (plus optional custom edge MQTT mappings), exported from live state via `danube ctl cluster export-config`

See [Configuration Workflow](/getting-started/configuration-workflow/) for how these surfaces interact in practice.

## 1. Per-Node Startup Flags (`danube up`)

Running `danube` without a subcommand defaults to `danube up`. By default, a node starts in `cluster` mode on single-port gRPC multiplexing (`127.0.0.1:6650` for both client pub/sub and admin RPCs), Raft transport port `7650`, and `./danube-data`.

### Broker & Cluster Flags

| Flag | Default | Description |
|------|---------|-------------|
| `--mode <mode>` | `cluster` | Runtime mode: `cluster`, `standalone`, or `edge` |
| `--data-dir <path>` | `./danube-data` | Base directory for Raft logs/snapshots, auto-generated `node_id`, WAL default, and auto-TLS artifacts |
| `--wal-dir <path>` | `{data_dir}/wal` | Per-node local WAL staging directory override (e.g., dedicated NVMe mount) |
| `--node-role <role>` | `all` | Workload role: `broker`, `lakehouse`, or `all`. See [Danube Iceberg](/lakehouse/overview/) |
| `--broker-addr <ip:port>` | `127.0.0.1:6650` | Bind/listen address for client gRPC (and Admin gRPC when `--admin-addr` is omitted) |
| `--admin-addr <ip:port>` | *(same as `--broker-addr`)* | Optional separate Admin gRPC listen address |
| `--advertised-addr <host:port>` | *(derived from `--broker-addr`)* | Address advertised to cluster peers and clients (e.g., Kubernetes Pod DNS / FQDN) |
| `--connect-url <url>` | *(same as `broker_url`)* | External proxy or ingress URL for clients; enables proxy routing when different from `broker_url` |
| `--raft-addr <ip:port>` | `*:7650` | Overrides the Raft inter-node transport port (`7650` by default) |
| `--seed-nodes <a,b,...>` | *(empty — single-node init)* | Comma-separated Raft peer seed addresses (`host:7650`) for multi-node discovery |
| `--join` | `false` | Join an existing Raft cluster (mutually exclusive with `--mode standalone` and `--mode edge`) |
| `--prom-exporter <ip:port>` | *(disabled)* | Optional Prometheus metrics HTTP listener address |
| `--auth-mode <mode>` | `none` | Startup authentication mode: `none`, `tls`, or `auto-tls` |
| `--tls-cert <path>` | *(none)* | Server TLS certificate PEM (required when configuring manual TLS via CLI) |
| `--tls-key <path>` | *(none)* | Server TLS private key PEM |
| `--ca-cert <path>` | *(none)* | CA certificate PEM used to verify peers and clients |
| `--jwt-secret <secret>` | *(none)* | HMAC shared secret for validating JWT bearer tokens (`issuer: danube-auth`, `expiration_time: 3600`) |
| `--super-admins <a,b,...>` | *(empty)* | Comma-separated JWT subjects granted super-admin bypass over RBAC |
| `--recovery-config <path>` | *(none)* | Local JSON/YAML `RecoveryConfig` break-glass file (also supplies custom edge `topic_mappings`) |

### Edge Mode Flags (`--mode edge`)

| Flag | Default | Description |
|------|---------|-------------|
| `--cloud-endpoint <url>` | *(required unless `--recovery-config` sets `edge`)* | Upstream Danube cluster gRPC URL (`http://` or `https://`) |
| `--edge-name <name>` | `HOSTNAME` or `edge-node` | Unique edge node identity used for `/{edge_name}/ingest` and `/edge_registry/edges/{edge_name}` |
| `--mqtt-addr <ip:port>` | `0.0.0.0:1883` | TCP listen address for the embedded MQTT broker |
| `--edge-token <token>` | *(none)* | Optional bearer token for authenticating to the upstream cluster |

:::note
`--mode edge` cannot be combined with `--join`. Node IDs in cluster mode are auto-generated on first boot and persisted under `{data_dir}/raft/`; there is no `--node-id` flag.
:::

### Environment Variables

| Variable | Component | Description |
|----------|-----------|-------------|
| `RUST_LOG` | `danube` | Tracing log filter (default: `warn,danube_broker=info,danube_raft=info,danube_persistent_storage=info,danube_client=info`) |
| `DANUBE_CLUSTER_SECRET` | `danube up --auth-mode auto-tls` | Shared secret used to derive/unseal the cluster CA key material stored in Raft `/cluster/security/ca` |
| `DANUBE_LAKEHOUSE_CONFIG` | `danube up` (`--node-role all\|lakehouse`) | Path to Lakehouse YAML config activating the embedded `LakehouseRuntime` |
| `DANUBE_ADMIN_ENDPOINT` | `danube ctl` | Target cluster gRPC endpoint (default: `http://127.0.0.1:6650`) |
| `DANUBE_ADMIN_TOKEN` / `DANUBE_ADMIN_API_KEY` | `danube ctl` | Admin JWT bearer token |
| `DANUBE_ADMIN_TLS`, `DANUBE_ADMIN_DOMAIN`, `DANUBE_ADMIN_CA`, `DANUBE_ADMIN_CERT`, `DANUBE_ADMIN_KEY` | `danube ctl` | Admin TLS/mTLS connection overrides |
| `DANUBE_TLS`, `DANUBE_CA`, `DANUBE_CERT`, `DANUBE_KEY`, `DANUBE_TOKEN` | `danube ctl produce\|consume` | Data-plane CLI client TLS and JWT flags |

### Node Data Directory Layout

<FileTree>
- danube-data/
  - raft/
    - log/ (Raft log entries, redb)
    - snapshot/ (Raft state machine snapshots)
  - wal/ (Default local WAL staging directory, or custom --wal-dir)
  - cluster_ca.secret (Generated in auto-TLS mode when DANUBE_CLUSTER_SECRET is unset)
  - bootstrap_admin.token (Initial super-admin JWT written on auto-TLS first boot)
</FileTree>

## 2. Live Cluster Configuration (`danube ctl cluster`)

Cluster-wide settings are persisted in the Raft state machine under `/cluster/config/*` and applied live across all connected brokers without restarts.

### Storage Backend (`danube ctl cluster storage`)

Controls where sealed WAL segments are exported for durable cross-broker storage (`/cluster/config/storage`):

```bash
# Inspect current effective storage configuration
danube ctl cluster storage status

# Switch to local-only WAL mode
danube ctl cluster storage local [--force]

# Switch to shared POSIX storage (NFS / EFS)
danube ctl cluster storage shared-fs --root /mnt/shared-danube/storage [--force]

# Switch to cloud or local object storage (s3 | gcs | azblob | filesystem)
danube ctl cluster storage object-store \
  --backend s3 \
  --root my-bucket/danube \
  --option region=us-east-1 \
  [--force]
```

Supported `--option KEY=VALUE` pairs by backend:

- **`s3`**: `region`, `endpoint`, `access_key`, `secret_key`, `session_token`, `anonymous`, `profile`, `role_arn`, `session_name`, `virtual_host_style`
- **`gcs`**: `project`, `endpoint`, `credential_file`, `credentials_path`, `credentials_json`
- **`azblob`**: `account_name`, `account_key`, `endpoint`
- **`filesystem`**: no extra options required (uses `--root` directory directly)

### Valkey Write Buffer (`danube ctl cluster write-buffer`)

Enables or tunes the Valkey warm write buffer (`/cluster/config/write_buffer`):

```bash
danube ctl cluster write-buffer status

danube ctl cluster write-buffer enable \
  --endpoints redis://valkey-0:6379,redis://valkey-1:6379 \
  --profile ha \
  [--wait-replicas <n>] \
  [--wait-timeout-ms <ms>] \
  [--on-wait-timeout fail|ack] \
  [--max-cached-segments <n>]

danube ctl cluster write-buffer disable
```

| Profile | `wait_replicas` | `wait_timeout_ms` | `on_wait_timeout` | `max_cached_closed_segments` |
|---|---|---|---|---|
| `ha` | `1` | `100` | `fail` | `10` |
| `dev` | `0` | `50` | `ack` | `2` |

When no `--profile` is supplied, unset fields use `WriteBufferConfig` defaults: `wait_replicas=1`, `wait_timeout_ms=100`, `on_wait_timeout=fail`, `max_cached_closed_segments=5`.

### WAL Lifecycle & Local Retention (`danube ctl cluster wal`)

Updates WAL buffering, flush batching, segment rotation, and local retention pruning (`/cluster/config/wal`):

```bash
danube ctl cluster wal \
  --retention-time-minutes 2880 \
  --retention-size-mb 20480 \
  --check-interval-minutes 5 \
  --rotate-max-bytes 536870912 \
  --rotate-max-hours 24 \
  --cache-capacity 1024 \
  --flush-interval-ms 5000 \
  --flush-max-batch-bytes 10485760

# Clear all local retention limits
danube ctl cluster wal --clear-retention
```

### Load Manager & Rebalancing (`danube ctl cluster load-manager`)

Updates topic placement strategy and automated rebalancing (`/cluster/config/load_manager`):

```bash
danube ctl cluster load-manager \
  --assignment-strategy balanced \
  --load-report-interval-seconds 30 \
  --rebalance true \
  --profile balanced \
  --check-interval-seconds 240 \
  --max-moves-per-hour 10 \
  --cooldown-seconds 60 \
  --min-brokers 2 \
  --min-topic-age-seconds 300 \
  --blacklist-topics "/system/*,/critical/*" \
  [--replace-blacklist]
```

See [Load Manager Architecture](/architecture/load-manager/) for scoring formulas and rebalancing profile defaults.

### Per-Topic Tiering & Stream Intents (`danube ctl topics`)

```bash
# Assign a stream intent preset on topic creation (realtime | event_stream | task_queue | audit_log)
danube ctl topics create /default/orders --intent audit_log

# Promote or revert an individual topic's storage tiering live
danube ctl topics storage-mode /default/events --mode cloud_tiered
danube ctl topics storage-mode /default/events --mode local --force
```

See [Stream Intents](/concepts/stream-intents/) for intent presets.

## 3. Declarative Desired-State Manifest (`danube ctl apply`)

Use `danube ctl apply` to reconcile cluster configuration, namespaces, and topics from a declarative YAML or JSON manifest (`DesiredStateManifest`):

```bash
danube ctl apply -f desired_state.yaml --dry-run
danube ctl apply -f desired_state.yaml [--prune] [--force]
```

Passing `--prune` deletes namespaces/topics absent from the manifest while automatically skipping `/system/*` internal topics.

### Full `DesiredStateManifest` Schema

```yaml title="desired_state.yaml"
namespaces:
  - production
  - analytics

# Use EITHER shared_fs OR object_store (not both)
shared_fs:
  root: /mnt/shared-danube/storage
  force: false

object_store:
  backend: s3                    # s3 | gcs | azblob | filesystem
  root: my-bucket/danube
  options:
    region: us-east-1
  force: false

write_buffer:
  enabled: true
  endpoints:
    - "redis://valkey-0:6379"
    - "redis://valkey-1:6379"
  profile: ha                    # Optional preset: ha | dev
  wait_replicas: 1               # Optional override
  wait_timeout_ms: 100           # Optional override
  on_wait_timeout: fail          # fail | ack
  max_cached_closed_segments: 10 # Optional override

load_manager:
  assignment_strategy: balanced  # fair | balanced | weighted_load
  load_report_interval_seconds: 30
  rebalancing:
    enabled: false
    aggressiveness: balanced     # conservative | balanced | aggressive
    check_interval_seconds: 300
    max_moves_per_hour: 10
    cooldown_seconds: 60
    min_brokers_for_rebalance: 2
    min_topic_age_seconds: 300
    min_topic_age_before_move_secs: 60
    topic_move_cooldown_secs: 120
    blacklist_topics:
      - "/system/*"

topics:
  - name: /production/orders
    intent: audit_log            # Optional: realtime | event_stream | task_queue | audit_log
    partitions: 6                # Optional partitioned topic count
    dispatch_strategy: reliable  # Optional: non_reliable | reliable
    schema_subject: orders-value # Optional Schema Registry subject
    storage_mode: cloud_tiered   # Optional: local | cloud_tiered
```

### Manifest Field Reference

| Top-Level Key | Type | Description |
|---|---|---|
| `namespaces` | `String[]` | Namespaces to ensure exist in the cluster |
| `topics` | `DesiredTopicSpec[]` | Desired topics (`name` required; optional `intent`, `partitions`, `dispatch_strategy`, `schema_subject`, `storage_mode`) |
| `shared_fs` | `Object` | Shared filesystem config: `{ root, force }` (mutually exclusive with `object_store`) |
| `object_store` | `Object` | Object store config: `{ backend, root, options, force }` |
| `write_buffer` | `Object` | Valkey buffer spec: `{ enabled, endpoints, profile, wait_replicas, wait_timeout_ms, on_wait_timeout, max_cached_closed_segments }` |
| `load_manager` | `Object` | Load manager config matching `LoadManagerConfig` (`assignment_strategy`, `load_report_interval_seconds`, `rebalancing.*`) |

### Edge Mode & Custom MQTT Mappings

In edge mode (`danube up --mode edge`), zero-YAML startup maps `#` -> `/{edge_name}/ingest` and stamps `mqtt.topic` and `edge.node_id` attributes on every message. When you need custom `topic_mappings`, payload validation, wildcard attribute extraction, or custom batching (`ingestion` / `replicator`), supply an `edge:` section inside `--recovery-config` (see [Danube Edge](/edge/overview/) for the complete `edge:` YAML schema and field table).

## 4. Break-Glass Recovery File (`--recovery-config`)

:::caution
`--recovery-config` is a **local disaster-recovery and emergency override mechanism** for quorum loss, admin lockout, emergency bind/storage overrides, or custom edge MQTT routing—**not** day-to-day cluster configuration. On healthy clusters, always use `danube ctl cluster ...` or `danube ctl apply`.
:::

Export a break-glass snapshot of the live cluster configuration at any time:

```bash
danube ctl cluster export-config --format yaml --output recovery.yaml
# Optional: include bind/admin addresses from a specific broker
danube ctl cluster export-config --broker-id 1 --format yaml --output recovery.yaml
```

Apply a recovery file at startup only when recovering a node or cluster:

```bash
danube up --data-dir /var/lib/danube --recovery-config ./recovery.yaml
```

### `RecoveryConfig` Schema

All fields in `RecoveryConfig` are optional; only present fields override the node's startup configuration:

```yaml title="recovery.yaml"
seed_nodes:
  - "broker-1:7650"
  - "broker-2:7650"

super_admins:
  - "break-glass-admin"

auto_create_topics: true
broker_addr: "0.0.0.0:6650"
admin_addr: "0.0.0.0:6650"

policies:
  max_producers_per_topic: 0            # 0 = unlimited
  max_subscriptions_per_topic: 0        # 0 = unlimited
  max_consumers_per_topic: 0            # 0 = unlimited
  max_consumers_per_subscription: 0     # 0 = unlimited
  max_publish_rate: 0                   # msgs/sec, 0 = unlimited
  max_subscription_dispatch_rate: 0     # msgs/sec, 0 = unlimited
  max_message_size: 10485760            # 10 MB default

storage:
  mode: object_store                    # local | shared_fs | object_store
  local_wal_root: /var/lib/danube/wal
  metadata_prefix: /danube
  durable:
    backend: s3                         # s3 | gcs | azblob (or { root: ... } for shared_fs)
    root: my-bucket/danube
    region: us-east-1
  local_retention:
    time_minutes: 2880
    size_mb: 20480
    check_interval_minutes: 5
  wal:
    cache_capacity: 1024
    file_sync:
      interval_ms: 5000
      max_batch_bytes: 10485760
    rotation:
      max_bytes: 536870912
      max_hours: 24
  write_buffer:
    backend: valkey
    endpoints:
      - "redis://valkey-0:6379"
    wait_replicas: 1
    wait_timeout_ms: 100
    on_wait_timeout: fail
    max_cached_closed_segments: 5

load_manager:
  assignment_strategy: balanced
  load_report_interval_seconds: 30
  rebalancing:
    enabled: false
    aggressiveness: balanced
    check_interval_seconds: 300
    max_moves_per_hour: 10
    cooldown_seconds: 60
    min_brokers_for_rebalance: 2
    min_topic_age_seconds: 300
    min_topic_age_before_move_secs: 60
    topic_move_cooldown_secs: 120
    blacklist_topics: []

auth:
  mode: tls                             # none | tls
  tls:
    cert_file: /etc/danube/certs/server.crt
    key_file: /etc/danube/certs/server.key
    ca_file: /etc/danube/certs/ca.crt
  jwt:
    secret_key: "<shared-hmac-secret>"
    issuer: danube-auth
    expiration_time: 3600
  super_admins:
    - "admin"

# Optional edge override (omitted by `cluster export-config`, parsed by `--recovery-config` in edge mode)
edge:
  edge:
    edge_name: edge-factory-01
    cluster_url: https://cloud:6650
    token: ""
    heartbeat_interval_ms: 30000
  replicator:
    batch_size: 100
    batch_timeout_ms: 1000
  mqtt:
    listener: "0.0.0.0:1883"
    max_payload_size: 262144
    max_connections: 10000
    ingestion:
      batch_size: 100
      batch_timeout_ms: 500
    topic_mappings:
      - mqtt_pattern: "#"
        danube_topic: "/edge-factory-01/ingest"
```

Note that `edge` has `#[serde(skip_serializing)]` on `RecoveryConfig`, so `danube ctl cluster export-config` emits only cluster/broker recovery fields and never includes `edge:`.
