With `--auth tls` or `--auth auto-tls`, every client and admin call must carry a JWT in the `authorization: Bearer <token>` header. This page shows how to get tokens to your apps and how to cut one off in seconds.

## Get a token in one command

```bash
# Ask the cluster for a 24h token for a service account (needs ManageCluster)
danube auth token issue --subject checkout-svc --ttl 24h
```

The command prints only the token, so you can capture it:

```bash
CHECKOUT_TOKEN="$(danube auth token issue --subject checkout-svc --ttl 168h)"
danube produce /payments/orders -r -m '{"id":1}' --token "$CHECKOUT_TOKEN" --endpoint https://broker1:6650 --tls-ca ./ca.pem --tls-domain broker1
```

## Who can call Danube

Each token maps to a principal. RBAC and the super-admin list match on its type and name.

<CardGrid>
  <Card title="user" icon="information">
    A human operator. The auto-generated `bootstrap-admin` is a user.
  </Card>
  <Card title="service_account" icon="setting">
    An app, connector, CI job or AI agent. The default type for new tokens.
  </Card>
</CardGrid>

Two more principals exist but never come from your tokens: brokers calling each other over mutual TLS, and the anonymous caller when `--auth none`.

### Token claims

- **`sub`** and **`principal_name`**: the identity RBAC checks. Danube sets both to `--subject`.
- **`principal_type`**: `user` or `service_account`.
- **`iss`**: issuer. `danube-auth` by default, `danube-cluster` for `auto-tls` tokens. Informational only.
- **`exp`**: expiry time. Expired tokens are rejected.

The broker checks the HMAC signature and the expiry. It caches a validated token for 30 seconds to keep hot paths fast, but the revocation list is checked on every call, cache or not.

## Set the signing secret

<Tabs>
<TabItem label="auto-tls">

Nothing to do. Danube generates `<data-dir>/tls/jwt.secret`, shares it across the cluster through Raft, and writes a 1-year `bootstrap-admin` token to `<data-dir>/bootstrap_admin.token`.

</TabItem>
<TabItem label="tls">

Pass the secret and your first super-admin on every node:

```bash
danube up standalone \
  --data-dir ./danube-data \
  --auth tls \
  --tls-cert /etc/danube/tls/server-cert.pem \
  --tls-key /etc/danube/tls/server-key.pem \
  --ca-cert /etc/danube/tls/ca-cert.pem \
  --jwt-secret "$DANUBE_JWT_SECRET" \
  --super-admin platform-admin
```

`--jwt-secret` also reads `DANUBE_JWT_SECRET`. Every node in a cluster must use the same secret.

</TabItem>
</Tabs>

## Manage tokens

`danube auth token` has two online commands that go through the cluster and two offline commands that only need the secret.

### Online: issue and revoke

Both need `ManageCluster` or a super-admin token.

```bash
# Service account token (type defaults to service_account, ttl to 24h)
danube auth token issue --subject checkout-svc --ttl 720h

# User token
danube auth token issue --subject alice --type user --ttl 8h

# Revoke every token for a subject, cluster-wide
danube auth token revoke --subject checkout-svc
```

Revoking writes the subject to Raft at `/auth/revoked/{subject}`. Every broker then rejects that subject with `Unauthenticated: Token subject has been revoked`, including tokens it had already cached. Revocation covers the subject, not one token, so tokens issued later for the same subject are rejected too: use a new subject name for the replacement.

<Aside type="caution">
Danube refuses to revoke the last active admin (an unrevoked super-admin or a principal with `ManageCluster` at cluster scope), so you cannot lock yourself out.
</Aside>

### Offline: create and validate

No broker needed. Useful before the first node starts or in air-gapped CI.

```bash
export DANUBE_JWT_SECRET="your-strong-hmac-secret"

# Create a 1-year token for your first admin
danube auth token create --subject platform-admin --type user --ttl 8760h

# Check a token and print its claims
danube auth token validate "$TOKEN" --jwt-secret "$DANUBE_JWT_SECRET"
```

- **`--subject`**: principal name. Required.
- **`--jwt-secret`**: must match the broker's secret. Also read from `DANUBE_JWT_SECRET`.
- **`--type`**: `service_account` (default) or `user`.
- **`--ttl`**: a number with `h` or `d`, for example `8h` or `30d`. A bare number means seconds. Defaults: `8760h` for `create`, `24h` for `issue`.
- **`--issuer`**: `create` only, default `danube-auth`.

## Use a token from the CLI

```bash
# Per command
danube topic list --namespace default --token "$TOKEN" --endpoint https://broker1:6650 --tls-ca ./ca.pem --tls-domain broker1

# From the environment
export DANUBE_TOKEN="$TOKEN"

# Saved in a context (stored with 0600 permissions)
danube context add prod --endpoint https://broker1:6650 --tls-ca ./ca.pem --tls-domain broker1 --token "$TOKEN" --use
```

The CLI picks a flag first, then the environment, then the current context. `--tls-domain` must match a name in the broker certificate; it defaults to `localhost`.
