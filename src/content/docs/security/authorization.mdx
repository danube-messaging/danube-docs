Once auth is on, Danube denies everything that is not explicitly granted. You group permissions into **roles**, then **bind** roles to a principal at a scope. This page shows how to give each app exactly what it needs.

## Let an app produce to one topic

<Steps>

1. **Create a role** with the permissions it needs:

   ```bash
   danube auth role create producer-role --permissions Lookup,Produce
   ```

2. **Bind it** to the app's service account on one topic:

   ```bash
   danube auth binding create checkout-orders-writer \
     --principal-type service_account \
     --principal-name checkout-svc \
     --roles producer-role \
     --scope topic \
     --resource /payments/orders
   ```

3. **Give the app a token** for that subject:

   ```bash
   danube auth token issue --subject checkout-svc --ttl 720h
   ```

</Steps>

Any call the bindings do not cover fails with `PERMISSION_DENIED`.

## How a request is checked

A call is allowed if any of these is true, in this order:

- **Auth is off** (`--auth none`): everything is allowed.
- **Broker to broker**: internal calls over mutual TLS are always allowed.
- **Super-admin**: the token's subject is listed with `--super-admin` (or is `bootstrap-admin` under `auto-tls`) and is not revoked.
- **A binding grants it**: a binding for the caller's type and name includes a role that has the permission, at the resource's scope or an enclosing one.

Scopes nest like this:

- **`cluster`**: applies everywhere.
- **`namespace`** (`--resource payments`): the namespace and every topic in it.
- **`topic`** (`--resource /payments/orders`): that topic only.

## Permissions

**Data plane**

- **`Lookup`**: find which broker serves a topic. Every producer and consumer needs it.
- **`Produce`**: create producers and publish.
- **`Consume`**: subscribe, receive, ack and nack.
- **`ReadPayload`**: read stored message bytes without consuming, for `danube topic peek`, `danube topic schema infer` and the matching MCP tools.

**Management**

- **`ManageNamespace`**: create and delete namespaces, list their topics, read their policies.
- **`ManageTopic`**: create, delete, describe, branch and unload topics, change storage mode, manage subscriptions, failure policies and DLQ replay.
- **`ManageSchema`**: register, read and delete schemas, set compatibility, attach schemas to topics.
- **`ManageBroker`**: list brokers, inspect load, unload and activate brokers.
- **`ManageCluster`**: `danube cluster status`, Raft membership, live cluster settings (`storage`, `wal`, `write-buffer`, `load-manager`), `export-config`, rebalancing, `danube apply`, roles and bindings, and `danube auth token issue|revoke`.
- **`Replicate`**: reserved for replication between brokers.

<Aside type="tip">
`ManageTopic` does not include `ReadPayload`. An operator or AI agent can create topics and debug stuck consumers without ever seeing message contents. Grant `ReadPayload` only to principals that may read data.
</Aside>

<Aside type="caution">
Schema reads are checked as `ManageSchema`, not `Consume`. Fetching a schema by ID checks `ManageSchema` at **cluster** scope. Reading the latest schema or listing versions checks `ManageSchema` on the subject. A client that resolves schemas, for example a consumer that decodes typed messages, needs a matching `ManageSchema` binding as well as its `Consume` binding.
</Aside>

## Manage roles

```bash
# Producer and consumer roles
danube auth role create producer-role --permissions Lookup,Produce
danube auth role create consumer-role --permissions Lookup,Consume

# Topic operator that cannot read payloads
danube auth role create topic-operator --permissions ManageTopic,ManageSchema

# Full admin
danube auth role create cluster-admin \
  --permissions Lookup,Produce,Consume,Replicate,ReadPayload,ManageNamespace,ManageTopic,ManageSchema,ManageBroker,ManageCluster
```

```bash
danube auth role list
danube auth role get producer-role --output json
danube auth role delete producer-role
```

## Manage bindings

A binding has an ID, a principal (`--principal-type` and `--principal-name`), one or more `--roles`, and a `--scope` with an optional `--resource`.

```bash
# Namespace scope: spark-reader may consume any topic in /analytics
danube auth binding create analytics-readers \
  --principal-type service_account \
  --principal-name spark-reader \
  --roles consumer-role \
  --scope namespace \
  --resource analytics

# Cluster scope: ops-lead is a full admin
danube auth binding create platform-ops-admin \
  --principal-type user \
  --principal-name ops-lead \
  --roles cluster-admin \
  --scope cluster
```

`list`, `get` and `delete` need the same scope and resource the binding was created with:

```bash
danube auth binding list --scope cluster
danube auth binding list --scope topic --resource /payments/orders --output json
danube auth binding get checkout-orders-writer --scope topic --resource /payments/orders
danube auth binding delete checkout-orders-writer --scope topic --resource /payments/orders
```

## You cannot lock yourself out

Danube refuses any change that would leave zero active admins. Active admins are unrevoked super-admins plus principals with a cluster-scope binding that grants `ManageCluster`.

- **`danube auth role delete`**: refused if the role is what keeps the last admin.
- **`danube auth binding delete`**: refused if it removes the last admin binding.
- **`danube auth token revoke`**: refused if it would revoke the last admin.
