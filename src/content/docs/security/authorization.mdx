When authentication is enabled (`--auth-mode tls` or `--auth-mode auto-tls`), Danube enforces **default-deny Role-Based Access Control (RBAC)** on every data-plane and control-plane RPC. If no binding grants the required permission on the target resource, the request fails with `PERMISSION_DENIED`.

---

## Evaluation Model

A request passes authorization if **any** of the following holds:

1. **Unauthenticated dev mode (`--auth-mode none`)**: All checks are bypassed.
2. **Internal broker (`Principal::BrokerInternal`)**: Inter-broker mTLS RPCs bypass user RBAC.
3. **Super-admin (`--super-admins`)**: Any unrevoked JWT subject listed in `--super-admins` (including `bootstrap-admin` under `--auth-mode auto-tls`) bypasses RBAC.
4. **Role Binding match**: The caller's `principal_type` and `principal_name` match a binding whose roles include the required `Permission`, evaluated at the target resource scope or inherited from an enclosing scope:
   * `cluster` scope (`--scope cluster`) applies cluster-wide and satisfies checks on namespaces, topics, brokers, schemas, and the cluster itself.
   * `namespace` scope (`--scope namespace --resource <ns>`) applies to the namespace and topics within it.
   * `topic` scope (`--scope topic --resource /<ns>/<topic>`) applies only to that topic.

## Permissions & Resources

Danube defines **10 permissions** across **5 resource types** (`Cluster`, `Broker`, `Namespace`, `Topic`, `SchemaSubject`):

| Permission | Scope / Resources | Operations Authorized |
| :--- | :--- | :--- |
| `Lookup` | Topic / Cluster | Service discovery (`lookup_topic`, `topic_partitions`) |
| `Produce` | Topic | Creating producers and publishing messages |
| `Consume` | Topic / Cluster | Subscribing, receiving, acknowledging messages, reading consumer offsets, and fallback broker logs/metrics |
| `Replicate` | Cluster / Topic | Replication permission for inter-broker / replicator operations |
| `ReadPayload` | Topic | Reading raw stored message bytes via `topics peek`, `topics sample`, and `topics infer-schema` (and MCP `peek_messages` / `infer_topic_schema`) |
| `ManageNamespace` | Namespace / Cluster | Creating/deleting namespaces, inspecting/setting policies, listing brokers' namespaces |
| `ManageTopic` | Topic / Cluster | Creating, deleting, describing, branching, seeking, DLQ replay, failure policies, schema association, unloading topics |
| `ManageSchema` | SchemaSubject / Cluster | Registering, reading, checking compatibility, setting compatibility mode, deleting schema versions |
| `ManageBroker` | Broker / Cluster | Listing brokers, inspecting load balance, draining (`unload`), activating brokers, telemetry/log queries |
| `ManageCluster` | Cluster | Raft membership (`add_node`, `promote_node`, `remove_node`), live cluster config (`storage`, `write-buffer`, `wal`, `load-manager`), `apply`, RBAC `roles`/`bindings` mutations, and online `tokens issue`/`revoke` |

<Aside type="note">
**Separation of control vs data payloads (`ReadPayload`)**: Granting `ManageTopic` lets an operator or agent inspect topic metadata, create topics, set failure policies, and diagnose consumer stalls without granting access to raw message payloads. Grant `ReadPayload` explicitly only to principals permitted to peek or sample topic payloads (`topics peek`, `topics infer-schema`).
</Aside>

## Managing Roles (`danube ctl security roles`)

Roles are named collections of permissions stored in Raft metadata (`/auth/roles/{name}`).

```bash
# Producer-only role
danube ctl security roles create producer-role \
  --permissions Lookup,Produce

# Consumer-only role
danube ctl security roles create consumer-role \
  --permissions Lookup,Consume

# Topic + schema operator (cannot read raw message payloads)
danube ctl security roles create topic-operator \
  --permissions ManageTopic,ManageSchema

# Auditor / schema-inference agent (metadata + payload inspection)
danube ctl security roles create payload-auditor \
  --permissions ManageTopic,ReadPayload

# Cluster admin role
danube ctl security roles create cluster-admin \
  --permissions Lookup,Produce,Consume,Replicate,ReadPayload,ManageNamespace,ManageTopic,ManageSchema,ManageBroker,ManageCluster
```

Inspect, list, or delete roles:

```bash
danube ctl security roles list --output json
danube ctl security roles get producer-role --output json
danube ctl security roles delete producer-role
```

## Managing Bindings (`danube ctl security bindings`)

Bindings attach one or more roles to a `user` or `service_account` principal at a specific `--scope`:

```bash
# 1. Topic-scoped binding: checkout-svc can only Lookup + Produce on /payments/orders
danube ctl security bindings create checkout-orders-writer \
  --principal-type service_account \
  --principal-name checkout-svc \
  --roles producer-role \
  --scope topic \
  --resource /payments/orders

# 2. Namespace-scoped binding: analytics team can Consume any topic in /analytics
danube ctl security bindings create analytics-readers \
  --principal-type service_account \
  --principal-name spark-reader \
  --roles consumer-role \
  --scope namespace \
  --resource analytics

# 3. Cluster-scoped binding: platform-ops user gets full cluster-admin role
danube ctl security bindings create platform-ops-admin \
  --principal-type user \
  --principal-name ops-lead \
  --roles cluster-admin \
  --scope cluster
```

List, inspect, or delete bindings:

```bash
danube ctl security bindings list --scope topic --resource /payments/orders --output json
danube ctl security bindings list --scope cluster --output json
danube ctl security bindings get checkout-orders-writer --scope topic --resource /payments/orders --output json
danube ctl security bindings delete checkout-orders-writer --scope topic --resource /payments/orders
```

## Last-Admin Lockout Protection

To prevent an administrator from accidentally locking everyone out of a live cluster, Danube evaluates `would_remove_last_admin` on every destructive RBAC mutation and refuses the request if it would leave **zero active cluster admins** (counting unrevoked `super_admins` plus principals with a cluster-scoped binding granting `ManageCluster`):

* `roles delete`: Refused if deleting the role would leave zero remaining active admins.
* `bindings delete`: Refused if deleting the cluster-scoped admin binding would leave zero remaining active admins.
* `tokens revoke`: Refused if revoking the subject would revoke the last active `super_admin` or cluster-admin principal.
