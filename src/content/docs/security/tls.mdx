One certificate set encrypts everything a Danube node talks over. Let Danube generate it with `--auth auto-tls`, or hand it your own files with `--auth tls`. Either way, clients also need a JWT: TLS and authentication are switched on together.

## What gets encrypted

- **Client and admin gRPC (port 6650)**: server TLS. Clients verify the broker against the CA; they do not need a client certificate.
- **Separate admin listener** (`--admin-listen`): same certificate, same TLS.
- **Raft (port 7650) and inter-broker replication**: mutual TLS. Both sides present a certificate signed by the cluster CA.

## Option 1: auto-tls

The fastest way to a secure node. Danube needs the `openssl` binary on the host to generate the files.

```bash
danube up standalone --data-dir ./danube-data --auth auto-tls
```

On first start it writes these files, all private ones with `0600` permissions:

- **`<data-dir>/tls/ca.pem`**: cluster CA certificate (ECDSA P-256, `CN=danube-cluster-ca`, valid 10 years).
- **`<data-dir>/tls/ca-key.pem`**: cluster CA private key.
- **`<data-dir>/tls/cert.pem`** and **`key.pem`**: the node certificate and key, valid 1 year, usable for server and client auth.
- **`<data-dir>/tls/jwt.secret`**: random HMAC secret used to sign and check JWTs.
- **`<data-dir>/bootstrap_admin.token`**: a 1-year JWT for the `bootstrap-admin` user, who is automatically a super-admin.

The node certificate covers `localhost`, `127.0.0.1`, the listen IP and the hosts from `--advertised-addr` and `--connect-url`. Set `--advertised-addr` to the name clients use, so the certificate matches it.

Restarts reuse the existing files, so the CA and tokens stay stable.

<Aside type="tip">
Use the bootstrap token for your first admin steps only. Create named admins with [roles and bindings](/security/authorization/), then keep the token offline for emergencies.
</Aside>

### auto-tls on a multi-node cluster

All nodes must trust the same CA, because Raft between nodes uses mutual TLS from the first connection. Once Raft is up, the cluster keeps the CA (key encrypted with AES-256-GCM) and the JWT secret in Raft at `/cluster/security/ca`, so every node also ends up with the same JWT secret.

<Steps>

1. **Share one cluster secret.** Set the same `DANUBE_CLUSTER_SECRET` on every node. It encrypts the CA key stored in Raft. Without it, each node generates its own `<data-dir>/cluster_ca.secret`.

   ```bash
   export DANUBE_CLUSTER_SECRET="replace-with-a-long-random-secret"
   ```

2. **Generate the CA once.** Start the first node with `--auth auto-tls`, or create a CA yourself, then copy `tls/ca.pem` and `tls/ca-key.pem` into `<data-dir>/tls/` on every other node before its first start. A node only generates a CA when none is present, and signs its own node certificate with the CA it finds.

3. **Start every node with `--auth auto-tls`.**

   ```bash
   danube up cluster \
     --data-dir /var/lib/danube \
     --listen 0.0.0.0:6650 \
     --advertised-addr broker1:6650 \
     --seed-nodes broker1:7650,broker2:7650,broker3:7650 \
     --auth auto-tls
   ```

4. **Use the first node's files** for clients: its `tls/ca.pem` and `bootstrap_admin.token`.

</Steps>

<Aside type="tip">
For production clusters, `--auth tls` with certificates from your own PKI is the more predictable choice: every node gets its certificate from the same place, and rotation follows your existing process.
</Aside>

## Option 2: bring your own certificates

If you run your own PKI (Vault, cert-manager, step-ca, OpenSSL), pass the files and a JWT secret:

```bash
danube up cluster \
  --data-dir /var/lib/danube \
  --listen 0.0.0.0:6650 \
  --advertised-addr broker1.internal:6650 \
  --seed-nodes broker1.internal:7650,broker2.internal:7650,broker3.internal:7650 \
  --auth tls \
  --tls-cert /etc/danube/tls/server-cert.pem \
  --tls-key /etc/danube/tls/server-key.pem \
  --ca-cert /etc/danube/tls/ca-cert.pem \
  --jwt-secret "$DANUBE_JWT_SECRET" \
  --super-admin platform-admin
```

- **`--tls-cert`**, **`--tls-key`**: the node's certificate and private key (PEM). Required with `--auth tls`.
- **`--ca-cert`**: CA used to verify peers. Required with `--auth tls`.
- **`--jwt-secret`**: HMAC secret for client tokens. Also read from `DANUBE_JWT_SECRET`. Without it, clients cannot authenticate.
- **`--super-admin`**: JWT subject that bypasses RBAC. Repeat the flag or pass a comma-separated list.

<Aside type="note">
Brokers use the same certificate for server and client roles in mutual TLS. It needs both `serverAuth` and `clientAuth` extended key usage, and its SANs must cover the node's advertised host.
</Aside>

### Make test certificates

```bash title="Test CA and broker certificate"
mkdir -p ./tls && cd ./tls

# 1. CA
openssl req -x509 -newkey rsa:4096 -days 365 -nodes \
  -keyout ca-key.pem -out ca-cert.pem -subj "/CN=danube-dev-ca"

# 2. Broker key and CSR
openssl req -newkey rsa:4096 -nodes \
  -keyout server-key.pem -out server.csr -subj "/CN=broker1"

# 3. Sign with SANs and both key usages
cat > san.ext <<EOF
subjectAltName = DNS:localhost,DNS:broker1,IP:127.0.0.1
extendedKeyUsage = serverAuth,clientAuth
EOF
openssl x509 -req -in server.csr -CA ca-cert.pem -CAkey ca-key.pem \
  -CAcreateserial -out server-cert.pem -days 365 -extfile san.ext
```

## Connect clients over TLS

<Tabs>
<TabItem label="danube CLI">

```bash
# One-off: flags
danube topic list --namespace default \
  --endpoint https://127.0.0.1:6650 \
  --tls-ca ./danube-data/tls/ca.pem \
  --token "$(cat ./danube-data/bootstrap_admin.token)"

# Every time: save a context
danube context add local-secure \
  --endpoint https://127.0.0.1:6650 \
  --tls-ca ./danube-data/tls/ca.pem \
  --token "$(cat ./danube-data/bootstrap_admin.token)" \
  --use
danube topic list --namespace default
```

An `https://` endpoint turns TLS on. The CLI checks the certificate for `localhost` by default: add `--tls-domain broker1` when you connect by another name.

</TabItem>
<TabItem label="Environment">

```bash
export DANUBE_ENDPOINT=https://127.0.0.1:6650
export DANUBE_TLS_CA=./danube-data/tls/ca.pem
export DANUBE_TOKEN="$(cat ./danube-data/bootstrap_admin.token)"

danube cluster status
```

</TabItem>
<TabItem label="Client libraries">

Use an `https://` service URL and pass the CA certificate and JWT in the client builder. Examples for every language are in [Client setup](/client-libraries/setup/).

</TabItem>
</Tabs>
