title: Securing a Cluster
description: From first boot to least-privilege service accounts. Turn on TLS, save an admin context, create roles and bindings, issue tokens, test them and revoke one.
---

import { Card, CardGrid, LinkCard, Steps, Tabs, TabItem, Aside } from '@astrojs/starlight/components';

In about ten minutes you will have an encrypted, authenticated Danube node where a checkout service can only write orders and a ledger service can only read them. Every step is a copy-pasteable command, and the last one shows how to cut off a leaked token.

<Steps>

1. ## Start a secured node

   <Tabs>
   <TabItem label="auto-tls (quickest)">

   ```bash
   danube up standalone --data-dir ./danube-data --auth auto-tls
   ```

   Danube writes a CA, a node certificate, a JWT secret and a `bootstrap-admin` token into `./danube-data`. See [TLS and certificates](/security/tls/) for the file list.

   </TabItem>
   <TabItem label="Your own certificates">

   ```bash
   # A first admin token, made offline with the same secret the broker uses
   export DANUBE_JWT_SECRET="replace-with-a-32-plus-character-random-secret"
   danube auth token create --subject platform-admin --type user --ttl 8760h > ./admin.token

   danube up standalone \
     --data-dir ./danube-data \
     --auth tls \
     --tls-cert /etc/danube/tls/server-cert.pem \
     --tls-key /etc/danube/tls/server-key.pem \
     --ca-cert /etc/danube/tls/ca-cert.pem \
     --super-admin platform-admin
   ```

   `danube up` reads the JWT secret from `DANUBE_JWT_SECRET`. In the next steps, use `/etc/danube/tls/ca-cert.pem` and `./admin.token` instead of the auto-tls files.

   </TabItem>
   <TabItem label="Three-node cluster">

   Use the same flags on every node with `danube up cluster`, plus membership:

   ```bash
   danube up cluster \
     --data-dir /var/lib/danube \
     --listen 0.0.0.0:6650 \
     --advertised-addr broker1.internal:6650 \
     --seed-nodes broker1.internal:7650,broker2.internal:7650,broker3.internal:7650 \
     --auth tls \
     --tls-cert /etc/danube/tls/server-cert.pem \
     --tls-key /etc/danube/tls/server-key.pem \
     --ca-cert /etc/danube/tls/ca-cert.pem \
     --super-admin platform-admin
   ```

   Every node needs the same `DANUBE_JWT_SECRET`. Add `--tls-domain broker1.internal` to client commands.

   </TabItem>
   </Tabs>

2. ## Save an admin context

   Store the endpoint, CA and admin token once, so you do not repeat them on every command:

   ```bash
   danube context add secure-admin \
     --endpoint https://127.0.0.1:6650 \
     --tls-ca ./danube-data/tls/ca.pem \
     --token "$(cat ./danube-data/bootstrap_admin.token)" \
     --use

   # Should print the node's status over TLS
   danube cluster status
   ```

   Contexts live in `~/.config/danube/contexts.toml` with `0600` permissions.

3. ## Create a namespace and a topic

   ```bash
   danube namespace create payments
   danube topic create /payments/orders --intent audit_log
   ```

4. ## Define least-privilege roles

   ```bash
   danube auth role create order-writer --permissions Lookup,Produce
   danube auth role create order-reader --permissions Lookup,Consume
   ```

5. ## Bind the roles to service accounts

   ```bash
   # checkout-svc may only write /payments/orders
   danube auth binding create checkout-writer \
     --principal-type service_account \
     --principal-name checkout-svc \
     --roles order-writer \
     --scope topic \
     --resource /payments/orders

   # ledger-svc may only read /payments/orders
   danube auth binding create ledger-reader \
     --principal-type service_account \
     --principal-name ledger-svc \
     --roles order-reader \
     --scope topic \
     --resource /payments/orders
   ```

6. ## Issue tokens for the services

   `issue` prints only the token, so capture it straight into a variable:

   ```bash
   CHECKOUT_TOKEN="$(danube auth token issue --subject checkout-svc --ttl 168h)"
   LEDGER_TOKEN="$(danube auth token issue --subject ledger-svc --ttl 168h)"
   ```

7. ## Check that access works, and is denied

   The connection flags below override the saved context. Start the consumer first: a new subscription starts at the end of a reliable topic.

   ```bash
   # Terminal 1, allowed: ledger-svc reads
   danube consume /payments/orders -s ledger-worker \
     --endpoint https://127.0.0.1:6650 --tls-ca ./danube-data/tls/ca.pem --token "$LEDGER_TOKEN"
   ```

   ```bash
   # Terminal 2, allowed: checkout-svc writes
   danube produce /payments/orders -m '{"order_id":"ord-1","amount":125.00}' \
     --endpoint https://127.0.0.1:6650 --tls-ca ./danube-data/tls/ca.pem --token "$CHECKOUT_TOKEN"

   # Denied with PERMISSION_DENIED: checkout-svc has no Consume
   danube consume /payments/orders -s sneaky \
     --endpoint https://127.0.0.1:6650 --tls-ca ./danube-data/tls/ca.pem --token "$CHECKOUT_TOKEN"
   ```

   Neither service can run `danube topic peek /payments/orders`: that needs `ReadPayload`.

8. ## Revoke a leaked token

   ```bash
   danube auth token revoke --subject checkout-svc
   ```

   Every broker rejects `checkout-svc` from its next request on, even with a cached token, and no restart is needed. Revocation applies to the subject, so issue the replacement under a new name such as `checkout-svc-v2` and bind it again.

</Steps>

## Before you go to production

- **Guard the secrets**: keep `DANUBE_CLUSTER_SECRET`, `DANUBE_JWT_SECRET`, `ca-key.pem` and `key.pem` in a secrets manager or `0600` files.
- **Retire the bootstrap token**: create named admins with a `cluster-admin` role, then store `bootstrap_admin.token` offline. Lockout protection keeps at least one admin alive.
- **Protect the console**: run `danube console` with `--require-auth` and `--http-token`, or behind an authenticating proxy. See [Security overview](/security/overview/#protect-the-web-console).
- **Keep recovery files safe**: `danube cluster export-config` redacts secrets by default. A break-glass file needs `--include-secrets`, which writes the JWT secret and storage credentials, so store it with `0600` permissions. See [Crash recovery](/durability/crash-recovery/#break-glass-recover-a-broken-cluster).
