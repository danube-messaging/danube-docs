import { Steps, Tabs, TabItem, Aside } from '@astrojs/starlight/components';

This guide walks through standing up an encrypted, authenticated Danube cluster with zero YAML config files, configuring your operator CLI, creating least-privilege RBAC policies, verifying denial/allow enforcement, and revoking credentials.

---

## 1. Start the Secured Cluster

Choose **`auto-tls`** for zero-config PKI with Raft-synced cluster CA and automatic `bootstrap-admin` provisioning, or **`tls`** if you supply your own certificates.

<Tabs>
  <TabItem label="Path A: Zero-Config auto-tls Cluster">
Set the same `DANUBE_CLUSTER_SECRET` across every node so joining brokers can decrypt the Raft-synced Cluster CA and mint certificates signed by it:

```bash title="Terminal 1: Seed node (broker 1)"
export DANUBE_CLUSTER_SECRET="prod-cluster-shared-secret-change-me"

danube up --mode cluster \
  --data-dir ./node1-data \
  --broker-addr 127.0.0.1:6650 \
  --raft-addr 127.0.0.1:7650 \
  --auth-mode auto-tls
```

Wait until node 1 elects itself Raft leader and prints `bootstrap_admin.token` path, then start nodes 2 and 3 pointing `--seed-nodes` at node 1:

```bash title="Terminal 2: Joining node (broker 2)"
export DANUBE_CLUSTER_SECRET="prod-cluster-shared-secret-change-me"

danube up --mode cluster \
  --data-dir ./node2-data \
  --broker-addr 127.0.0.1:6660 \
  --raft-addr 127.0.0.1:7660 \
  --prom-exporter 127.0.0.1:9050 \
  --seed-nodes 127.0.0.1:6650 \
  --auth-mode auto-tls
```

```bash title="Terminal 3: Joining node (broker 3)"
export DANUBE_CLUSTER_SECRET="prod-cluster-shared-secret-change-me"

danube up --mode cluster \
  --data-dir ./node3-data \
  --broker-addr 127.0.0.1:6670 \
  --raft-addr 127.0.0.1:7670 \
  --prom-exporter 127.0.0.1:9060 \
  --seed-nodes 127.0.0.1:6650 \
  --auth-mode auto-tls
```
  </TabItem>
  <TabItem label="Path B: Custom PKI (--auth-mode tls)">
Pass your CA, server/client cert & key, HMAC JWT secret, and bootstrap `--super-admins` directly on `danube up`:

```bash
# 1. Generate a bootstrap super-admin JWT offline first
export JWT_SECRET="replace-with-32-plus-char-random-secret"
danube ctl security tokens create \
  --subject platform-admin \
  --type user \
  --ttl 8760h \
  --secret-key "$JWT_SECRET" > ./bootstrap_admin.token

# 2. Boot each broker with --auth-mode tls
danube up --mode cluster \
  --data-dir ./node1-data \
  --broker-addr 127.0.0.1:6650 \
  --raft-addr 127.0.0.1:7650 \
  --auth-mode tls \
  --tls-cert /etc/danube/tls/server-cert.pem \
  --tls-key /etc/danube/tls/server-key.pem \
  --ca-cert /etc/danube/tls/ca-cert.pem \
  --jwt-secret "$JWT_SECRET" \
  --super-admins "platform-admin"
```
  </TabItem>
</Tabs>

## 2. Configure Your Admin CLI Environment

Point `danube ctl` at the multiplexed TLS endpoint (`6650`) using the CA certificate and bootstrap token:

```bash
# For auto-tls (seed node generated CA & bootstrap token under ./node1-data):
export DANUBE_ADMIN_ENDPOINT=https://127.0.0.1:6650
export DANUBE_ADMIN_TLS=true
export DANUBE_ADMIN_CA=./node1-data/tls/ca.pem
export DANUBE_ADMIN_DOMAIN=localhost
export DANUBE_ADMIN_TOKEN="$(cat ./node1-data/bootstrap_admin.token)"

# Verify cluster health and Raft quorum
danube ctl cluster status
danube ctl brokers list
```

## 3. Create Namespaces, Roles & Bindings

<Steps>
1. **Create an application namespace and topic**:
   ```bash
   danube ctl namespaces create payments
   danube ctl topics create /payments/orders --intent audit_log
   ```

2. **Define least-privilege RBAC roles**:
   ```bash
   # Application writer & reader roles
   danube ctl security roles create order-writer --permissions Lookup,Produce
   danube ctl security roles create order-reader --permissions Lookup,Consume

   # Operator role with topic admin + payload peek access
   danube ctl security roles create payment-ops \
     --permissions ManageTopic,ReadPayload,ManageSchema
   ```

3. **Bind principals to scoped resources**:
   ```bash
   danube ctl security bindings create checkout-writer-binding \
     --principal-type service_account \
     --principal-name checkout-svc \
     --roles order-writer \
     --scope topic \
     --resource /payments/orders

   danube ctl security bindings create ledger-reader-binding \
     --principal-type service_account \
     --principal-name ledger-svc \
     --roles order-reader \
     --scope namespace \
     --resource payments
   ```
</Steps>

## 4. Issue Service Account Tokens & Verify Enforcement

Issue dedicated short- or medium-lived tokens using the online `tokens issue` command:

```bash
danube ctl security tokens issue --subject checkout-svc --type service_account --ttl 168h
danube ctl security tokens issue --subject ledger-svc --type service_account --ttl 168h
```

Export the issued JWTs in your test shell:

```bash
export CHECKOUT_TOKEN="<checkout-svc-jwt>"
export LEDGER_TOKEN="<ledger-svc-jwt>"
```

Test both authorized and unauthorized paths using `danube ctl produce` / `consume`:

```bash
# Authorized: checkout-svc produces to /payments/orders
danube ctl produce \
  --service-addr https://127.0.0.1:6650 \
  --tls --ca ./node1-data/tls/ca.pem \
  --token "$CHECKOUT_TOKEN" \
  --topic /payments/orders \
  --message '{"order_id":"ord-1","amount":125.00}'

# Authorized: ledger-svc consumes from /payments/orders
danube ctl consume \
  --service-addr https://127.0.0.1:6650 \
  --tls --ca ./node1-data/tls/ca.pem \
  --token "$LEDGER_TOKEN" \
  --topic /payments/orders \
  --subscription ledger-worker \
  --limit 1

# Denied: checkout-svc does NOT have Consume permission
danube ctl consume \
  --service-addr https://127.0.0.1:6650 \
  --tls --ca ./node1-data/tls/ca.pem \
  --token "$CHECKOUT_TOKEN" \
  --topic /payments/orders \
  --subscription unauthorized-test
```

Similarly, a principal without `ReadPayload` cannot run `danube ctl topics peek /payments/orders`.

## 5. Rotate & Revoke Credentials

If a service token leaks or a service is retired, revoke the subject cluster-wide immediately (no broker restart needed):

```bash
danube ctl security tokens revoke --subject checkout-svc
```

Any subsequent request presenting a token for `checkout-svc` (even within the 30-second JWT validation cache window) is rejected with `Unauthenticated ("Token subject has been revoked")`.

## 6. Operational Checklist

<Aside type="tip">
Before going to production:
* Store `DANUBE_CLUSTER_SECRET` and private keys (`ca-key.pem`, `key.pem`) in a secrets manager or restricted `0600` files.
* Move day-to-day administration off `bootstrap-admin` onto named user accounts bound to cluster-admin roles, while retaining at least one active admin binding so last-admin lockout protection never blocks rotation.
* When exposing `danube ctl serve --mode ui`, protect `/ui/v1/*` and `/mcp` with `DANUBE_HTTP_TOKEN` and `DANUBE_HTTP_REQUIRE_AUTH=true`, or place it behind an authenticating reverse proxy.
</Aside>
