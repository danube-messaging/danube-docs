A stream intent is a one-word answer to "what is this topic for?". Pass it once with `--intent` and Danube picks the delivery mode, how hard it syncs to disk, how often it retries, and what it does with messages that keep failing.

## The idea in plain words

Ordering a coffee, you say "cappuccino", not "18 g of espresso, 120 ml of milk at 65 degrees". An intent works the same way. You name the workload and Danube expands it into concrete settings, stored in Raft next to the topic.

```bash
danube topic create /default/jobs --intent task_queue
danube topic describe /default/jobs
```

```text
Intent: task_queue (delivery=reliable, wal_sync=fsync_batch, max_retries=5,
        backoff_ms=1000, poison_policy=dead_letter, dlq=/default/jobs-dlq)
```

Because the expanded settings live in Raft, they do not drift: the topic keeps the same behaviour after restarts, broker moves, and upgrades, whatever client flags people use.

## Pick one of four intents

<CardGrid>
  <Card title="realtime" icon="rocket">
    Fast, in memory, zero disk I/O. Messages can be lost if nobody is listening.

    - Use it for live metrics, heartbeats, token streaming, RPC chatter.
    - Delivery: non-reliable.
    - Retries: none. No DLQ.
    - Aliases: `telemetry_firehose`, `firehose`, `telemetry`, `ephemeral`.
  </Card>
  <Card title="event_stream" icon="random">
    Reliable pub/sub with low latency.

    - Use it for event buses, agent event meshes, CDC and lakehouse feeds.
    - Delivery: reliable, WAL sync `os_cache_flush`.
    - Retries: 3, starting at 500 ms, exponential.
    - Poison: dead letter to `<topic>-dlq`.
    - Aliases: `agent_event_mesh`, `event_mesh`, `events`, `lakehouse_feed`, `lakehouse`, `custom`.
  </Card>
  <Card title="task_queue" icon="list-format">
    Durable work queue that survives power loss.

    - Use it for background jobs and agent task dispatch.
    - Delivery: reliable, WAL sync `fsync_batch`.
    - Retries: 5, starting at 1000 ms, exponential.
    - Poison: dead letter to `<topic>-dlq`.
    - Aliases: `agent_task_queue`, `tasks`, `work_queue`.
  </Card>
  <Card title="audit_log" icon="approve-check">
    Strict, ordered ledger that never skips an entry.

    - Use it for tool-call logs, compliance trails, state logs.
    - Delivery: reliable, WAL sync `fsync_batch`.
    - Retries: 10, starting at 500 ms, exponential.
    - Poison: block. No DLQ.
    - Aliases: `tool_invocation_log`, `tool_log`, `audit`, `state_log`.
  </Card>
</CardGrid>

Aliases are case-insensitive and accept `-` or `_` (`agent-task-queue` works). They are normalized to the canonical name when the topic is created. Partitions (`--partitions N`) and the schema subject (`--schema-subject`) stay separate flags.

```bash
# Same result, written with an alias
danube topic create /agents/tool-calls --intent tool_log
```

## What an intent configures

An intent writes two kinds of settings:

- **Topic settings**: delivery mode (`non_reliable` or `reliable`) and the WAL sync mode. Every broker that loads the topic reads them from Raft.
- **Subscription defaults**: retry count, base backoff, and poison policy. These are copied into each new subscription (see below).

### Disk durability (WAL sync modes)

- **`os_cache_flush`** (`event_stream`): each batch is flushed to the operating system before the producer gets its ack. Survives a broker crash or `kill -9`. Sub-millisecond latency.
- **`fsync_batch`** (`task_queue`, `audit_log`): each batch is also synced to disk (`fdatasync`) before the ack. Survives power loss and kernel panics. Writes that arrive together share one sync, so the cost is spread out.
- **`realtime`**: no WAL at all. Messages go straight from producer to connected consumers in memory.

### Poison handling

When a message has failed `max_retries` times:

- **`dead_letter`** (`event_stream`, `task_queue`): the message is copied to `<topic>-dlq` with diagnostic headers, and the subscription moves on. One bad message never stalls the queue.
- **`block`** (`audit_log`): delivery stops on that message until it is acked, the policy changes, or an operator moves the cursor. Nothing is skipped silently.

More detail on headers and replay: [Subscriptions: failure policies](/concepts/subscriptions/#handle-failing-messages).

## How intent settings reach subscriptions

<Steps>
1. **You create the topic** with `--intent`. The expanded settings are saved with the topic in Raft.

2. **A consumer opens a new subscription name** on that topic. The broker looks for a stored failure policy for that subscription and finds none.

3. **The broker builds one from the intent** and saves it for that subscription:
   - `max_redelivery_count` = intent retries (3, 5, or 10)
   - `base_redelivery_delay_ms` = intent backoff (500 or 1000)
   - `ack_timeout_ms` = 30000
   - `max_redelivery_delay_ms` = 60000
   - `backoff_strategy` = exponential
   - `poison_policy` = `dead_letter` with `dead_letter_topic` = `<topic>-dlq` when the intent has a DLQ, otherwise `block`

4. **The saved policy wins from then on.** New consumers joining the same subscription reuse it, and it is never overwritten by the intent again.
</Steps>

Topics created without an intent give new subscriptions the broker defaults: 5 retries, 30 s ack timeout, 1 s to 60 s exponential backoff, poison policy `block`.

## Override one subscription

Each subscription can have its own policy without touching the others. Check what a subscription inherited, then change it:

```bash
# What did "worker-pool" inherit? (after a consumer has subscribed)
danube topic subscription failure-policy get /default/jobs -s worker-pool

# Give this one subscription more patience
danube topic subscription failure-policy set /default/jobs \
  -s worker-pool \
  --max-redelivery-count 8 \
  --ack-timeout-ms 45000 \
  --base-redelivery-delay-ms 1000 \
  --max-redelivery-delay-ms 60000 \
  --backoff-strategy exponential \
  --poison-policy dead_letter \
  --dead-letter-topic /default/jobs-dlq
```

<Aside type="caution">
`failure-policy set` replaces the whole policy, so pass every value. `--backoff-strategy` defaults to `fixed` if you leave it out, and `dead_letter` needs `--dead-letter-topic`.
</Aside>

## Declare intents three ways

<Tabs>
  <TabItem label="CLI">
    ```bash
    danube topic create /agents/events --intent agent_event_mesh --partitions 3
    danube topic create /agents/tasks --intent task_queue --partitions 6
    danube topic create /agents/tool-audit --intent tool_invocation_log
    ```
  </TabItem>
  <TabItem label="danube apply">
    ```yaml title="desired_state.yaml"
    namespaces:
      - agents
    topics:
      - name: /agents/events
        intent: agent_event_mesh
        partitions: 3
      - name: /agents/tasks
        intent: task_queue
        partitions: 6
      - name: /agents/tool-audit
        intent: tool_invocation_log
    ```

    ```bash
    danube apply -f desired_state.yaml --dry-run
    danube apply -f desired_state.yaml
    ```
  </TabItem>
  <TabItem label="MCP">
    AI assistants connected to `danube mcp` call the `create_topic` tool:

    ```json
    { "name": "/agents/tool-audit", "intent": "audit_log", "partitions": 1 }
    ```

    and `set_subscription_failure_policy` for per-subscription overrides.
  </TabItem>
</Tabs>

<Aside type="note">
A producer follows the strategy of the topic it attaches to, so `danube produce /agents/tasks -m '{"job":1}'` works on a reliable topic without a flag. `-r/--reliable` only matters when the producer auto-creates the topic, and it is rejected on a non-reliable topic.
</Aside>
