A message is a payload of bytes plus a small envelope: where it came from, where it sits in the topic, and any labels you add. Add a schema and Danube can check every message against a shared contract before it reaches a consumer.

## The idea in plain words

Think of a parcel. The payload is what is inside the box. The envelope carries the sender, a tracking number, and optional stickers (attributes). A schema is the packing list that says what the box must contain.

```text
┌──────────────── message ─────────────────┐
│ msg_id      /default/orders @ offset 42  │  tracking number
│ producer    orders-api                   │  sender
│ attributes  source=web, priority=high    │  stickers
│ routing_key customer-42                  │  delivery hint
│ schema      orders-value v3              │  packing list
│ payload     {"id":1,"item":"book"}       │  contents
└──────────────────────────────────────────┘
```

## Send a message with attributes and a key

```bash
# Terminal 1: start a consumer first, printing JSON lines to see the envelope
danube consume /default/orders -s inspect --limit 1 -o jsonl

# Terminal 2: send one message with attributes and a key
danube produce /default/orders \
  -m '{"id":1,"item":"book"}' \
  --attr source:web,priority:high \
  --key customer-42
```

```rust title="Rust client"
let mut attrs = HashMap::new();
attrs.insert("source".to_string(), "web".to_string());

producer.send(payload, Some(attrs.clone())).await?;                  // no key
producer.send_with_key(payload2, Some(attrs), "customer-42").await?; // with key
```

## What a message contains

Every delivered message (`StreamMessage`) has these fields:

- **`payload`**: the content, as raw bytes.
- **`msg_id`**: where the message lives (see below).
- **`publish_time`**: when the producer sent it, in Unix milliseconds.
- **`producer_name`**: the producer that sent it.
- **`attributes`**: your key-value labels (string to string).
- **`routing_key`**: optional key used by [Key-Shared](/concepts/subscriptions/#key-shared) subscriptions and partition routing. If missing, the producer name is used.
- **`schema_id`** and **`schema_version`**: which schema the payload follows, if any.
- **`subscription_name`**: set by the broker on delivery, so acks go to the right subscription.
- **`request_id`**: an id for tracking the publish request.

### Message ID

The `msg_id` works like a tracking number:

- **`topic_name`**: the topic (or partition) it was written to.
- **`topic_offset`**: its position in that topic. Offsets only grow, which gives you order.
- **`producer_id`**: the producer within that topic.
- **`broker_addr`**: the broker that delivered it, so acks go back to the right place.

## Reserved attributes

Danube uses attribute keys starting with `x-` for its own features. Avoid these names for your own data.

- **Request and reply**: `x-danube-correlation-id`, `x-danube-reply-to`.
- **Task trees**: `x-danube-parent-msg-id`, `x-danube-root-msg-id` (used by `cancel_task_tree`).
- **Work hints**: `x-danube-deadline-ms` (absolute Unix ms), `x-danube-compute-cost-units`.
- **Checkpoints**: `x-danube-checkpoint-b64`, written by `report_progress`.
- **Dead-letter diagnostics**: `x-original-topic`, `x-original-subscription`, `x-original-topic-offset`, `x-original-producer-id`, `x-original-broker-addr`, `x-poison-policy`, `x-delivery-attempt`, `x-failure-reason`.
- **DLQ replay**: `x-danube-replayed-from-dlq`, `x-danube-replayed-subscription`, added by `danube topic dlq replay`.

## Look inside a topic

```bash
# Read stored messages without moving any subscription cursor
danube topic peek /default/orders --start-offset 0 --count 10

# Guess a JSON Schema from recent payloads
danube topic schema infer /default/orders --sample-size 100
```

## Add a schema

Instead of sending the full schema with each message, the producer sends a small `schema_id` and `schema_version`. The broker and consumers look up the definition in the [schema registry](/client-libraries/schema-registry/) and cache it.

<Steps>
1. **Register a schema** under a subject:

   ```bash
   danube schema register orders-value --schema-type json_schema --file ./orders.schema.json
   ```

2. **Attach it to a topic** and choose how strict the broker should be:

   ```bash
   danube topic schema configure /default/orders --subject orders-value --validation-policy enforce
   ```

3. **Publish with the schema**:

   ```bash
   danube produce /default/orders -f ./order.json --schema-subject orders-value
   ```

4. **Check the result**:

   ```bash
   danube topic schema show /default/orders
   ```
</Steps>

### Choose a validation policy

<CardGrid>
  <Card title="none" icon="information">
    No checks. Schema fields are optional. Good for development.
  </Card>
  <Card title="warn" icon="warning">
    Logs a warning when the schema id is missing or wrong, but accepts the message.
  </Card>
  <Card title="enforce" icon="approve-check">
    Rejects messages with a missing, unknown, or mismatched schema.
  </Card>
</CardGrid>

Add `--enable-payload-validation` to also check the payload itself against the schema, not only the schema id.

```bash
danube topic schema validation-policy /default/orders --policy warn --enable-payload-validation
```

## Subject rules vs topic rules

Schema settings live at two levels:

- **Subject level: how a schema may change.** The compatibility mode (`backward`, `forward`, `full`, `none`) is set per subject and applies to every topic using it. Set it with `danube schema set-compatibility orders-value --mode backward`.
- **Topic level: how strictly messages are checked.** Validation policy and payload validation are set per topic. Two topics can share a subject and still enforce it differently.
- **Producer level: which version to send.** Producers pick a version with `--schema-version` or `--schema-min-version` (or the matching client builder methods).

```text
Subject "order-events" (compatibility: backward)
  ├── /dev/order-events         validation: none
  ├── /staging/order-events     validation: warn, payload validation on
  └── /production/order-events  validation: enforce, payload validation on
```
