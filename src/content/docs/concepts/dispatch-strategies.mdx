Every topic picks one of two delivery modes. Non-reliable is a live broadcast: fast and light, but listeners who miss it miss it. Reliable is registered mail: stored first, delivered, and tracked until the consumer confirms.

## Compare the two modes

<CardGrid>
  <Card title="Non-reliable" icon="rocket">
    Messages go from producer to connected consumers in memory.

    - At most once. No disk, no acks needed, no retries.
    - Lowest latency and overhead.
    - Lost if no consumer is connected or a consumer crashes.
    - Use it for metrics, heartbeats, live token streams.
    - Intent: `realtime`.
  </Card>
  <Card title="Reliable" icon="approve-check">
    Messages are written to the topic's write-ahead log (WAL) first, then delivered and tracked per subscription.

    - At least once. Survives broker crashes and restarts.
    - Retries, failure policies, dead-letter topics, seek, replay.
    - Consumers can read history and catch up.
    - Use it for events, jobs, audit trails.
    - Intents: `event_stream`, `task_queue`, `audit_log`.
  </Card>
</CardGrid>

Both modes can run side by side in one cluster, and all four [subscription types](/concepts/subscriptions/) work with either.

## Pick a mode for a topic

<Tabs>
  <TabItem label="With an intent (recommended)">
    ```bash
    danube topic create /default/metrics --intent realtime      # non-reliable
    danube topic create /default/orders  --intent event_stream  # reliable
    ```

    The intent also sets disk sync and retry rules. See [Stream intents](/concepts/stream-intents/).
  </TabItem>
  <TabItem label="Explicit strategy">
    ```bash
    danube topic create /default/metrics --dispatch-strategy non_reliable
    danube topic create /default/orders  --dispatch-strategy reliable
    ```

    Without `--intent` or `--dispatch-strategy`, a topic is non-reliable.
  </TabItem>
  <TabItem label="Client auto-create">
    ```bash
    danube produce /default/orders -m 'hi' --reliable
    ```

    ```rust
    client.new_producer()
        .with_topic("/default/orders")
        .with_name("orders-producer")
        .with_reliable_dispatch()
        .build()?;
    ```

    The producer's choice only applies when it creates the topic. On an existing topic, the topic's strategy wins: a non-reliable producer can attach to a reliable topic, but a reliable producer on a non-reliable topic is rejected.
  </TabItem>
</Tabs>

## How non-reliable delivery works

1. The producer sends to the broker that owns the topic.
2. The broker checks the schema rules, if any.
3. Each subscription picks a consumer by its type and the message is pushed straight to it.
4. Nothing is written to disk. Acks are accepted but never cause redelivery.

## How reliable delivery works

**Write path**

1. The producer sends to the owning broker.
2. The broker appends the message to the topic's WAL, using the topic's sync mode, and gives it the next offset.
3. If the cluster write buffer (Valkey) is on, the write is mirrored there for fast recovery on another node.
4. The producer gets its ack and the message becomes available to subscriptions.
5. With shared-fs or object-store storage, finished WAL segments are uploaded in the background.

**Read path**

1. A consumer subscribes. The broker loads the subscription's cursor and failure policy.
2. The broker sends messages up to the in-flight window and waits for acks.
3. The cursor only moves past offsets that are acked without gaps, so an out-of-order ack never skips a message.
4. A consumer that reconnects or seeks back reads older data from cloud segments, Valkey, or the local WAL, then joins the live tail.

## Disk sync modes

Reliable topics choose how hard to push each batch to disk before acking the producer:

- **`os_cache_flush`**: flushed to the OS page cache. Survives a broker crash. Used by `event_stream`.
- **`fsync_batch`**: flushed and synced to disk (`fdatasync`), one sync per batch. Survives power loss. Used by `task_queue` and `audit_log`.
- **`async`**: buffered and flushed on a timer. Fastest, with a small window of unflushed data on crash.

Batch size and timing are cluster-wide WAL settings, changed live:

```bash
# Show current WAL settings
danube cluster wal

# Tune group commit and retention
danube cluster wal --flush-interval-ms 5 --flush-max-batch-bytes 1048576 \
  --retention-time-minutes 1440 --retention-size-mb 10240
```

## In-flight window

A reliable subscription keeps up to `max_unacked_messages` messages in flight (default 10), so consumers stay busy while earlier messages are still being processed.

- **Small window (1 to 5)**: tight backpressure, few redeliveries after a crash.
- **Default (10)**: a balanced choice for most workloads.
- **Large window (100 to 10,000)**: maximum throughput for batch workers.

The window can be tuned per subscription (1 to 10,000) through the admin gRPC API (`SetSubscriptionDispatchConfig`). Key-Shared adds one rule on top: one message per key in flight at a time.

## Retries and poison messages

Two things trigger a redelivery:

- **`nack`**: the consumer rejects the message, optionally with a delay and a reason.
- **Ack timeout**: no `ack`, `extend_lease`, or `report_progress` arrived within `ack_timeout_ms`.

```rust title="Rust client: nack with a reason"
consumer.nack(&message, Some(2_000), Some("db timeout".into())).await?;
```

After `max_redelivery_count` attempts, the subscription's poison policy applies: `dead_letter`, `block`, or `drop`. Inspect and change it per subscription:

```bash
danube topic subscription failure-policy get /default/orders -s payment-workers
```

Full details, DLQ headers, and replay: [Subscriptions: handle failing messages](/concepts/subscriptions/#handle-failing-messages).

<Aside type="tip">
Not sure which mode you need? If losing a message would cost money, trust, or a retry by hand, use reliable.
</Aside>
