Danube scales in two directions that work together: partitions split one busy topic into parallel lanes, and more brokers give those lanes somewhere to run. The Load Manager decides which broker owns which topic, and you can grow or shrink the cluster while it keeps serving traffic.

## The idea in plain words

Think of a supermarket. Partitions are extra checkout lanes for the same store. Brokers are the cashiers. Adding lanes helps only if there are cashiers to staff them, and the floor manager (Load Manager) moves cashiers to where the queues are longest.

```text
  /default/clicks (3 partitions)
     part-0 ─► broker 1
     part-1 ─► broker 2      add broker 4 ─► rebalance ─► part-2 ─► broker 4
     part-2 ─► broker 3
```

## Scale a topic with partitions

```bash
# One topic, 6 lanes, placed across the cluster
danube topic create /default/clicks --intent event_stream --partitions 6
```

- **Throughput**: each partition is its own internal topic (`/default/clicks-part-0` ...), so writes, disk I/O, and consumers spread over brokers.
- **Order**: messages with the same key go to the same partition and stay ordered. Without a key, messages are spread round-robin.
- **Fixed count**: choose the partition count at creation. It cannot change later, so leave some headroom.

Consumers and producers use the parent name (`/default/clicks`). See [Topics & partitions](/concepts/topics/).

## Understand the cluster

Every broker in cluster mode runs a Raft node. Raft stores the cluster's metadata (topics, owners, settings) and keeps it consistent.

- **Voters**: take part in every metadata decision. Danube keeps at most 5 voters by default, which tolerates 2 failed voters and keeps commits fast.
- **Learners**: receive the same metadata but do not vote. Brokers beyond the voter cap stay learners.
- **Both serve traffic**: voters and learners host topics and clients the same way. Voting only affects metadata, not message throughput.

How many voters can fail?

- **3 voters**: needs 2, survives 1 failure.
- **4 voters**: needs 3, survives 1 failure.
- **5 voters**: needs 3, survives 2 failures.

```bash
# Leader, term, voters, learners
danube cluster status

# Brokers, their addresses and states
danube broker list

# How evenly load is spread
danube broker balance
```

## Start a cluster

<Tabs>
  <TabItem label="Three nodes from day one">
    Start each node with the same seed list. The node with the lowest id bootstraps the cluster and the others join.

    ```bash
    # On broker1 (repeat on broker2 and broker3 with their own --advertised-addr)
    danube up cluster \
      --data-dir /var/lib/danube \
      --listen 0.0.0.0:6650 \
      --advertised-addr broker1:6650 \
      --seed-nodes broker1:7650,broker2:7650,broker3:7650
    ```
  </TabItem>
  <TabItem label="One node, grow later">
    ```bash
    danube up cluster --data-dir /var/lib/danube --single-node
    ```
  </TabItem>
</Tabs>

Restarting a node with the same `--data-dir` always resumes its existing Raft state, whatever membership flag you pass.

## Grow to more nodes

Pick one of two ways to add a broker.

<Tabs>
  <TabItem label="Automatic (seed nodes)">
    Point a fresh node at the running members. It finds the leader, asks to join, and is promoted to voter automatically while the cluster is below the voter cap.

    ```bash
    danube up cluster \
      --data-dir /var/lib/danube \
      --listen 0.0.0.0:6650 \
      --advertised-addr broker4:6650 \
      --seed-nodes broker1:7650,broker2:7650,broker3:7650
    ```
  </TabItem>
  <TabItem label="Manual (--join)">
    Start the node in waiting mode, then add it from any machine that can reach the cluster.

    <Steps>
    1. **Start the new node and let it wait**

       ```bash
       danube up cluster \
         --data-dir /var/lib/danube \
         --listen 0.0.0.0:6650 \
         --admin-listen 0.0.0.0:50051 \
         --advertised-addr broker4:6650 \
         --join
       ```

    2. **Add it as a learner.** The CLI asks the new node (on its admin port) for its id and Raft address, then tells the leader (`--endpoint`) to add it.

       ```bash
       danube cluster node add --node-addr http://broker4:50051 --endpoint http://broker1:6650
       ```

    3. **Promote it to voter (optional).** Find its id in `danube cluster status`. If the cluster already has 5 voters, the promote is refused and the node simply stays a learner.

       ```bash
       danube cluster node promote --node-id 12345678 --endpoint http://broker1:6650
       ```
    </Steps>
  </TabItem>
</Tabs>

A newly joined broker becomes **active** as soon as it sees the Raft leader, so new topics can be placed on it right away. Existing topics stay where they are until you rebalance:

```bash
danube broker rebalance --dry-run   # preview the moves
danube broker rebalance             # do it
danube broker balance               # check the result
```

<Aside type="caution">
A `--join` node needs its own `--admin-listen`. Its shared `--listen` port only opens after it becomes a member, so `danube cluster node add --node-addr` must point at the admin port.
</Aside>

## Let the Load Manager place topics

The Load Manager picks a broker for each new topic or partition, and can move topics later to even out load. Its settings live in Raft and change live.

<CardGrid>
  <Card title="fair" icon="list-format">
    Counts topics only. Simple and predictable. Good for development and tests.
  </Card>
  <Card title="balanced" icon="setting">
    The default. Scores brokers on topic load, CPU, and memory together. Good for most production clusters.
  </Card>
  <Card title="weighted_load" icon="magnifier">
    Finds the resource under the most pressure and weighs it higher. Good for spiky, mixed workloads.
  </Card>
</CardGrid>

```bash
# Show the current Load Manager settings
danube cluster load-manager

# Switch strategy and turn on automatic rebalancing
danube cluster load-manager --assignment-strategy weighted_load --rebalance true --profile balanced
```

Automatic rebalancing is off by default. When on, the profile sets how uneven the cluster must get before topics move:

- **`conservative`**: moves when load spread (coefficient of variation) is above 40%, at most 5 moves per hour.
- **`balanced`**: above 30%, at most 10 moves per hour.
- **`aggressive`**: above 20%, at most 20 moves per hour.

Override details with `--check-interval-seconds`, `--max-moves-per-hour`, `--cooldown-seconds`, `--min-brokers`, `--min-topic-age-seconds`, and `--blacklist-topics` (comma-separated patterns that never move).

More on scoring and moves: [Load Manager architecture](/architecture/load-manager/).

## Shrink the cluster

Move the work off a broker before you stop it, so clients never lose their topics.

<Steps>
1. **Preview and unload the broker.** Its topics move to other brokers and it ends up drained (no new topics).

   ```bash
   danube broker unload --broker-id 12345678 --dry-run
   danube broker unload --broker-id 12345678 --max-parallel 5
   ```

2. **Remove it from Raft membership.**

   ```bash
   danube cluster node remove --node-id 12345678
   ```

3. **Stop the process** and remove its data directory if the node is gone for good.
</Steps>

<Aside type="caution">
Remove voters one at a time and check `danube cluster status` in between. Losing more voters than the cluster can tolerate stops metadata changes.
</Aside>

Changed your mind? A drained broker can take traffic again:

```bash
danube broker activate --broker-id 12345678 --reason maintenance-done
```

Moving a single topic is also possible: `danube topic unload /default/clicks` releases it so the Load Manager places it again.
