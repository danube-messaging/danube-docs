This guide explains how Danube brokers join and leave a cluster, how Raft consensus stays fast past five nodes using active non-voting learners, and how to rebalance traffic on bare metal, Docker Compose, or Kubernetes.

---

## Node Lifecycle

Every broker embeds a Raft consensus node started via `danube up --mode cluster`. On startup, each broker inspects its local `data_dir` and seed peers to decide how to proceed:

| Scenario | How It's Detected | What Happens |
|----------|-------------------|--------------|
| **Single-node, first boot** | No `node_id` file, empty `--seed-nodes` | Auto-initializes a 1-voter Raft cluster |
| **Multi-node, first boot** | No `node_id` file, seed peers have no leader yet | Peers discover each other; lowest `node_id` bootstraps the cluster |
| **New node, existing cluster** | No `node_id` file, `--join` passed or seed peer reports `has_leader = true` | Starts Admin/gRPC and enters join mode in **drained** state |
| **Restart** | `node_id` file exists on disk | Rejoins Raft, syncs latest metadata, and resumes serving |

### Broker States

Once a broker joins the cluster, it moves through explicit lifecycle states:

```text
drained ──► active ──► drained (unload) ──► removed
```

- **Drained**: Registered in the cluster, but the Load Manager will not assign topics to it. Newly joined nodes start here.
- **Active**: Eligible for topic placement and client traffic after running `danube ctl brokers activate --broker-id <ID>`.
- **Removed**: Evicted from Raft membership via `danube ctl cluster remove-node --node-id <ID>` and safe to shut down.

## Raft Voter Cap & Non-Voting Learners

Raft commit latency degrades when too many nodes participate in every quorum round-trip. To combine strong metadata consistency with large compute scale-out, Danube enforces a configurable **`target_voter_count` (default: `5`)** stored under `/cluster/config/target_voter_count`:

- **Brokers 1–5 (Raft Voters)**: Promoted into the Raft voting set. A 5-voter quorum tolerates 2 simultaneous node failures while keeping metadata commits fast.
- **Brokers 6+ (Active Non-Voting Learners)**: Once `voters.len() >= target_voter_count`, newly joined brokers remain Raft **learners**. Learners receive live Raft log replication without casting quorum votes, and once activated (`danube ctl brokers activate --broker-id <ID>`), they serve producer/consumer topic traffic identically to voting brokers. Calling `cluster promote-node` past the voter cap is safely rejected with a precondition message so the quorum stays bounded.

## Prerequisites

- `danube` binary installed (provides `danube up`, `danube ctl`, and `danube mcp`)
- `DANUBE_ADMIN_ENDPOINT` pointing to any active broker's client/admin port (`6650` by default when `--admin-addr` is omitted)

```bash
export DANUBE_ADMIN_ENDPOINT=http://broker-1:6650
```

### Cluster Overview Commands

```bash title="Inspect cluster topology, leader, and load balance"
# Raft consensus state (leader_id, term, last_applied, voters, learners)
danube ctl cluster status

# Registered brokers with addresses, states, and roles
danube ctl brokers list

# Broker currently holding cluster leadership
danube ctl brokers leader-broker

# Load distribution and Coefficient of Variation (CV) across brokers
danube ctl brokers balance
```

## Live Load Manager & Zero-YAML Rebalancing

Instead of editing YAML config files and restarting nodes, configure placement strategy and automated rebalancing live in Raft metadata using `danube ctl cluster load-manager` (or declaratively via `danube ctl apply`):

```bash title="Configure placement strategy and automated rebalancing live"
# Switch assignment strategy (fair, balanced, or weighted_load) and enable balanced auto-rebalancing
danube ctl cluster load-manager \
  --assignment-strategy weighted_load \
  --rebalance true \
  --profile balanced \
  --check-interval-seconds 60 \
  --max-moves-per-hour 10 \
  --cooldown-seconds 300 \
  --min-brokers 2 \
  --min-topic-age-seconds 120 \
  --blacklist-topics "/system/*"
```

You can also inspect current Load Manager settings at any time by running `danube ctl cluster load-manager` with no flags, or trigger an on-demand rebalance:

```bash title="Preview or execute manual topic rebalancing"
danube ctl brokers rebalance --dry-run
danube ctl brokers rebalance --max-moves 5
```

## Scaling Up (Bare Metal / Docker Compose)

Adding a new broker follows four steps: start → add → (promote up to voter cap) → activate.

<Steps>
1. **Start the new broker in join mode**

   ```bash title="Start broker-4 with zero YAML"
   danube up --mode cluster \
     --broker-addr 0.0.0.0:6653 \
     --raft-addr 0.0.0.0:7653 \
     --data-dir ./danube-data/node-4 \
     --wal-dir /mnt/nvme-wal-4 \
     --prom-exporter 0.0.0.0:9043 \
     --join
   ```

   Because `--admin-addr` is omitted, Admin gRPC multiplexes cleanly on `--broker-addr` (`6653`). Check the broker's assigned `node_id` from startup logs or `./danube-data/node-4/node_id`.

2. **Add as a Raft learner**

   ```bash
   danube ctl cluster add-node --node-addr http://broker-4:6653
   ```

   The new node streams Raft log snapshots and entries asynchronously without affecting voting quorum.

3. **Promote to voter (when below `target_voter_count = 5`)**

   ```bash
   danube ctl cluster promote-node --node-id <NODE_ID>
   ```

   If the cluster already has 5 voters, skip promotion — the broker continues as a learner and still hosts topics once activated.

4. **Activate the broker**

   ```bash
   danube ctl brokers activate --broker-id <BROKER_ID> --reason "Scale-up"
   ```

5. **Rebalance existing topics (optional)**

   Activation makes the broker eligible for **new** topics immediately. To move existing partitions onto the new node (or let automated rebalancing handle it):

   ```bash
   danube ctl brokers rebalance --dry-run
   danube ctl brokers rebalance
   ```
</Steps>

## Scaling Down (Bare Metal / Docker Compose)

Removing a node follows the reverse sequence: unload → remove → stop.

:::caution
Always unload topics and remove the node from Raft membership **before** stopping the process so voter quorum is preserved cleanly.
:::

### Understanding Quorum (Up to `target_voter_count = 5`)

| Voter Count | Quorum Needed | Simultaneous Voter Losses Tolerated |
|:-----------:|:-------------:|:-----------------------------------:|
| 3 | 2 | 1 |
| 4 | 3 | 1 |
| 5 | 3 | 2 |

<Steps>
1. **Unload all topics off the broker**

   ```bash
   # Preview topic migrations
   danube ctl brokers unload --broker-id <BROKER_ID> --dry-run

   # Execute topic migration (transitions broker to drained)
   danube ctl brokers unload --broker-id <BROKER_ID>
   ```

2. **Remove the node from Raft membership**

   ```bash
   danube ctl cluster remove-node --node-id <NODE_ID>
   ```

3. **Stop the broker process**

   ```bash
   kill $(cat broker.pid)
   ```
</Steps>

### Rejoining After Wipe or Maintenance

If a removed node is brought back with stale Raft state, clear its metadata directory first (or mount a clean PVC), start it with `danube up --mode cluster ... --join`, and repeat `cluster add-node` → (`cluster promote-node` if under cap) → `brokers activate`.

## Scaling on Kubernetes (Helm)

When running on Kubernetes, pods run as a StatefulSet with headless DNS discovery.

### Scaling Up

<Steps>
1. **Increase replica count**

   ```bash
   helm upgrade danube-core ./charts/danube-core -n danube \
     --set broker.replicaCount=5
   ```

   New pods detect `has_leader = true` via seed discovery and enter join mode automatically.

2. **Add, promote (up to 5 voters), and activate each new broker**

   ```bash title="Port-forward port 6650 and register new pods"
   kubectl port-forward danube-core-broker-0 6650:6650 -n danube

   # Add pod to Raft, promote if within voter cap, and activate for topic traffic:
   danube ctl cluster add-node \
     --node-addr http://danube-core-broker-3.danube-core-broker-headless.danube.svc.cluster.local:6650
   danube ctl cluster promote-node --node-id <NODE_ID>
   danube ctl brokers activate --broker-id <BROKER_ID>
   ```

3. **Rebalance (optional)**

   ```bash
   danube ctl brokers rebalance
   ```
</Steps>

### Scaling Down

<Steps>
1. **Unload topics and remove from Raft** via `danube ctl brokers unload --broker-id <BROKER_ID>` and `danube ctl cluster remove-node --node-id <NODE_ID>`.

2. **Reduce replica count**

   ```bash
   helm upgrade danube-core ./charts/danube-core -n danube \
     --set broker.replicaCount=3
   ```

3. **Clean up orphaned PVCs**

   ```bash
   kubectl delete pvc data-danube-core-broker-3 -n danube
   kubectl delete pvc data-danube-core-broker-4 -n danube
   ```
</Steps>

### Pod Restarts and Rolling Upgrades

Normal pod restarts preserve `node_id` on the PersistentVolumeClaim, so pods rejoin Raft and resume serving automatically without manual `add-node` calls.

## Command Reference

| Command | Purpose |
|---------|---------|
| `danube ctl cluster status` | Show Raft leader, term, `last_applied`, voters, and learners |
| `danube ctl cluster add-node --node-addr URL` | Register a joining broker as a Raft learner |
| `danube ctl cluster promote-node --node-id ID` | Promote a learner to voter (respecting `target_voter_count = 5`) |
| `danube ctl cluster remove-node --node-id ID` | Remove a broker from Raft membership |
| `danube ctl cluster load-manager ...` | Configure placement strategy and automated rebalancing live |
| `danube ctl brokers list` | List all registered brokers, states, and addresses |
| `danube ctl brokers leader-broker` | Show the current cluster leader broker |
| `danube ctl brokers activate --broker-id ID` | Transition broker to active (eligible for topic placement) |
| `danube ctl brokers unload --broker-id ID [--dry-run]` | Migrate all topics off a broker |
| `danube ctl brokers balance` | Report cluster load distribution and CV metric |
| `danube ctl brokers rebalance [--dry-run] [--max-moves N]` | Preview or trigger manual topic rebalancing |

See [Broker Configuration Reference](/reference/broker-configuration/) and [CLI: Cluster Operations](/admin/cli-cluster/) for full flag details.
