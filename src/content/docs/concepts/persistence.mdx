Reliable topics keep every message on disk so consumers can replay history, recover after a crash, and follow a topic when it moves to another broker. Non-reliable topics skip storage entirely. This page shows where data lives and how to change it without restarting anything.

## The idea in plain words

Think of a desk, a filing cabinet, and an archive room. New messages land on the desk (fast local disk). Optionally a copy goes into a shared cabinet that other brokers can reach quickly (Valkey). Finished stacks are boxed and sent to the archive (shared filesystem or object storage), where they stay cheap and safe.

```text
producer ─► [ Hot: local WAL ] ──mirror──► [ Warm: Valkey ]       (optional)
                    │
                    └── sealed segments ──► [ Cold: shared FS / S3 / GCS / Azure ]  (optional)

reader   ◄── cold ──► warm ──► hot ──► live tail   (stitched by offset, no gaps)
```

## Three storage tiers

<CardGrid>
  <Card title="Hot: local WAL" icon="rocket">
    Every reliable message is appended to the topic's write-ahead log on the broker's disk and gets the next offset. Always on.

    - Put it on a fast disk with `--wal-dir`.
  </Card>
  <Card title="Warm: Valkey" icon="star">
    Optional. Writes are mirrored to Valkey so another broker can recover recent data fast after a crash.

    - `danube cluster write-buffer enable|disable`
  </Card>
  <Card title="Cold: segment storage" icon="open-book">
    Optional. Sealed WAL segments are uploaded in the background to a shared filesystem or object store for long history and replay.

    - `danube cluster storage shared-fs|object-store`
  </Card>
</CardGrid>

## Place the WAL on a fast disk

The WAL location is a per-node startup flag. Everything else is cluster-wide and lives in Raft.

```bash
# Keep Raft state in /var/lib/danube and the WAL on NVMe
danube up cluster --data-dir /var/lib/danube --wal-dir /mnt/nvme-wal --single-node
```

## Choose cluster storage

<Tabs>
  <TabItem label="Local only">
    The WAL is the only copy. Good for development, single nodes, and edge.

    ```bash
    danube cluster storage local
    ```
  </TabItem>
  <TabItem label="Shared filesystem">
    A POSIX filesystem every broker can mount (NFS, EFS). Good for on-prem clusters.

    ```bash
    danube cluster storage shared-fs --root /mnt/danube-segments
    ```
  </TabItem>
  <TabItem label="Object store">
    S3, GCS, Azure Blob (`azblob`), or a plain `filesystem` backend. Good for cloud clusters.

    ```bash
    danube cluster storage object-store \
      --backend s3 \
      --root s3://danube-archive/prod \
      --option region=us-east-1
    ```
  </TabItem>
</Tabs>

```bash
# See what is active right now
danube cluster storage show
```

<Aside type="caution">
Replacing an active shared-fs or object-store backend while topics are tiered to it is refused unless you pass `--force`.
</Aside>

## Add the Valkey write buffer

```bash
# Turn on mirroring with the high-availability preset
danube cluster write-buffer enable --endpoints valkey://valkey-1:6379 --profile ha

# Turn it off again
danube cluster write-buffer disable
```

- **`--profile ha|dev`**: preset for replica waits and timeouts.
- **`--wait-replicas`**, **`--wait-timeout-ms`**, **`--on-wait-timeout fail|ack`**: fine-tune how long a write waits for Valkey replicas.

## Tune WAL retention and batching

```bash
# Show the current cluster config
danube cluster wal

# Keep one day or 10 GiB, rotate segments at 64 MiB, batch writes every 5 ms
danube cluster wal \
  --retention-time-minutes 1440 \
  --retention-size-mb 10240 \
  --rotate-max-bytes 67108864 \
  --flush-interval-ms 5 \
  --flush-max-batch-bytes 1048576
```

You can also declare storage, write buffer, and other cluster settings in a file and apply them with `danube apply -f desired_state.yaml`.

## Per-topic overrides

**Storage mode.** A topic can opt in or out of cold storage on its own:

```bash
# Tier this topic to cloud segments (needs shared-fs or object-store)
danube topic storage-mode /default/orders --mode cloud_tiered

# Keep a scratch topic on local WAL only
danube topic storage-mode /default/scratch --mode local --force
```

**Disk sync.** Each reliable topic has a WAL sync mode set by its [stream intent](/concepts/stream-intents/):

- **`os_cache_flush`** (`event_stream`): flushed to the OS before the ack. Survives a broker crash.
- **`fsync_batch`** (`task_queue`, `audit_log`): synced to disk before the ack. Survives power loss.
- **`async`**: flushed on a timer. Fastest, small loss window. (`realtime` topics are non-reliable and skip the WAL.)

## How writes and reads flow

**Writing**

1. The broker appends the message to the local WAL with the topic's sync mode and assigns the next offset.
2. If Valkey is on, the write is mirrored there.
3. The message enters the in-memory cache for live consumers.
4. With cold storage, sealed segments are uploaded in the background.

Offsets are assigned before upload and before delivery, so a message keeps the same identity forever.

**Reading**

- **Live consumers** read straight from the in-memory tail.
- **Catching up or rewound consumers** read cold segments, then Valkey, then the local WAL, then join the live tail. Each tier covers a different offset range, so nothing is read twice or skipped.

## Branch a topic

`danube topic branch` makes an independent copy of a topic up to an offset or a point in time. Use it to replay history into a test, try a new consumer, or debug without touching production.

```bash
# Copy everything up to and including offset 5000
danube topic branch /default/orders /default/orders-exp --at-offset 5000

# Or up to a publish time (nanoseconds since the Unix epoch)
danube topic branch /default/orders /default/orders-exp --at-timestamp-ns 1763150400000000000
```

Segments already in cold storage are shared by reference (copy-on-write), not copied byte for byte. Only the recent tail still in the local WAL is copied. After that, both topics change independently.

## What happens when a topic moves

When the Load Manager or an operator moves a topic to another broker:

1. The old owner seals the topic and records the last committed offset.
2. The new owner reads the topic's intent and storage mode from Raft and continues at the next offset.

Consumers keep their positions. Details: [Reliable topic move](/architecture/reliable-topic-move/).
