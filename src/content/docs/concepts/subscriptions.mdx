A subscription is a named reader on a topic. It remembers how far it has read and decides how messages are split between the consumers attached to it. Pick the right type and you get queues, fan-out, or per-key ordering from the same topic.

## The idea in plain words

Picture a mail room. The topic is the stream of letters. Each subscription is a department with its own copy of every letter, and its own rule for handing letters to the people (consumers) in that department.

```text
                      ┌─► subscription "billing"   (exclusive)  ─► 1 consumer gets all
  /default/orders  ───┼─► subscription "workers"   (shared)     ─► letters split between 3 consumers
                      └─► subscription "per-user"  (key-shared) ─► same customer always to same consumer
```

- **Different subscription names**: each one gets every message (fan-out).
- **Same subscription name**: the consumers share that subscription's messages, using its type.

## Try it in two terminals

```bash
# Terminal 1 and 2: two workers in the same shared subscription
danube consume /default/orders -s workers -t shared

# Terminal 3: send 10 messages, watch them split between the workers
danube produce /default/orders -m 'order' --count 10 --interval 100
```

Add a consumer with `-s audit` before producing and it receives all 10 messages as well, because it is a different subscription.

<Aside type="note">
A new subscription starts at the end of the topic, so start consumers before you produce. `danube produce` follows the existing topic's dispatch strategy, so reliable topics need no extra flag.
</Aside>

## Choose a subscription type

<CardGrid>
  <Card title="Exclusive" icon="document">
    One consumer only. A second consumer with the same subscription name is rejected.

    - Strict order.
    - Use it for sequential workflows and single readers.
    - CLI: `-t exclusive`
  </Card>
  <Card title="Shared" icon="random">
    Many consumers, round-robin. Each message goes to exactly one of them.

    - Scales out, no ordering guarantee.
    - Use it for worker pools and task queues.
    - CLI: `-t shared` (the CLI default)
  </Card>
  <Card title="Fail-over" icon="approve-check">
    Many consumers, one active. If it disconnects, the next one takes over.

    - Strict order plus a hot standby.
    - Use it for critical single-reader services.
    - CLI: `-t fail-over`
  </Card>
  <Card title="Key-Shared" icon="puzzle">
    Many consumers, routed by message key. The same key always goes to the same consumer.

    - Order per key, parallel across keys.
    - Use it for per-order, per-user, or per-device processing.
    - CLI: `-t key-shared`
  </Card>
</CardGrid>

On a partitioned topic, every partition has its own copy of the subscription. A fail-over subscription therefore has one active consumer per partition, and partitions fail over independently.

```rust title="Rust client: pick the type"
let mut consumer = client
    .new_consumer()
    .with_topic("/default/orders")
    .with_consumer_name("worker-1")
    .with_subscription("workers")
    .with_subscription_type(SubType::Shared) // Exclusive, Shared, FailOver, KeyShared
    .build()?;
```

## Key-Shared

Key-Shared gives you the parallelism of Shared with per-key ordering.

- **Routing**: consumers sit on a hash ring. The message's routing key decides which consumer owns it.
- **Ordering**: at most one message per key is in flight. The next message for that key waits until the current one is acked. Other keys keep flowing.
- **Elasticity**: when a consumer joins or leaves, only about 1/N of the keys move.
- **No key**: messages sent without a key use the producer name as their key.

```bash
# Terminal 1: key-shared consumer, optionally only some keys
danube consume /default/orders -s per-customer -t key-shared --key-filter 'customer-*'

# Terminal 2: tag messages with a key
danube produce /default/orders -m '{"item":"book"}' --key customer-42
```

### Filter keys

A consumer can ask for only some keys with glob patterns (repeat the flag for several):

- **`payment`**: exactly `payment`.
- **`ship*`**: `shipping`, `shipment`, and so on.
- **`eu-west-?`**: `eu-west-1`, `eu-west-2`, and so on.
- **`*`** or no filter: every key.

If a message's key matches no consumer's filters, that subscription skips it.

```rust title="Rust client: key filters"
let mut consumer = client
    .new_consumer()
    .with_topic("/default/orders")
    .with_consumer_name("payments-worker")
    .with_subscription("orders-sub")
    .with_subscription_type(SubType::KeyShared)
    .with_key_filter("payment")
    .with_key_filter("invoice")
    .build()?;
```

See [Key-Shared in the client guide](/client-libraries/key-shared/) for a full example.

## Build common patterns

- **Work queue**: one Shared subscription, many consumers with the same subscription name. Each job is processed once.
- **Fan-out**: one subscription per downstream service (`billing`, `analytics`, `monitoring`). Each service sees every event.
- **Per-entity processing**: one Key-Shared subscription keyed by order id, user id, or device id.

## Handle failing messages

On reliable topics, a consumer must `ack` each message. If it calls `nack`, or does not ack within the ack timeout, the broker redelivers with a growing delay. After too many attempts the message is "poison", and the subscription's poison policy decides what happens.

```text
deliver ─► nack / timeout ─► wait (backoff) ─► redeliver ... ─► max retries reached ─► poison policy
```

### Failure policy fields

Every subscription on a reliable topic has its own failure policy:

- **`max_redelivery_count`**: redeliveries before the poison policy applies.
- **`ack_timeout_ms`**: how long a consumer may hold a message before it is redelivered.
- **`base_redelivery_delay_ms`**: first retry delay.
- **`max_redelivery_delay_ms`**: cap on the retry delay.
- **`backoff_strategy`**: `fixed` (always the base delay) or `exponential` (doubles up to the cap).
- **`dead_letter_topic`**: where `dead_letter` sends messages.
- **`poison_policy`**: `dead_letter`, `block`, or `drop`.

### Pick a poison policy

<CardGrid>
  <Card title="dead_letter" icon="warning">
    Copy the message to the dead-letter topic, then move on.

    - The queue keeps flowing.
    - Default for `event_stream` and `task_queue` (`<topic>-dlq`).
  </Card>
  <Card title="block" icon="setting">
    Stop on this message (or this key, in Key-Shared) until it is acked, the policy changes, or the cursor is moved.

    - Nothing is ever skipped.
    - Default for `audit_log` and for topics without an intent.
  </Card>
  <Card title="drop" icon="information">
    Skip the message for this subscription and move on. Other subscriptions are not affected.

    - For data where losing a bad message is fine.
  </Card>
</CardGrid>

### Where defaults come from

- **Topic created with an intent**: the first time a subscription name is used, the broker copies the intent's retries, backoff, and poison policy into it. See [how intent settings reach subscriptions](/concepts/stream-intents/#how-intent-settings-reach-subscriptions).
- **Topic without an intent**: 5 retries, 30000 ms ack timeout, 1000 ms to 60000 ms exponential backoff, `block`.
- **After that**: the stored policy belongs to the subscription and you change it per subscription.

```bash
# Inspect
danube topic subscription failure-policy get /default/orders -s payment-workers

# Override this subscription only
danube topic subscription failure-policy set /default/orders \
  -s payment-workers \
  --max-redelivery-count 8 \
  --ack-timeout-ms 45000 \
  --base-redelivery-delay-ms 1000 \
  --max-redelivery-delay-ms 60000 \
  --backoff-strategy exponential \
  --poison-policy dead_letter \
  --dead-letter-topic /default/orders-dlq
```

### Read and replay the dead-letter topic

Each dead-lettered copy keeps its original attributes and gains diagnostic headers:

- **`x-original-topic`**, **`x-original-subscription`**, **`x-original-topic-offset`**: where it came from.
- **`x-original-producer-id`**, **`x-original-broker-addr`**: who sent it and which broker held it.
- **`x-poison-policy`**, **`x-delivery-attempt`**, **`x-failure-reason`**: what happened (the reason is the last `nack` reason, when given).

```bash
# Look at what failed
danube topic peek /default/orders-dlq --start-offset 0 --count 10

# After fixing the consumer, republish up to 100 messages to the source topic
danube topic dlq replay /default/orders --subscription payment-workers --max-messages 100
```

Replay strips the diagnostic headers and adds `x-danube-replayed-from-dlq` and `x-danube-replayed-subscription`. Use `--dlq-topic` to read from a specific DLQ instead of the subscription's configured one.

## Rewind or skip ahead

Move a subscription's cursor without restarting consumers. This also unblocks a `block` subscription.

```bash
# Resume from an exact offset
danube topic subscription seek /default/orders --subscription payment-workers --to-offset 1200

# Or from a publish time (nanoseconds since the Unix epoch)
danube topic subscription seek /default/orders --subscription payment-workers --to-timestamp-ns 1763150400000000000

# See all subscriptions, or remove one
danube topic subscription list /default/orders
danube topic subscription delete /default/orders --subscription old-sub
```

## Long-running work

For slow jobs such as LLM or tool calls, the Rust consumer can do more than `ack` and `nack`:

- **`extend_lease`**: push back the ack deadline so the message is not redelivered while you are still working.
- **`report_progress`**: save a checkpoint (up to 64 KiB) and extend the lease. If the worker dies, the next one receives the checkpoint in `x-danube-checkpoint-b64` and can resume.
- **`cancel_task_tree`**: cancel a root task and its subtasks (linked by `x-danube-root-msg-id`).

See [AI Agents](/ai-agents/overview/) and the [consumer guide](/client-libraries/consumer/).

<Aside type="note">
All four subscription types work with both delivery modes. Retries, failure policies, DLQ, and seek apply to reliable topics only. See [Dispatch strategies](/concepts/dispatch-strategies/).
</Aside>
