A topic is a named stream of messages. Producers write to it, consumers read from it, and Danube keeps every message in order. Get topics right and everything else (subscriptions, durability, scaling) falls into place.

## The idea in one picture

Think of a topic as a conveyor belt with a name tag. Producers put boxes on one end, and each subscription watches the belt from its own position.

```text
  producer A ─┐
              ├──►  /default/orders  [m1][m2][m3][m4] ──►  subscription "billing"
  producer B ─┘                                      └──►  subscription "analytics"
```

A partitioned topic is the same belt split into several parallel lanes. Each lane can live on a different broker, so one topic can use the CPU, disk, and network of several machines.

```text
                    ┌─► /default/orders-part-0  (broker 1)
  producers ──►     ├─► /default/orders-part-1  (broker 2)
                    └─► /default/orders-part-2  (broker 3)
```

## Create your first topic

```bash
# A plain topic on the local broker
danube topic create /default/orders

# Check owner broker, delivery mode, intent, schema, subscriptions
danube topic describe /default/orders

# Terminal 1: start a consumer first (a new subscription starts at the end)
danube consume /default/orders -s first-look --limit 1

# Terminal 2: send a message
danube produce /default/orders -m 'hello'
```

<Aside type="tip">
In production, create topics with a [stream intent](/concepts/stream-intents/) so the topic carries its delivery, durability, and retry rules with it: `danube topic create /default/orders --intent event_stream`.
</Aside>

## Name a topic

Every topic lives in a namespace and uses a path that starts with a slash:

```text
/{namespace}/{topic_name}
```

- **Simple names**: `/default/orders`, `/payments/refunds`.
- **Nested names**: extra segments are allowed, for example `/agents/team-a/planner/tasks`.
- **Allowed characters**: letters, digits, `-`, `_` and `.` in each segment. Empty segments are rejected.
- **Reserved suffix**: `-part-<N>` is reserved for partitions, so you cannot name a topic `/default/orders-part-0` yourself.

You can also pass a short name plus `--namespace`, for example `danube topic create orders --namespace default`.

## Choose partitioned or not

<CardGrid>
  <Card title="Non-partitioned" icon="document">
    One broker serves the whole topic.

    - Use it for low to moderate traffic.
    - Use it when you need one strict global order.
    - Use it for audit and state logs.
  </Card>
  <Card title="Partitioned" icon="random">
    `N` internal topics named `{topic}-part-0` to `{topic}-part-(N-1)`, placed across brokers by the Load Manager.

    - Use it for high write throughput.
    - Use it to spread consumers over machines.
    - Order is kept per key, not globally.
  </Card>
</CardGrid>

```bash
# A partitioned, durable topic with 3 lanes
danube topic create /default/clicks --intent event_stream --partitions 3
```

The partition count is fixed for the life of the topic. Clients always use the parent name (`/default/clicks`): producers discover the partitions on their own and consumers merge messages from every partition.

## Route messages to partitions

The producer picks the partition for each message:

- **No key** (`send`): round-robin across partitions, for even load.
- **With a key** (`send_with_key`): a hash of the key picks the partition, so every message with the same key lands in the same partition and stays in order.

```bash
# Same key, same partition, ordered
danube produce /default/clicks -m '{"page":"/home"}' --key user-42
```

```rust title="Rust client: keyed send"
producer.send_with_key(payload, None, "user-42").await?;
```

Pair keyed sends with a [Key-Shared subscription](/concepts/subscriptions/#key-shared) to keep per-key order on the consumer side too.

## Create topics explicitly or let producers do it

<Tabs>
  <TabItem label="Explicit (recommended)">
    Create the topic first with the CLI, a desired-state file, or the MCP server. The settings are stored in Raft and follow the topic across restarts and broker moves.

    ```bash
    danube topic create /default/agent-tasks --intent task_queue --partitions 4
    ```

    Or declare it in a file and run `danube apply -f desired_state.yaml`.
  </TabItem>
  <TabItem label="Implicit (auto-create)">
    If a producer connects to a topic that does not exist, the broker creates it. It uses the producer's dispatch mode (non-reliable unless the client asks for reliable) and its partition count. On a topic that already exists, the topic's own strategy wins.

    ```bash
    # Auto-creates a reliable topic with 2 partitions
    danube produce /default/new-topic -m 'first' --reliable --partitions 2
    ```

    ```rust
    let mut producer = client
        .new_producer()
        .with_topic("/default/new-topic")
        .with_name("my-producer")
        .with_reliable_dispatch()
        .with_partitions(2)
        .build()?;
    producer.create().await?;
    ```
  </TabItem>
</Tabs>

<Aside type="note">
`--intent` and `--dispatch-strategy` are alternatives on `danube topic create`. The intent already picks the dispatch strategy. Without either flag, the topic is non-reliable.
</Aside>

## Inspect and manage topics

```bash
# List topics in a namespace
danube topic list --namespace default

# Read up to 10 stored messages without moving any subscription cursor
danube topic peek /default/agent-tasks --start-offset 0 --count 10

# Guess a JSON Schema from recent payloads
danube topic schema infer /default/agent-tasks --sample-size 100

# Fork a topic up to an offset, for replay or experiments
danube topic branch /default/agent-tasks /default/agent-tasks-replay --at-offset 5000

# Move a topic's history to cloud segments (needs shared-fs or object-store storage)
danube topic storage-mode /default/agent-tasks --mode cloud_tiered

# Delete a topic
danube topic delete /default/orders
```

- **`peek`**: non-destructive read, 1 to 100 messages.
- **`schema infer`**: samples recent payloads and prints a JSON Schema you can register.
- **`branch`**: creates an independent copy; see [topic branching](/concepts/persistence/#branch-a-topic).
- **`storage-mode`**: switches between `local` and `cloud_tiered` (`--force` to go back to `local`).
