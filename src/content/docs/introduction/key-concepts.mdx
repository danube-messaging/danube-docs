A handful of terms is all you need to read the rest of these docs. Each one links to a deeper page when you want details.

## Topics and namespaces

A **topic** is a named stream of messages, written as `/{namespace}/{topic}`, for example `/default/orders`. A **namespace** groups topics and carries shared policies such as limits. The `default` namespace exists out of the box.

Topics can be **partitioned** (`--partitions N`) to spread load across brokers. See [Topics](/concepts/topics/).

## Producers, consumers and messages

A **producer** publishes messages to a topic. A **consumer** reads them and, on durable topics, acks each one (or NACKs it to get it redelivered). Messages carry a payload, optional attributes and an optional routing key. See [Messages](/concepts/messages/).

## Subscriptions

A **subscription** is a named cursor on a topic. Every subscription gets its own copy of every message (fan-out). Consumers inside one subscription share the work according to its type:

- **Exclusive**: one consumer, strict order.
- **Shared**: round-robin across consumers. The default in `danube consume`.
- **Failover**: one active consumer, others on standby.
- **Key-Shared**: per-key order across many consumers, with optional key filters.

See [Subscriptions](/concepts/subscriptions/).

## Stream intents

An **intent** says what a topic is for, and Danube picks delivery, durability, retries and dead-letter handling to match:

- **`realtime`**: in memory, zero disk I/O, may drop on disconnect. Token streams, metrics, heartbeats.
- **`event_stream`**: durable, 3 retries, DLQ `<topic>-dlq`. Event meshes, CDC, lakehouse feeds.
- **`task_queue`**: durable with batched fsync, 5 retries, DLQ `<topic>-dlq`. Work queues, agent tool tasks.
- **`audit_log`**: durable with batched fsync, 10 retries, blocks on a poison message instead of skipping. Ledgers, tool-call logs.

```bash
danube topic create /default/jobs --intent task_queue
```

See [Stream intents](/concepts/stream-intents/) for aliases and exact settings.

## Delivery: reliable or not

Under the hood every topic uses one of two **dispatch strategies**. **Non-reliable** pushes messages straight from producer to consumer with no storage. **Reliable** writes to the WAL first and delivers at least once, with acks, retries and DLQs. Intents choose for you. See [Dispatch strategies](/concepts/dispatch-strategies/).

## Storage: WAL and tiers

Reliable topics are written to a local **write-ahead log (WAL)** for fast sequential writes. Older segments can move to S3, GCS, Azure Blob or a shared filesystem. See [Durability](/durability/overview/).

## Schema registry

The **schema registry** is part of the broker and shares port 6650. It stores JSON Schema, Avro and Protobuf schemas with versioning and compatibility checks. See [Schema registry](/client-libraries/schema-registry/).

## Cluster settings live in Raft

Cluster-wide settings (storage, WAL retention, load manager) are not startup flags. They are stored in Raft and changed live with `danube cluster ...` or declaratively with `danube apply -f`. See [Configuration workflow](/getting-started/configuration-workflow/).
