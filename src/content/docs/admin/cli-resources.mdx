This page covers the things you create and fix every day: namespaces, topics, subscriptions and schemas. Each section is a task with copy-paste commands built on `danube topic`, `danube namespace`, `danube schema` and `danube apply`.

```bash
danube topic create /default/orders --intent task_queue
danube topic describe /default/orders
danube topic subscription list /default/orders
```

Topic arguments accept a full path (`/default/orders`) or a bare name plus `--namespace default`. Most read commands take `--output json`.

## Organise topics into namespaces

A namespace groups topics and carries their policies. Every cluster starts with `default`.

```bash
danube namespace create payments
danube namespace topics payments
danube namespace policies payments --output json
danube namespace delete payments     # must be empty first
```

Namespace policies cap producers, subscriptions and consumers per topic, publish and dispatch rates, and message size.

## Create a topic for your workload

Pick a stream intent and Danube chooses delivery, durability and retry behaviour for you:

```bash
danube topic create /default/telemetry --intent realtime
danube topic create /default/events    --intent event_stream
danube topic create /default/jobs      --intent task_queue
danube topic create /default/audit     --intent audit_log
```

- **`realtime`**: in memory, no disk I/O, best effort. For telemetry and live dashboards.
- **`event_stream`**: reliable, WAL-backed, 3 retries then a `<topic>-dlq` dead-letter topic.
- **`task_queue`**: reliable with batched fsync, 5 retries then a `<topic>-dlq`.
- **`audit_log`**: reliable with batched fsync, 10 retries, then blocks rather than dropping anything.

Partitions and schemas stay explicit:

```bash
danube topic create /default/orders --intent event_stream --partitions 6 --schema-subject orders-value
```

Prefer to choose the dispatch strategy yourself? Skip the intent:

```bash
danube topic create /default/raw --dispatch-strategy reliable
```

See [Stream Intents](/concepts/stream-intents/) for every setting each intent applies.

## Inspect a topic

```bash
# Topics in a namespace, or owned by one broker
danube topic list --namespace default
danube topic list --broker 12345678 --output json

# Partitions, dispatch strategy, schema and subscriptions
danube topic describe /default/orders

# Read up to 100 stored messages without moving any cursor
danube topic peek /default/orders --start-offset 0 --count 20
```

<Aside type="note">
`peek` and `schema infer` read payloads, so on a secured cluster your token needs the `ReadPayload` permission.
</Aside>

## Fix a stuck consumer

When a subscription stops making progress, the cause is usually a poison message or a failure policy that does not fit the workload.

<Steps>
1. **Find the subscription** and look at its failure policy:
   ```bash
   danube topic subscription list /default/orders
   danube topic subscription failure-policy get /default/orders --subscription billing
   ```

2. **Adjust retries and send poison messages to a DLQ** instead of blocking:
   ```bash
   danube topic subscription failure-policy set /default/orders --subscription billing \
     --max-redelivery-count 5 --ack-timeout-ms 30000 \
     --base-redelivery-delay-ms 1000 --max-redelivery-delay-ms 60000 \
     --backoff-strategy exponential \
     --poison-policy dead_letter --dead-letter-topic /default/orders-dlq
   ```
   Poison policies: `dead_letter`, `block` or `drop`.

3. **Or skip past the bad range** by moving the cursor:
   ```bash
   danube topic subscription seek /default/orders --subscription billing --to-offset 4200
   ```
</Steps>

To ask an AI assistant for a diagnosis instead, the MCP tool `explain_consumer_stall` does it in one call (see [AI Admin](/admin/mcp/)).

## Replay a DLQ

After you fix the bug that sent messages to the dead-letter topic, push them back to the source topic:

```bash
# Look at what is in the DLQ first
danube topic peek /default/orders-dlq --count 10

# Replay up to 500 messages into /default/orders for the billing subscription
danube topic dlq replay /default/orders --subscription billing --max-messages 500

# Use an explicit DLQ topic and start offset
danube topic dlq replay /default/orders --subscription billing \
  --dlq-topic /default/orders-dlq --start-offset 100
```

## Rewind a subscription

Seeking moves an existing subscription's cursor, so its consumers re-read (or skip) messages.

```bash
danube topic subscription seek /default/events --subscription analytics --to-offset 0
danube topic subscription seek /default/events --subscription analytics \
  --to-timestamp-ns 1700000000000000000
```

## Branch a topic for an experiment

A branch is a zero-copy fork of a topic's history. Test a new consumer or replay production data without touching the original.

```bash
# Branch everything up to now
danube topic branch /default/orders /default/orders-exp

# Branch up to an offset or a point in time
danube topic branch /default/orders /default/orders-exp --at-offset 1000
danube topic branch /default/orders /default/orders-exp --at-timestamp-ns 1700000000000000000
```

## Move a topic to cloud storage

When cluster storage points at an object store (see [Switch storage to S3](/admin/cli-cluster/#switch-storage-to-s3)), promote topics to tiered storage one at a time:

```bash
danube topic storage-mode /default/events --mode cloud_tiered

# Back to local only (needs --force)
danube topic storage-mode /default/events --mode local --force
```

## Move a topic to another broker

Unloading releases a topic from its current broker so the load manager can assign it to a different one.

```bash
danube topic unload /default/orders
```

## Delete things

```bash
danube topic subscription delete /default/orders --subscription old-sub
danube topic delete /default/orders
```

## Register and evolve a schema

The schema registry stores versioned schemas under a subject. Producers and consumers reference the subject; the registry enforces compatibility.

<Steps>
1. **Register the first version**:
   ```bash
   danube schema register orders-value --schema-type json_schema --file orders.json \
     --description "Order events"
   ```
   Types: `json_schema`, `avro`, `protobuf`, `string`, `bytes`.

2. **Pick a compatibility mode**:
   ```bash
   danube schema set-compatibility orders-value --mode backward
   ```
   Modes: `none`, `backward` (new readers read old data), `forward` (old readers read new data), `full` (both).

3. **Check a new version before registering it**:
   ```bash
   danube schema check orders-value --schema-type json_schema --file orders-v2.json
   danube schema register orders-value --schema-type json_schema --file orders-v2.json
   ```

4. **Inspect what is registered**:
   ```bash
   danube schema list-subjects
   danube schema versions orders-value
   danube schema get --subject orders-value --version 1 --output json
   danube schema get --id 42
   danube schema get-compatibility orders-value
   ```
</Steps>

Remove a single version with `danube schema delete orders-value --version 1 --confirm`.

## Enforce a schema on a topic

Bind a subject to a topic and choose how strictly payloads are checked:

```bash
danube topic schema configure /default/orders --subject orders-value \
  --validation-policy enforce --enable-payload-validation

danube topic schema show /default/orders

# Loosen it later
danube topic schema validation-policy /default/orders --policy warn
```

- **`none`**: no checks.
- **`warn`**: invalid messages are accepted and logged.
- **`enforce`**: invalid messages are rejected. Add `--enable-payload-validation` to validate the payload itself, not only the schema reference.

## Infer a schema from live data

Have JSON flowing but no schema yet? Let Danube draft one from recent messages:

```bash
danube topic schema infer /default/orders --sample-size 200
```

The output reports how many messages were sampled and prints a Draft-07 JSON Schema. Review it, save it as `orders.json`, then register it:

```bash
danube schema register orders-value --schema-type json_schema --file orders.json
```

More on schemas in [Schema Registry](/client-libraries/schema-registry/).

## Manage everything from a manifest

`danube apply` reconciles the cluster with a YAML or JSON file. Keep it in git and you have reviewable, repeatable infrastructure.

```yaml title="desired_state.yaml"
namespaces:
  - payments
  - agents

topics:
  - name: /payments/transactions
    intent: audit_log
    partitions: 4
    schema_subject: payment-txn
  - name: /agents/tasks
    intent: task_queue
    partitions: 8
  - name: /agents/events
    dispatch_strategy: reliable
    storage_mode: cloud_tiered

object_store:
  backend: s3
  root: s3://danube-prod/segments
  options:
    region: us-east-1

load_manager:
  assignment_strategy: balanced
  rebalancing:
    enabled: true
    aggressiveness: conservative
```

```bash
# Always look at the plan first
danube apply -f desired_state.yaml --dry-run

# Create and update what differs
danube apply -f desired_state.yaml

# Also delete topics missing from the file (empty, idle ones only)
danube apply -f desired_state.yaml --prune

# Prune even busy or non-empty topics
danube apply -f desired_state.yaml --prune --force

# Read from stdin
cat desired_state.json | danube apply -f -
```

<Aside type="caution">
`apply` is additive by default. Topics only disappear with `--prune`, and `/system/*` topics are never pruned. Run `--dry-run` before every prune.
</Aside>

The manifest also accepts `shared_fs` and `write_buffer` sections. Every field is listed in the [manifest reference](/reference/broker-configuration/#desired-state-manifest).
