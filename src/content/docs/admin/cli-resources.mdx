Use `danube ctl` subcommands (`namespaces`, `topics`, `schemas`, `security`) to manage all messaging resources against the broker endpoint configured via `--endpoint` or `DANUBE_ADMIN_ENDPOINT` (default `http://127.0.0.1:6650`).

```bash
export DANUBE_ADMIN_ENDPOINT=http://127.0.0.1:6650
```

See [CLI: Produce & Consume](/admin/cli-messaging/) for data-plane `produce` and `consume` commands, and [CLI: Cluster & Brokers](/admin/cli-cluster/) for cluster configuration and declarative `apply`.

## Namespaces (`danube ctl namespaces`)

Namespaces provide multi-tenant isolation for topics and policies. Every topic path begins with `/<namespace>/<topic>` (for example, `/default/events`).

### `namespaces create` / `namespaces delete`

```bash
# Create a namespace
danube ctl namespaces create payments

# Delete an empty namespace
danube ctl namespaces delete payments
```

<Aside type="caution">
A namespace **must be empty** before it can be deleted. Delete all topics inside the namespace first using `danube ctl topics delete`.
</Aside>

### `namespaces topics`

List all topics belonging to a namespace:

```bash
danube ctl namespaces topics default
danube ctl namespaces topics default --output json
```

### `namespaces policies`

Inspect effective resource limits and rate policies on a namespace (`max_producers_per_topic`, `max_subscriptions_per_topic`, `max_consumers_per_topic`, `max_consumers_per_subscription`, `max_publish_rate`, `max_subscription_dispatch_rate`, `max_message_size`):

```bash
danube ctl namespaces policies default
danube ctl namespaces policies default --output json
```

Example JSON output:

```json
{
  "max_producers_per_topic": 0,
  "max_subscriptions_per_topic": 0,
  "max_consumers_per_topic": 0,
  "max_consumers_per_subscription": 0,
  "max_publish_rate": 0,
  "max_subscription_dispatch_rate": 0,
  "max_message_size": 0
}
```

## Topics (`danube ctl topics`)

### `topics list` & `topics describe`

List topics by namespace or by owning broker, or inspect full topic metadata:

```bash
# List topics in a namespace
danube ctl topics list --namespace default
danube ctl topics list --namespace default --output json

# List topics currently owned by a specific broker
danube ctl topics list --broker broker-1

# Describe topic partitions, delivery strategy, subscriptions, producers, and consumers
danube ctl topics describe /default/orders
danube ctl topics describe orders --namespace default --output json
```

### `topics create` & `topics delete`

Create a topic directly using a workload [`StreamIntent` profile](/concepts/stream-intents/) (`--intent`) or explicit dispatch/partition settings:

```bash
# Recommended: create with a StreamIntent profile
danube ctl topics create /default/agent-tasks --intent task_queue
danube ctl topics create /default/telemetry --intent realtime --partitions 8
danube ctl topics create /default/audit --intent audit_log

# Or specify partitions, dispatch strategy, and schema explicitly
danube ctl topics create /default/orders \
  --partitions 4 \
  --dispatch-strategy reliable \
  --schema-subject order-events

# Using --namespace flag separately
danube ctl topics create orders --namespace default --partitions 4

# Delete a topic
danube ctl topics delete /default/orders
```

| Flag | Values | Description |
| :--- | :--- | :--- |
| `--namespace <NS>` | string | Namespace if omitted from `<topic>` |
| `--partitions <N>` | integer | Partition count |
| `--dispatch-strategy` | `non_reliable`, `reliable` | Delivery / persistence strategy |
| `--intent` | `realtime`, `event_stream`, `task_queue`, `audit_log` | Preset [Stream Intent](/concepts/stream-intents/) workload profile |
| `--schema-subject` | string | Bind topic to an existing Schema Registry subject |

### `topics storage-mode`

Switch an existing topic between local storage and cloud-tiered storage (`local` or `cloud_tiered`):

```bash
danube ctl topics storage-mode /default/orders --mode cloud_tiered
danube ctl topics storage-mode /default/orders --mode local --force
```

### `topics subscriptions`, `unsubscribe` & `unload`

```bash
# List active subscriptions on a topic
danube ctl topics subscriptions /default/orders --output json

# Remove an unused subscription
danube ctl topics unsubscribe /default/orders -s old-worker-sub

# Unload a topic so the Load Manager reassigns it
danube ctl topics unload /default/orders
```

### Subscription Failure Policies (`set-failure-policy` / `get-failure-policy`)

Configure redelivery backoff, ack timeouts, dead-letter routing, and poison-message handling per subscription:

```bash
# Configure exponential backoff and Dead-Letter Queue (DLQ) routing
danube ctl topics set-failure-policy /default/orders \
  -s payment-workers \
  --max-redelivery-count 5 \
  --ack-timeout-ms 30000 \
  --base-redelivery-delay-ms 1000 \
  --max-redelivery-delay-ms 60000 \
  --backoff-strategy exponential \
  --dead-letter-topic /default/orders-dlq \
  --poison-policy dead_letter

# Inspect active failure policy
danube ctl topics get-failure-policy /default/orders -s payment-workers --output json
```

| Flag | Values | Description |
| :--- | :--- | :--- |
| `-s`, `--subscription <NAME>` | string | Target subscription name |
| `--max-redelivery-count <N>` | integer | Maximum redelivery attempts before poison-policy triggers |
| `--ack-timeout-ms <MS>` | integer | Unacknowledged delivery timeout in milliseconds |
| `--base-redelivery-delay-ms <MS>` | integer | Initial redelivery delay |
| `--max-redelivery-delay-ms <MS>` | integer | Upper bound for exponential backoff delay |
| `--backoff-strategy` | `fixed`, `exponential` | Redelivery delay progression |
| `--dead-letter-topic <TOPIC>` | topic path | Destination DLQ topic when using `dead_letter` policy |
| `--poison-policy` | `dead_letter` (`dead-letter`), `block`, `drop` | Action once redeliveries exceed `--max-redelivery-count` |

### Zero-Copy Branching, Seeking, Peeking, Replay & Schema Inference

```bash
# Zero-copy branch a topic at head, at an offset, or at a nanosecond timestamp
danube ctl topics branch /default/events /default/events-replay
danube ctl topics branch /default/events /default/events-fork --at-offset 1500
danube ctl topics branch /default/events /default/events-t0 --at-timestamp-ns 1731619200000000000

# Seek an existing subscription to a specific offset or timestamp
danube ctl topics seek /default/events --subscription analytics --to-offset 1000
danube ctl topics seek /default/events --subscription analytics --to-timestamp-ns 1731619200000000000

# Replay messages from a Dead-Letter Queue back into the source topic
danube ctl topics replay-dlq /default/orders \
  --subscription payment-workers \
  --dlq-topic /default/orders-dlq \
  --max-messages 100 \
  --start-offset 0

# Peek at retained messages without advancing any consumer cursor (requires ReadPayload)
danube ctl topics peek /default/events --start-offset 0 --count 10

# Infer a JSON Schema draft from recent JSON payloads on a topic (requires ReadPayload)
danube ctl topics infer-schema /default/events --sample-size 100
```

<Aside type="note">
When RBAC authorization is enabled, `topics peek` and `topics infer-schema` require the `ReadPayload` permission on the target topic because they inspect raw message bytes.
</Aside>

### Topic Schema Association & Validation

```bash
# Associate a schema subject and validation policy with a topic
danube ctl topics configure-schema /default/orders \
  --subject order-events \
  --validation-policy enforce \
  --enable-payload-validation

# Update only the validation policy (none, warn, or enforce)
danube ctl topics set-validation-policy /default/orders \
  --policy enforce \
  --enable-payload-validation

# Inspect topic schema configuration
danube ctl topics get-schema-config /default/orders --output json
```

## Schemas (`danube ctl schemas`)

Manage centralized schemas, versions, and compatibility rules in the Danube Schema Registry.

### `schemas list-subjects`

```bash
danube ctl schemas list-subjects
danube ctl schemas list-subjects --output json
```

### `schemas register`

Register a new schema or evolve an existing subject (`json_schema`, `avro`, `protobuf`, `string`, `bytes`):

```bash
# Register from file
danube ctl schemas register order-events \
  --schema-type json_schema \
  --file ./order.schema.json \
  --description "Order lifecycle event schema" \
  --tags domain=commerce \
  --tags team=checkout \
  --output json

# Or pass schema inline
danube ctl schemas register metric-ping \
  --schema-type json_schema \
  --schema '{"type":"object","properties":{"cpu":{"type":"number"}},"required":["cpu"]}'
```

### `schemas get` & `schemas versions`

```bash
# List all registered versions of a subject
danube ctl schemas versions order-events --output json

# Fetch latest schema for a subject
danube ctl schemas get --subject order-events --output json

# Fetch by global schema ID (optionally pinning a version)
danube ctl schemas get --id 1 --version 2 --output json
```

### `schemas check`, `get-compatibility` & `set-compatibility`

```bash
# Get or set subject compatibility mode (none, backward, forward, full)
danube ctl schemas get-compatibility order-events
danube ctl schemas set-compatibility order-events --mode backward

# Check whether a candidate schema satisfies compatibility rules
danube ctl schemas check order-events \
  --file ./order-v2.schema.json \
  --schema-type json_schema \
  --mode full
```

### `schemas delete`

Delete a specific schema version (requires explicit `--confirm`):

```bash
danube ctl schemas delete order-events --version 1 --confirm
```

## Security (`danube ctl security`)

Manage RBAC roles, principal bindings, and JWT tokens. See [Security Overview](/security/overview/) and [Authentication & Authorization](/security/authorization/) for full details.

### Permissions

Roles are composed from these 10 granular permissions:

* Data plane: `Lookup`, `Produce`, `Consume`, `Replicate`, `ReadPayload`
* Admin plane: `ManageNamespace`, `ManageTopic`, `ManageSchema`, `ManageBroker`, `ManageCluster`

### Roles (`danube ctl security roles`)

```bash
# Create a role
danube ctl security roles create topic-writer --permissions Lookup,Produce
danube ctl security roles create schema-admin --permissions ManageSchema,ManageTopic

# Inspect, list, and delete roles
danube ctl security roles get topic-writer --output json
danube ctl security roles list --output json
danube ctl security roles delete topic-writer
```

### Bindings (`danube ctl security bindings`)

Bind roles to `user` or `service_account` principals at `cluster`, `namespace`, or `topic` scope:

```bash
# Grant a service account topic-level write permissions
danube ctl security bindings create orders-producer \
  --principal-type service_account \
  --principal-name checkout-svc \
  --roles topic-writer \
  --scope topic \
  --resource /default/orders

# List and inspect bindings at namespace or cluster scope
danube ctl security bindings list --scope namespace --resource default --output json
danube ctl security bindings get orders-producer --scope topic --resource /default/orders --output json

# Remove a binding
danube ctl security bindings delete orders-producer --scope topic --resource /default/orders
```

### Tokens (`danube ctl security tokens`)

Danube supports both **online cluster-managed tokens** (`issue` / `revoke`, persisted & checked against the broker `SecurityAdmin` RPC) and **offline signed tokens** (`create` / `validate`, using `--secret-key` or `DANUBE_JWT_SECRET_KEY`):

```bash
# Online: issue a JWT via the broker SecurityAdmin service (requires ManageCluster)
danube ctl security tokens issue \
  --subject checkout-svc \
  --type service_account \
  --ttl 24h

# Online: revoke a subject's tokens immediately cluster-wide (requires ManageCluster)
danube ctl security tokens revoke --subject compromised-svc

# Offline: sign a token locally with the shared HMAC secret key
export DANUBE_JWT_SECRET_KEY="my-secret-key"
danube ctl security tokens create \
  --subject bootstrap-admin \
  --type user \
  --ttl 8760h \
  --issuer danube-auth \
  --secret-key "$DANUBE_JWT_SECRET_KEY"

# Offline: validate and decode a token
danube ctl security tokens validate \
  --token "<jwt>" \
  --secret-key "$DANUBE_JWT_SECRET_KEY"
```

<Aside type="caution">
Danube enforces **last-admin lockout protection**: the broker blocks deleting the last role or binding granting `ManageCluster` at cluster scope, or revoking the last active admin / `super_admin` subject.
</Aside>
