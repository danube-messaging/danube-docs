This page is a cookbook for the people who keep Danube running. Each section is one task, with the exact commands to do it, using `danube cluster`, `danube broker` and `danube auth`.

```bash
danube cluster status      # who leads, who votes
danube broker list         # every broker and its state
danube broker balance      # how evenly load is spread
```

All commands connect to `http://127.0.0.1:6650` by default. Add `--endpoint`, `--context` or `DANUBE_ENDPOINT` to target another cluster, as described in [connecting to a broker](/admin/overview/#connect-to-a-broker).

## Check cluster health

```bash
# Raft leader, term, voters and learners
danube cluster status

# Brokers, their addresses and status
danube broker list
danube broker leader

# Load spread across brokers (CV under 20% is well balanced)
danube broker balance
```

Every list command accepts `--output json` for scripts:

```bash
danube broker list --output json
```

## Add a node

New nodes join as non-voting learners first, then you promote them. This keeps quorum safe while the new node catches up.

<Steps>
1. **Start the new node in join mode** on its own host. Give it a separate `--admin-listen`: the shared `--listen` port only opens once the node is a member, so the admin port is how the CLI reaches it before that:
   ```bash
   danube up cluster --data-dir /var/lib/danube --join \
     --listen 0.0.0.0:6650 --admin-listen 0.0.0.0:50051 --advertised-addr node4:6650
   ```

2. **Add it as a learner** from anywhere that can reach both the leader and the new node. `--node-addr` is the new node's admin address:
   ```bash
   danube cluster node add --node-addr http://node4:50051 --endpoint http://node1:6650
   ```
   The CLI asks the new node for its id and Raft address, then tells the leader to add it. Note the printed `node_id`.

3. **Promote it to a voter** once it has caught up:
   ```bash
   danube cluster node promote --node-id 12345678 --endpoint http://node1:6650
   ```

4. **Spread load onto it**:
   ```bash
   danube broker rebalance --dry-run
   danube broker rebalance
   ```
</Steps>

<Aside type="tip">
Starting a brand-new cluster is different: give every node the same `--seed-nodes` list and they bootstrap together. See [Broker Modes](/getting-started/broker-modes/).
</Aside>

## Remove a node

Drain the broker first, then take it out of Raft.

```bash
# Move its topics elsewhere
danube broker unload --broker-id 12345678

# Remove it from the Raft membership
danube cluster node remove --node-id 12345678
```

<Aside type="caution">
Before removing a voter, make sure the remaining voters still form a majority. A three-voter cluster tolerates the loss of one voter, not two.
</Aside>

## Drain a broker for maintenance

Unloading moves every topic off a broker so you can upgrade or restart it with no client-visible downtime.

<Steps>
1. **Preview** which topics will move:
   ```bash
   danube broker unload --broker-id 12345678 --dry-run
   ```

2. **Drain it**, a few topics at a time:
   ```bash
   danube broker unload --broker-id 12345678 --max-parallel 5 --timeout-seconds 120
   ```
   Limit the scope with `--namespaces-include default` or `--namespaces-exclude test` (both repeatable).

3. **Do the maintenance**, then **bring it back** into topic assignment:
   ```bash
   danube broker activate --broker-id 12345678 --reason "kernel upgrade done"
   ```
</Steps>

## Rebalance the cluster

```bash
# 1. How uneven is it?
danube broker balance

# 2. What would move?
danube broker rebalance --dry-run

# 3. Move at most 10 topics
danube broker rebalance --max-moves 10

# 4. Check again
danube broker balance
```

To let the cluster do this on its own, turn on automated rebalancing (see [tune the load manager](#tune-the-load-manager)).

## Switch storage to S3

Cluster storage decides where sealed WAL segments go for durability and tiering. It is a live setting stored in Raft: one command switches every broker, no restart needed.

```bash
# Print the storage section of the cluster config (credentials redacted)
danube cluster storage show
```

<Tabs>
  <TabItem label="S3 / MinIO">
    ```bash
    danube cluster storage object-store --backend s3 \
      --root s3://danube-prod/segments \
      --option region=us-east-1

    # MinIO or any S3-compatible endpoint
    danube cluster storage object-store --backend s3 \
      --root s3://danube/segments \
      --option endpoint=http://minio:9000 \
      --option access_key=minio --option secret_key=minio123
    ```
    S3 options: `region`, `endpoint`, `access_key`, `secret_key`, `session_token`, `anonymous`, `profile`, `role_arn`, `session_name`, `virtual_host_style`.
  </TabItem>
  <TabItem label="GCS">
    ```bash
    danube cluster storage object-store --backend gcs \
      --root gcs://danube-prod/segments \
      --option credentials_path=/etc/danube/gcs.json
    ```
    GCS options: `project`, `endpoint`, `credential_file`, `credentials_path`, `credentials_json`.
  </TabItem>
  <TabItem label="Azure Blob">
    ```bash
    danube cluster storage object-store --backend azblob \
      --root azblob://danube-container/segments \
      --option account_name=mystorage --option account_key="$AZURE_KEY"
    ```
    Azure options: `account_name`, `account_key`, `endpoint`.
  </TabItem>
  <TabItem label="Shared filesystem">
    ```bash
    # NFS, EFS or any POSIX mount shared by all brokers
    danube cluster storage shared-fs --root /mnt/danube-shared
    ```
  </TabItem>
  <TabItem label="Local only">
    ```bash
    # Back to local WAL only
    danube cluster storage local
    ```
  </TabItem>
</Tabs>

<Aside type="caution">
If some topics are already `cloud_tiered`, changing or removing the durable store is refused unless you add `--force`. Know where those segments will be read from before forcing it.
</Aside>

Once a durable store is configured, move individual topics to it with `danube topic storage-mode /default/events --mode cloud_tiered` (see [tiered storage](/durability/tiered-storage/)).

## Add a Valkey write buffer

A Valkey (or Redis) write buffer keeps recent WAL segments warm and replicated across machines before they reach object storage.

```bash
# Production preset: wait for 1 replica, fail on timeout
danube cluster write-buffer enable \
  --endpoints redis://valkey-0:6379,redis://valkey-1:6379 --profile ha

# Fine-tune any field on top of the preset
danube cluster write-buffer enable --endpoints redis://valkey-0:6379 \
  --profile ha --wait-replicas 2 --wait-timeout-ms 250 --max-cached-segments 20

# Turn it off
danube cluster write-buffer disable
```

- **`--profile`**: `ha` (1 replica, 100 ms, fail, 10 cached segments) or `dev` (0 replicas, 50 ms, ack, 2 cached segments).
- **`--on-wait-timeout`**: `fail` rejects the write when replicas do not confirm in time, `ack` accepts it anyway.

## Tune WAL retention

Run `danube cluster wal` with no flags to print the current `storage.wal` and `storage.local_retention` settings. Add flags to change them:

```bash
# Keep 2 days or 20 GiB of local WAL, whichever comes first
danube cluster wal --retention-time-minutes 2880 --retention-size-mb 20480

# Rotate segments at 512 MiB or 24 hours
danube cluster wal --rotate-max-bytes 536870912 --rotate-max-hours 24

# Flush batching and cache size
danube cluster wal --flush-interval-ms 100 --flush-max-batch-bytes 1048576 --cache-capacity 1024

# Remove retention limits and stop the background deleter
danube cluster wal --clear-retention
```

## Tune the load manager

```bash
# Place new topics by measured load
danube cluster load-manager --assignment-strategy weighted_load

# Turn on automated rebalancing with a preset
danube cluster load-manager --rebalance true --profile conservative

# Override individual limits
danube cluster load-manager --max-moves-per-hour 5 --cooldown-seconds 120 \
  --min-brokers 3 --min-topic-age-seconds 600

# Never move these topics
danube cluster load-manager --blacklist-topics "/system/*,/critical/*"
danube cluster load-manager --blacklist-topics "/critical/*" --replace-blacklist   # replace it
danube cluster load-manager --replace-blacklist                                   # clear it
```

- **Strategies**: `fair`, `balanced`, `weighted_load`.
- **Profiles**: `conservative`, `balanced`, `aggressive` set the check interval, moves per hour and cooldown together.

Run it with no flags to print the current `load_manager` settings. The scoring is explained in [Load Manager](/architecture/load-manager/).

## Back up the cluster config

`export-config` writes the live Raft config as YAML or JSON. Secrets (JWT secret, object-store credentials, Valkey URL passwords) are replaced with `<redacted>` by default, so the output is safe to share.

```bash
# Redacted copy, safe for tickets and reviews
danube cluster export-config --format yaml --output cluster.yaml

# Break-glass recovery file with real secrets (written with 0600 permissions)
danube cluster export-config --include-secrets --format yaml --output recovery.yaml

# Include one broker's bind and admin addresses
danube cluster export-config --include-secrets --broker-id 12345678 --format json --output broker.json
```

`--include-secrets` prints a warning to stderr. Keep that file somewhere safe. If quorum is ever lost, start a node with `danube up cluster --data-dir /var/lib/danube --recovery-config recovery.yaml`. A file that still contains `<redacted>` is rejected. See [Crash Recovery](/durability/crash-recovery/) before you do.

## Manage access

These commands need a cluster started with JWT auth (`--auth tls` plus `--jwt-secret`, or `--auth auto-tls`) and a token with the right permissions.

### Give an app permission to produce

```bash
# 1. A role is a named set of permissions
danube auth role create producer-role --permissions Produce,Lookup

# 2. A binding grants roles to a principal at a scope
danube auth binding create orders-app-produce \
  --principal-type service_account --principal-name orders-app \
  --roles producer-role --scope namespace --resource default

# 3. Issue a token for that principal (needs ManageCluster)
danube auth token issue --subject orders-app --ttl 720h
```

- **Permissions**: `Lookup`, `Produce`, `Consume`, `Replicate`, `ManageNamespace`, `ManageTopic`, `ManageSchema`, `ManageBroker`, `ManageCluster`.
- **Scopes**: `cluster` (no `--resource`), `namespace` (`--resource default`) or `topic` (`--resource /default/orders`).

### Inspect and clean up

```bash
danube auth role list
danube auth role get producer-role --output json
danube auth binding list --scope namespace --resource default
danube auth binding get orders-app-produce --scope namespace --resource default
danube auth binding delete orders-app-produce --scope namespace --resource default
danube auth role delete producer-role
```

### Revoke a leaked token

```bash
# Invalidates every token issued for this subject, cluster-wide
danube auth token revoke --subject orders-app
```

### Work with tokens offline

`create` and `validate` never contact a broker. They sign and check tokens with the shared JWT secret, which is handy for bootstrapping.

```bash
export DANUBE_JWT_SECRET=your-shared-secret
danube auth token create --subject ci-runner --ttl 24h
danube auth token create --subject alice --type user --ttl 8h
danube auth token validate eyJhbGciOi...
```

For the full model see [Authentication](/security/authentication/) and [Authorization](/security/authorization/).
