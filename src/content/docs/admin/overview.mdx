Running Danube day to day means creating topics, watching consumers, adding nodes and changing storage. You can do all of it from three places, and all three ship inside the same `danube` binary you already use to start the broker.

```bash
danube up standalone                 # terminal 1: a local node
danube cluster status                # terminal 2: talk to it
```

## Pick your admin surface

<CardGrid>
  <Card title="CLI" icon="seti:shell">
    Every operation as a command: `danube topic`, `danube cluster`, `danube broker`, `danube auth`, `danube apply`. Scriptable, CI friendly, and the reference for everything else.

    ```bash
    danube topic list --namespace default
    ```
  </Card>
  <Card title="Web console" icon="laptop">
    `danube console` runs the HTTP backend for the Danube web console: dashboards for brokers, topics, schemas and RBAC, plus an MCP endpoint at `/mcp`.

    ```bash
    danube console --endpoint http://127.0.0.1:6650
    ```
  </Card>
  <Card title="AI admin (MCP)" icon="puzzle">
    `danube mcp` exposes the admin API as Model Context Protocol tools, prompts and a metrics resource for Claude, Cursor, VS Code, Antigravity and your own agents.

    ```bash
    danube mcp --endpoint http://127.0.0.1:6650
    ```
  </Card>
</CardGrid>

## Where the CLI commands live

The admin commands are split into three task-oriented pages:

- **[Cluster, brokers and access](/admin/cli-cluster/)**: grow and shrink the cluster, switch storage, tune the WAL and load manager, drain brokers, manage roles and tokens.
- **[Topics, namespaces and schemas](/admin/cli-resources/)**: create topics with intents, fix stuck subscriptions, replay a DLQ, register schemas, apply a manifest.
- **[Produce and consume](/admin/cli-messaging/)**: send and read messages from the terminal for testing and debugging.

## Connect to a broker

Every client command talks to the broker's admin gRPC API. By default that is `http://127.0.0.1:6650`, the same port clients publish to, so a local node needs no extra setup.

Point at another cluster with a flag, an environment variable, or a saved context:

```bash
# One-off
danube broker list --endpoint http://broker1:6650

# For the whole shell session
export DANUBE_ENDPOINT=http://broker1:6650

# Saved profile, reused across sessions
danube context add prod --endpoint https://danube.example.com:6650 --tls-ca ./ca.pem --use
danube broker list
```

Settings resolve in this order: flag, then environment variable, then the current context, then the default. Contexts are stored client-side in `~/.config/danube/contexts.toml`; the broker never reads that file.

<Aside type="tip">
On a node started with `--auth auto-tls`, the bootstrap admin token and the CA are written to the data directory. Use them like this: `danube context add local --endpoint https://127.0.0.1:6650 --tls-ca ./danube-data/tls/ca.pem --token "$(cat ./danube-data/bootstrap_admin.token)" --use`.
</Aside>

The full story of connection flags, contexts and shell completions is in [The Danube CLI](/getting-started/the-danube-cli/). Every flag is listed in the [CLI & Configuration Reference](/reference/broker-configuration/).
