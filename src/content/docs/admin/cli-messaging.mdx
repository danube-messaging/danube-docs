`danube produce` and `danube consume` let you poke a topic from the terminal: send a test event, watch what arrives, check a schema, or generate load. No client code, no project setup.

```bash
# Terminal 1: start listening
danube consume /default/events

# Terminal 2: send something
danube produce /default/events -m 'hello'
```

<Aside type="caution">
Start the consumer first. A new subscription on a reliable topic begins at the end of the stream, so messages sent before it exists are not delivered to it.
</Aside>

## Send your first message to a reliable topic

Topics created with an intent such as `event_stream` or `task_queue` use reliable dispatch. The CLI producer must match, so add `-r`:

<Steps>
1. **Create the topic**:
   ```bash
   danube topic create /default/orders --intent event_stream
   ```

2. **Start a consumer** in one terminal:
   ```bash
   danube consume /default/orders -s billing
   ```

3. **Produce** from another:
   ```bash
   danube produce /default/orders -r -m '{"id":1,"total":42.5}'
   ```
</Steps>

If the topic does not exist yet and auto-creation is on, `produce` creates it on first publish. `-r` makes that topic reliable and `-p 3` makes it partitioned. Prefer `danube topic create --intent` so the choice is explicit.

## Generate a burst of traffic

```bash
# 100 messages, one every 50 ms
danube produce /default/events -m '{"temp":21.3}' --count 100 --interval 50
```

- **`-c, --count`**: number of messages. Default `1`.
- **`-i, --interval`**: delay between messages in ms, minimum `10`. Default `500`.
- **`-n, --producer-name`**: producer name. Default `danube-producer`.

## Send a file

The file's raw bytes become the payload, so this works for JSON, Avro, Protobuf or binary data:

```bash
danube produce /default/orders -r -f ./order.json
```

## Route by key and add attributes

Keys drive [Key-Shared](/client-libraries/key-shared/) routing: all messages with the same key go to the same consumer, in order.

```bash
danube produce /default/orders -r -m '{"id":7}' --key customer-42 --attr source:cli,env:dev
```

Then read only some keys:

```bash
danube consume /default/orders -s workers --type key-shared --key-filter 'customer-4*'
```

`--key-filter` is a glob, repeatable, and only applies to `key-shared` subscriptions.

## Choose a subscription type

```bash
danube consume /default/events -s analytics --type exclusive
danube consume /default/events -s workers   --type shared
danube consume /default/events -s standby   --type fail-over
danube consume /default/events -s per-user  --type key-shared
```

- **`exclusive`**: one consumer owns the subscription.
- **`shared`** (default): messages are spread round-robin across consumers.
- **`fail-over`**: one active consumer, others wait to take over.
- **`key-shared`**: each key sticks to one consumer.

Run the same command in two terminals to watch how each type distributes messages. Details in [Subscriptions](/concepts/subscriptions/).

## Read a few messages for a script

```bash
# Stop after 10 messages, one JSON object per line
danube consume /default/events -s probe --limit 10 -o jsonl
```

Without `--limit` (or with `--limit 0`) the consumer streams until you press Ctrl-C.

## Publish with a schema

Messages that reference a registered schema are validated by the broker, and `consume` decodes and validates them before printing.

<Tabs>
  <TabItem label="Existing subject">
    ```bash
    danube produce /default/orders -r -f ./order.json --schema-subject orders-value

    # Pin an exact version, or require a minimum one
    danube produce /default/orders -r -f ./order.json --schema-subject orders-value --schema-version 2
    danube produce /default/orders -r -f ./order.json --schema-subject orders-value --schema-min-version 2
    ```
  </TabItem>
  <TabItem label="Register on the fly">
    ```bash
    # Registers schema.json under the subject "default-orders", then publishes with it
    danube produce /default/orders -r -m '{"id":1}' \
      --schema-file ./schema.json --schema-type json-schema
    ```
    Schema types: `bytes`, `string`, `number`, `json-schema`, `avro`, `protobuf`. The subject name is the topic path with slashes turned into dashes.
  </TabItem>
</Tabs>

Manage subjects and compatibility with `danube schema`, see [Register and evolve a schema](/admin/cli-resources/#register-and-evolve-a-schema).

## Use it inside Docker Compose

Every Danube image ships the `danube` binary, so you can run the CLI inside a broker container:

```bash
# Terminal 1
docker exec -it danube-broker1 danube consume /default/test -s demo

# Terminal 2
docker exec danube-broker1 danube produce /default/test -m 'hello from compose' --count 20
```

## Connect to a remote or secured cluster

Both commands take the standard connection flags, environment variables and contexts:

```bash
danube consume /default/events --endpoint https://danube.example.com:6650 \
  --tls-ca ./ca.pem --token "$DANUBE_TOKEN"

# Or once per shell
export DANUBE_ENDPOINT=https://danube.example.com:6650
export DANUBE_TLS_CA=./ca.pem
danube produce /default/events -m 'hi'
```

See [client connection flags](/reference/broker-configuration/#client-connection-flags) for the full list.
