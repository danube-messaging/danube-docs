`danube mcp` turns your cluster into something an AI assistant can actually operate. It exposes the Danube admin API as [Model Context Protocol](https://modelcontextprotocol.io) tools, so Claude, Cursor, VS Code, Antigravity or your own agent can check health, explain a stalled consumer, or create topics, all through the same guarded API the CLI uses.

```bash
danube mcp --endpoint http://127.0.0.1:6650
```

That one command speaks MCP over stdio, which is what IDEs expect. Add it to your assistant's config and ask "is my Danube cluster healthy?".

## What the server exposes

<CardGrid>
  <Card title="71 tools" icon="setting">
    Cluster, topics, schemas, security, diagnostics, logs and metrics. Destructive ones refuse to run without explicit confirmation.
  </Card>
  <Card title="4 prompts" icon="list-format">

## Connect your assistant

The server binary is `danube`, the subcommand is `mcp`, and connection flags work exactly as in the CLI.

<Tabs>
  <TabItem label="Claude Desktop / Cursor">
    Add this to `claude_desktop_config.json` or `.cursor/mcp.json`:
    ```json
    {
      "mcpServers": {
        "danube": {
          "command": "danube",
          "args": ["mcp", "--endpoint", "http://127.0.0.1:6650"]
        }
      }
    }
    ```
  </TabItem>
  <TabItem label="VS Code">
    Add this to `.vscode/mcp.json`:
    ```json
    {
      "servers": {
        "danube": {
          "type": "stdio",
          "command": "danube",
          "args": ["mcp", "--endpoint", "http://127.0.0.1:6650"]
        }
      }
    }
    ```
  </TabItem>
  <TabItem label="Claude Code">
    ```bash
    claude mcp add danube -- danube mcp --endpoint http://127.0.0.1:6650
    ```
  </TabItem>
  <TabItem label="Secured cluster">
    Pass the token and CA through the environment so they stay out of the args list:
    ```json
    {
      "mcpServers": {
        "danube": {
          "command": "danube",
          "args": ["mcp", "--endpoint", "https://danube.example.com:6650"],
          "env": {
            "DANUBE_TOKEN": "<admin-jwt>",
            "DANUBE_TLS_CA": "/path/to/ca.pem"
          }
        }
      }
    }
    ```
    You can also save a context once (`danube context add prod ... --use`) and use `"args": ["mcp", "--context", "prod"]`.
  </TabItem>
</Tabs>

## Serve MCP over HTTP

For remote agents, containers or a shared team gateway, serve streamable HTTP instead of stdio:

```bash
danube mcp --http 0.0.0.0:8080 --endpoint http://127.0.0.1:6650
```

Clients connect to `http://<host>:8080/mcp`:

```json
{
  "mcpServers": {
    "danube-remote": {
      "type": "streamable-http",
      "url": "http://danube-admin.internal:8080/mcp"
    }
  }
}
```

<Aside type="caution">
`danube mcp --http` has no HTTP authentication of its own. To require a bearer token on `/mcp`, run [`danube console`](/admin/admin-ui/) with `--http-token` instead: it serves the same `/mcp` endpoint and checks `Authorization: Bearer <token>` on every request.
</Aside>

## Command flags

- **`--http <ADDR>`**: serve streamable HTTP MCP on this address instead of stdio.
- **`--config <FILE>`**: MCP configuration file that enables log access tools. Env: `DANUBE_MCP_CONFIG`.
- **`--prometheus-url <URL>`**: Prometheus used by the metrics tools. Default `http://localhost:9090`. Env: `DANUBE_PROMETHEUS_URL`.
- **`--metrics-timeout-ms <MS>`**: Prometheus query timeout. Default `5000`.
- **`--request-timeout-ms <MS>`**: admin API request timeout. Default `5000`.
- **Connection**: `--endpoint`, `--context`, `--token`, `--tls`, `--tls-ca`, `--tls-cert`, `--tls-key`, `--tls-domain`. See [client connection flags](/reference/broker-configuration/#client-connection-flags).

## Works with zero configuration

You do not need Prometheus or a log collector to get started:

- **Logs**: without a config file, `get_broker_logs` reads the broker's in-memory log ring buffer over the admin API, with `lines`, `level`, `target` and `contains` filters.
- **Metrics**: when Prometheus is unreachable, `get_cluster_metrics`, `get_broker_metrics` and `get_topic_metrics` fall back to the broker's built-in telemetry snapshot.

Add Prometheus (`--prometheus-url`) for historical PromQL queries, and a config file for container and pod logs.

## Add log access with a config file

The `--config` file tells the server where your brokers' logs live, which unlocks `fetch_container_logs`, `fetch_pod_logs` and the named-broker mode of `get_broker_logs`.

<Tabs>
  <TabItem label="Docker">
    ```yaml title="mcp-config.yml"
    broker_endpoint: "http://localhost:6650"
    prometheus_url: "http://localhost:9090"
    deployment:
      type: docker
      docker:
        brokers:
          - id: broker1
            container: danube-broker1
          - id: broker2
            container: danube-broker2
          - id: broker3
            container: danube-broker3
    ```
  </TabItem>
  <TabItem label="Kubernetes">
    ```yaml title="mcp-config.yml"
    broker_endpoint: "http://danube-broker.danube.svc:6650"
    deployment:
      type: kubernetes
      kubernetes:
        namespace: danube
        broker_selector: "app=danube-broker"   # or broker_service: danube-broker
    ```
    Requires `kubectl` configured for the cluster.
  </TabItem>
  <TabItem label="Local files">
    ```yaml title="mcp-config.yml"
    broker_endpoint: "http://127.0.0.1:6650"
    deployment:
      type: local
      local:
        log_dir: ./logs
        brokers:
          - id: broker1
            log_file: broker1.log
    ```
  </TabItem>
</Tabs>

```bash
danube mcp --config ./mcp-config.yml
```

<Aside type="note">
In stdio mode, `broker_endpoint` from the config file decides which broker the server connects to, overriding `--endpoint`.
</Aside>

## Safety guardrails

Destructive tools refuse to run unless the call includes `confirm_destructive: true`. An assistant exploring your cluster cannot delete anything by accident.

- **Cluster**: `unload_broker`, `delete_namespace`, `promote_cluster_node`, `remove_cluster_node`, and `apply_desired_state` when `prune` is true and `dry_run` is false.
- **Topics and subscriptions**: `delete_topic`, `unsubscribe`, `unload_topic`, `seek_subscription`, `replay_dlq`.
- **Schemas and security**: `delete_schema_version`, `delete_role`, `delete_binding`.

<Aside type="tip">
`trigger_rebalance`, `unload_broker` and `apply_desired_state` accept `dry_run: true`, so the assistant can show you the exact plan before asking for confirmation.
</Aside>

## Tools by category

### Cluster, brokers and configuration (21)

- `cluster_status`: Raft leader, term, voters and learners.
- `list_brokers`, `get_leader`: brokers with address, role and status.
- `get_cluster_balance`, `trigger_rebalance`: inspect load spread and move topics (supports dry run).
- `unload_broker`, `activate_broker`: drain a broker and bring it back.
- `list_namespaces`, `get_namespace_policies`, `create_namespace`, `delete_namespace`.
- `add_cluster_node`, `promote_cluster_node`, `remove_cluster_node`: Raft membership.
- `cluster_configure_storage`, `configure_object_store`: switch durable storage.
- `cluster_configure_write_buffer`, `cluster_configure_wal`, `cluster_configure_load_manager`: live cluster settings.
- `cluster_export_config`: export the break-glass recovery config.
- `apply_desired_state`: reconcile a YAML or JSON manifest (`dry_run`, `prune`, `force`).

### Topics and subscriptions (18)

- `list_topics`, `describe_topic`, `create_topic` (with `intent`), `delete_topic`, `unload_topic`.
- `list_subscriptions`, `unsubscribe`, `seek_subscription`.
- `get_subscription_failure_policy`, `set_subscription_failure_policy`: retries, backoff, poison policy and DLQ.
- `replay_dlq`: move dead-lettered messages back to the source topic.
- `explain_consumer_stall`: diagnose why a subscription stopped making progress.
- `peek_messages`, `infer_topic_schema`: read payloads without moving cursors (need the `ReadPayload` permission).
- `branch_topic`: zero-copy branch at head, an offset or a timestamp.
- `configure_topic_schema`, `set_topic_validation_policy`, `get_topic_schema_config`.

### Schema registry (9)

- `list_subjects`, `register_schema`, `get_schema`, `get_schema_by_id`, `list_schema_versions`.
- `check_schema_compatibility`, `get_schema_compatibility_mode`, `set_schema_compatibility_mode`.
- `delete_schema_version`.

### Security (10)

- `create_role`, `get_role`, `list_roles`, `delete_role`.
- `create_binding`, `get_binding`, `list_bindings`, `delete_binding`.
- `create_token`, `validate_token`: sign and decode JWTs with a shared secret.

### Diagnostics (3)

- `health_check`: brokers, Raft and topic balance in one report.
- `analyze_consumer_lag`: find backlog and unacked buildup.
- `get_recommendations`: next steps, phrased as concrete tool calls.

### Logs (6)

- `get_broker_logs`: from the config file sources, or the broker ring buffer when there is none.
- `list_configured_brokers`: the log sources defined in the config file.
- `list_docker_containers`, `fetch_container_logs`: any Docker container.
- `list_k8s_pods`, `fetch_pod_logs`: any Kubernetes pod.

### Metrics (4)

- `get_cluster_metrics`, `get_broker_metrics`, `get_topic_metrics`: Prometheus, with a snapshot fallback.
- `query_prometheus`: run any PromQL query.

## Prompts

Prompts are ready-made workflows the assistant follows step by step.

- **`cluster_health_check`**: full assessment of Raft, load balance, broker status and security. No arguments.
- **`prepare_cluster_rebalance`**: dry run, review, execute, verify. Optional `max_moves`.
- **`manage_schema_evolution`**: compatibility check, registration and topic policy review. Arguments `subject` and optional `schema_type`.
- **`secure_cluster_setup`**: TLS, JWT tokens, RBAC roles and bindings end to end. Optional `environment`.
