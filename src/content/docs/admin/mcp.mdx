Danube includes a native [Model Context Protocol (MCP)](https://modelcontextprotocol.io) server inside the unified `danube` binary (`danube mcp` / `danube ctl serve`). It exposes **71 operational tools across 7 categories**, **4 guided diagnostic prompts**, and **1 metrics catalog resource** to AI assistants such as Claude Code, Antigravity, Cursor, VS Code, and custom agent frameworks.

For broader agent-native workflows (zero-copy branching, schema inference, and `StreamIntent` profiles), see [Danube for AI Agents](/ai-agents/overview/).

---

## Running the MCP Server

### Option 1: Local `stdio` Transport (`danube mcp`)

Ideal for local IDE integrations that spawn the MCP process directly:

```bash
danube mcp --broker-endpoint http://localhost:6650
```

`danube mcp` is equivalent to `danube ctl serve --mode mcp`.

### Option 2: Streamable HTTP Transport (`/mcp`)

To expose MCP over HTTP (for remote agents, containers, or shared team gateways), start `danube ctl serve` in `ui` (HTTP) or `all` (HTTP + `stdio`) mode. The HTTP server exposes `/mcp` alongside the `/ui/v1/...` Admin UI BFF routes:

```bash
danube ctl serve --mode ui \
  --listen-addr 0.0.0.0:8080 \
  --broker-endpoint http://localhost:6650
```

Remote MCP clients connect to `http://<host>:8080/mcp`. When `DANUBE_HTTP_TOKEN` (or `DANUBE_ADMIN_TOKEN`) is set, or `DANUBE_HTTP_REQUIRE_AUTH=true` is configured, requests to `/mcp` require an `Authorization: Bearer <jwt>` header.

<Aside type="tip">
Basic health checks, metrics queries, and log inspection work with **zero extra configuration** — `get_broker_logs` and metrics tools automatically fall back to the broker's in-memory gRPC ring buffers over port `6650` when external Docker/Kubernetes log paths or Prometheus are not configured.
</Aside>

## IDE & Client Setup

<Tabs>
  <TabItem label="Claude Code">
    Add the server via the CLI:
    ```bash
    claude mcp add danube -- danube mcp --broker-endpoint http://localhost:6650
    ```
  </TabItem>
  <TabItem label="Cursor / VS Code / Antigravity">
    Add the following to your MCP client configuration (`.mcp.json` or IDE settings):
    ```json
    {
      "mcpServers": {
        "danube": {
          "command": "danube",
          "args": ["mcp", "--broker-endpoint", "http://localhost:6650"],
          "env": {
            "DANUBE_ADMIN_TOKEN": "optional-jwt-for-secured-clusters"
          }
        }
      }
    }
    ```
    For secured clusters using TLS, also set `DANUBE_ADMIN_TLS=true` and `DANUBE_ADMIN_CA` (plus `DANUBE_ADMIN_CERT` / `DANUBE_ADMIN_KEY` for mTLS) inside `"env"`.
  </TabItem>
  <TabItem label="Streamable HTTP Client">
    Point remote MCP clients at the HTTP server's `/mcp` endpoint:
    ```json
    {
      "mcpServers": {
        "danube-remote": {
          "type": "streamable-http",
          "url": "http://localhost:8080/mcp",
          "headers": {
            "Authorization": "Bearer <YOUR_JWT_TOKEN>"
          }
        }
      }
    }
    ```
  </TabItem>

## Zero-Config Fallbacks vs Optional `mcp-config.yml`

Out of the box, MCP metrics and logs require no Prometheus instance or container runtime sockets:

* **In-memory Broker Logs (`GetBrokerLogs` RPC)**: If no `deployment` block is configured in `mcp-config.yml`, `get_broker_logs` queries the broker's tracing ring buffer directly over gRPC, supporting `lines` (`1`–`2000`), `level`, `target`, and `contains` filters.
* **In-memory Telemetry Snapshots (`GetMetricsSnapshot` RPC)**: When Prometheus (`--prometheus-url`, default `http://localhost:9090`) is unavailable or unreachable, `get_cluster_metrics`, `get_broker_metrics`, and `get_topic_metrics` fall back to the broker's 1-hour telemetry ring buffer (sampled every 10 seconds, defaulting to a 300-second window).

When you want historical PromQL queries or host-level Docker/Kubernetes container log fetching (`fetch_container_logs`, `fetch_pod_logs`), supply an optional `mcp-config.yml` via `--config /path/to/mcp-config.yml` (or `DANUBE_MCP_CONFIG`):

```yaml title="mcp-config.yml (Docker example)"
broker_endpoint: "http://localhost:6650"
prometheus_url: "http://localhost:9090"
deployment:
  type: "docker"
  docker:
    brokers:
      - id: "broker-1"
        container: "danube-broker1"
      - id: "broker-2"
        container: "danube-broker2"
      - id: "broker-3"
        container: "danube-broker3"
```

```yaml title="mcp-config.yml (Kubernetes / Local examples)"
# Kubernetes:
deployment:
  type: "kubernetes"
  kubernetes:
    namespace: "danube"
    broker_selector: "app=danube-broker"

# Local processes reading log files from disk:
deployment:
  type: "local"
  local:
    log_dir: "./logs"
    brokers:
      - id: "broker-1"
        log_file: "./logs/broker1.log"
```

## Safety Guardrails (`confirm_destructive: true`)

Destructive or state-disrupting MCP tools reject execution unless the caller explicitly passes `confirm_destructive: true`. This prevents accidental data loss during autonomous debugging or rebalancing.

Tools enforced by `confirm_destructive: true`:

* **Cluster & Namespaces**: `unload_broker` (when `dry_run` is not `true`), `delete_namespace`, `promote_cluster_node`, `remove_cluster_node`, `apply_desired_state` (when `prune: true` and `dry_run` is not `true`)
* **Topics & Subscriptions**: `delete_topic`, `unsubscribe`, `unload_topic`, `seek_subscription`, `replay_dlq`
* **Schemas & Security**: `delete_schema_version`, `delete_role`, `delete_binding`

<Aside type="tip">
Both `trigger_rebalance`, `unload_broker`, and `apply_desired_state` support `dry_run: true`, allowing an AI assistant to inspect the exact impact plan before requesting confirmation.
</Aside>
