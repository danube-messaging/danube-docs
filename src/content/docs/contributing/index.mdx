Want to fix a bug or add a feature? This page takes you from a fresh clone to a merged pull request. Danube is pure Rust with embedded Raft, so a full dev cluster runs on your laptop with no etcd, ZooKeeper or config files.

```bash
# Build, start a node, and poke it
cargo build -p danube-broker
target/debug/danube up standalone
target/debug/danube topic list --namespace default   # in a second terminal
```

## What you need

- **[Rust](https://www.rust-lang.org/tools/install)** (stable): builds the `danube` binary and the workspace crates.
- **[protobuf-compiler](https://grpc.io/docs/protoc-installation/)** (3.x+): generates gRPC code from `.proto` files.
- **[Docker](https://docs.docker.com/get-docker/)** and **[Docker Compose](https://docs.docker.com/compose/install/)** (optional): containerized 3-broker cluster and Prometheus.

## Fork and clone

<Steps>

1. **Fork** [github.com/danube-messaging/danube](https://github.com/danube-messaging/danube).

2. **Clone** your fork:

   ```bash
   git clone https://github.com/<your-username>/danube.git
   cd danube
   ```

3. **Add upstream** to stay in sync:

   ```bash
   git remote add upstream https://github.com/danube-messaging/danube.git
   ```

</Steps>

## Build the binary

Everything compiles into one binary, `danube`, from the `danube-broker` crate. It holds the server (`danube up`), the CLI (`danube topic`, `danube cluster`, ...), the web console backend (`danube console`) and the MCP server (`danube mcp`).

<Tabs>
  <TabItem label="Debug (daily work)">

```bash
cargo build -p danube-broker
# -> target/debug/danube
```

  </TabItem>
  <TabItem label="Release">

```bash
cargo build --release -p danube-broker
# -> target/release/danube
```

  </TabItem>
  <TabItem label="With lakehouse">

```bash
# Apache Iceberg export; use lakehouse-aws for S3 support
cargo build --release -p danube-broker --features lakehouse

# Check the whole workspace including lakehouse crates
cargo check --workspace --features danube-broker/lakehouse
```

  </TabItem>
</Tabs>

## Run Danube locally

### One node, fastest loop

```bash
target/debug/danube up standalone --data-dir /tmp/danube-dev
```

<Aside type="tip">
Append `--dry-run` to any `danube up` command to print the resolved config and exit. Handy when you change flag handling.
</Aside>

### A 3-broker cluster

<Tabs>
  <TabItem label="Makefile (native)">

```bash
make brokers
```

This builds `target/release/danube` and starts three `danube up cluster` processes that bootstrap through seed nodes:

- **Broker 0**: client `6650`, admin `50051`, Raft `7650`, metrics `9040`
- **Broker 1**: client `6651`, admin `50052`, Raft `7651`, metrics `9041`
- **Broker 2**: client `6652`, admin `50053`, Raft `7652`, metrics `9042`

Data goes to `./danube-data/broker-N`, logs to `temp/broker_<port>.log`. Admin runs on its own port here (`--admin-listen`), so point admin commands at it:

```bash
target/release/danube cluster status --endpoint http://127.0.0.1:50051
```

**Useful targets**

- **`make brokers`**: build and start 3 brokers
- **`make brokers-stop`**: stop them, keep Raft data for restart testing
- **`make brokers-clean`**: stop them and delete all data
- **`make broker-kill ID=0`** / **`make broker-start ID=0`**: stop or start one broker
- **`make cluster-status`**: `danube cluster status` against broker 0
- **`make data-clean`**: remove `./danube-data/broker-*`
- **`make admin`** / **`make admin-clean`**: start or stop `danube console` on port `8080`
- **`make prom`** / **`make prom-clean`**: start or stop Prometheus on `9090` (Docker)

Raise the log level with `RUST_LOG=danube_broker=debug make brokers`.

  </TabItem>
  <TabItem label="Docker Compose">

```bash
cd docker
docker compose up -d --build
```

`docker/docker-compose.yml` builds the image from the root `Dockerfile` and runs `broker1`, `broker2` and `broker3`. Client, schema and admin gRPC share one port per broker:

- **`danube-broker1`**: `6650`, metrics `9040`
- **`danube-broker2`**: `6651`, metrics `9041`
- **`danube-broker3`**: `6652`, metrics `9042`

Run CLI commands from the host or inside a container:

```bash
target/release/danube cluster status
docker exec danube-broker1 danube cluster status
```

Run the web console and HTTP MCP endpoint (`http://127.0.0.1:8080/mcp`) against it:

```bash
target/release/danube console --listen 0.0.0.0:8080 --endpoint http://127.0.0.1:6650
```

Tear it down with `docker compose down -v`.

  </TabItem>
</Tabs>

## Run the tests

### Unit tests (no services needed)

```bash
# Everything CI runs as unit tests
cargo test --workspace --lib --bins

# Just the broker binary, or just the CLI parsing tests
cargo test -p danube-broker --bin danube
cargo test -p danube-broker --bin danube cli::
```

The `cli::` tests check the whole command tree: every command parses, `danube up` mode rules, the data-dir mode marker and plural aliases. Run them whenever you touch a flag.

### Integration tests (need a cluster)

<Steps>

1. **Start a cluster** and give Raft a few seconds to elect a leader:

   ```bash
   make brokers
   ```

2. **Broker suites**, run serially to avoid timing contention. They connect to `http://127.0.0.1:6650` (override with `DANUBE_BROKER_ENDPOINT`):

   ```bash
   cargo test --release -p danube-broker --tests -- --test-threads=1 --nocapture
   ```

3. **Raft and storage suites:**

   ```bash
   cargo test -p danube-raft --tests -- --nocapture
   cargo test -p danube-persistent-storage --tests -- --nocapture
   ```

4. **Admin CLI suites** (topic, namespace and schema lifecycles, MCP smoke test):

   ```bash
   cargo test -p danube-admin --tests -- --nocapture
   ```

5. **Clean up:**

   ```bash
   make brokers-clean
   ```

</Steps>

### What each crate tests

- **`danube-broker`**: pub/sub, intents, agentic primitives, schema validation, Key-Shared, partitioning, reliable dispatch, branching, security, failover, topic moves.
- **`danube-admin`**: CLI commands, namespace/topic/schema/security lifecycles, `danube apply`, console HTTP API and MCP server.
- **`danube-raft`**: metadata CRUD, watches and TTLs, `/cluster/config/*`, leadership.
- **`danube-persistent-storage`**: WAL, retention, tiered storage (`local`, `shared_fs`, `object_store`), ownership transitions.
- **`danube-edge`**: MQTT gateway and WAL-buffered replication.
- **`danube-iceberg`**: Iceberg table export (with `--features lakehouse`).
- **`danube-schema`**: JSON Schema, Avro and Protobuf parsing and compatibility.
- **`danube-client`**: Rust client SDK and agent runtime primitives.
- **`danube-core`**: protocol definitions, `StreamMessage` and attribute constants.

## Open a pull request

<Steps>

1. **Branch** from `main`:

   ```bash
   git checkout -b feature/my-change
   ```

2. **Commit** with a clear message:

   ```bash
   git add .
   git commit -m "feat: add support for XYZ"
   ```

3. **Run unit tests and the lakehouse check:**

   ```bash
   cargo test --workspace --lib --bins
   cargo check --workspace --features danube-broker/lakehouse
   ```

4. **Run integration tests** against a local cluster:

   ```bash
   make brokers
   cargo test --release -p danube-broker --tests -- --test-threads=1 --nocapture
   make brokers-clean
   ```

5. **Push** and open a PR at [github.com/danube-messaging/danube/pulls](https://github.com/danube-messaging/danube/pulls):

   ```bash
   git push origin feature/my-change
   ```

</Steps>

### What CI runs

- **`unit-tests.yml`**: `cargo test --workspace --lib --bins` and the lakehouse feature check.
- **`pull-request-tests.yml`**: builds the release binary, starts 3 brokers, runs the `danube-broker`, `danube-raft` and `danube-persistent-storage` integration suites, and prints all broker logs if anything fails.
- **End-to-end workflows**: CLI, security, failover, restart, rebalancing, reliable move on shared FS, write buffer and edge replication each have their own `*-e2e.yml`.

## Read the logs

<Tabs>
  <TabItem label="Makefile brokers">

```bash
tail -f temp/broker_6650.log
```

  </TabItem>
  <TabItem label="Docker Compose">

```bash
docker compose logs -f broker1
```

  </TabItem>
  <TabItem label="From the broker itself">

Every broker keeps its last 5,000 structured log entries and an hour of telemetry samples in memory. Read them over the admin API through `danube mcp` (`GetBrokerLogs`, `GetMetricsSnapshot`), or from the web console.

  </TabItem>

## Find your way around

<FileTree>
- danube/
  - danube-broker/ (the `danube` binary: server, `up` CLI, E2E tests)
  - danube-admin/ (client CLI commands, console HTTP API, MCP server)
  - danube-client/ (Rust client library and agent runtime primitives)
  - danube-core/ (shared types, attribute keys, protobuf definitions)
  - danube-edge/ (edge MQTT gateway library)
  - danube-iceberg/ (Iceberg lakehouse export, feature `lakehouse`)
  - danube-persistent-storage/ (WAL, durable segments, shared and cloud backends)
  - danube-raft/ (embedded Raft and `/cluster/config/*` state)
  - danube-schema/ (Schema Registry logic)
  - docker/ (3-broker `docker-compose.yml`)
  - Dockerfile (the `ghcr.io/danube-messaging/danube` image)
  - Makefile (local multi-broker commands)
  - .github/workflows/ (unit, PR and E2E pipelines)
</FileTree>
