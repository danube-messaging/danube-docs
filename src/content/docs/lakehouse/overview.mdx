Danube Iceberg bridges real-time messaging and batch analytics. Built directly into the `danube` binary as an isolated, feature-gated `LakehouseRuntime`, it continuously converts sealed WAL segments exported to object storage into Apache Iceberg tables—queryable by Spark, Trino, DuckDB, Snowflake, Athena, and any Iceberg-compatible engine.

---

## Why Lakehouse Integration

Streaming platforms and data lakes have traditionally been separate systems. Getting data from one to the other meant building and maintaining fragile ETL pipelines that introduce latency, require separate orchestration, and break when schemas evolve.

Danube makes the lakehouse export pipeline a native, isolated capability of the node runtime:

## What It Does

`LakehouseRuntime` watches for sealed WAL segments exported by brokers to cloud or local object storage (S3, GCS, Azure Blob, or filesystem). When new segments appear, it decodes the WAL frames, compacts messages into ZSTD-compressed Parquet files with column statistics, and atomically commits them to an Iceberg catalog.

<Steps>
1. **Discover new segments**

   Polls the Danube cluster for newly sealed `.dnb1` segments in object storage. Only immutable, sealed segments are processed—active WAL segments being written by brokers are never touched.

2. **Decode and resolve schema**

   Reads each sealed segment and decodes WAL frames back into messages. If the topic has a schema registered in the Danube Schema Registry (JSON Schema or Avro), the runtime produces typed Parquet columns. Topics without a schema fall back to a structured envelope format.

3. **Write Parquet data files**

   Compacts decoded records into Parquet files using ZSTD compression. Each file includes per-column statistics (min/max bounds and null counts) so query engines skip irrelevant files via predicate pushdown.

4. **Commit to Iceberg catalog**

   Registers new data files with the configured Iceberg catalog (REST, AWS Glue, S3 Tables, SQL, or Parquet-only `none`). Each commit is atomic—readers never observe partial data.

5. **Checkpoint progress**

   Persists per-topic checkpoints in object storage so restarts resume cleanly from the last committed segment offset with at-least-once semantics.
</Steps>

## Key Features

### Isolated Execution & Dedicated Worker Roles

`LakehouseRuntime` runs inside the `danube` process on its own isolated Tokio runtime (`danube-lakehouse` worker threads, defaulting to 2 threads and a 128 MiB memory budget), completely separate from the broker's pub/sub I/O threads.

You can deploy it in two topologies via `--node-role`:

| `--node-role` | Behavior | Best For |
|---|---|---|
| `all` *(default)* | Runs both pub/sub broker serving and `LakehouseRuntime` (activated when `DANUBE_LAKEHOUSE_CONFIG` is set) | Compact clusters, dev/staging, single-binary deployments |
| `lakehouse` | Starts as a dedicated Lakehouse worker node and auto-registers as `drained` (`lakehouse_only`) so the Load Manager never assigns client pub/sub topics to it | Production isolation—scale Parquet compaction independently from message brokers |
| `broker` | Runs pub/sub broker serving only and skips `LakehouseRuntime` even if `DANUBE_LAKEHOUSE_CONFIG` is set | Stateless or latency-critical messaging nodes |

### Schema-Aware Conversion

When a topic has a registered schema (JSON Schema or Avro), `LakehouseRuntime` emits Parquet files with native typed columns—a temperature reading becomes a `Float64` column named `temperature` rather than a binary blob requiring query-time parsing.

For schema-less topics, it writes a queryable envelope schema with `offset`, `publish_time`, `producer_name`, and `payload` columns.

### Crash-Safe Checkpointing

Progress is checkpointed per topic in object storage. On restart or container rescheduling, the worker resumes from the last committed segment without external state stores or duplicate full scans.

### Query Engine Statistics

Every Parquet file records per-column min/max bounds, null counts, and value counts, allowing Iceberg query engines to prune files before scanning storage.

## Supported Catalogs

| Catalog (`catalog.type`) | Feature Requirement | Description | Typical Use Case |
|---|---|---|---|
| `rest` | `lakehouse` *(default in Dockerfile)* | Universal REST catalog (Nessie, Polaris, Tabular, Unity) | Multi-engine environments, self-hosted or managed |
| `glue` | `lakehouse-aws` | AWS Glue Data Catalog | AWS-native data lakes |
| `s3tables` | `lakehouse-aws` | AWS S3 Tables (managed Iceberg) | Fully managed Iceberg on S3 |
| `sql` | `lakehouse` | SQL-backed catalog (SQLite, PostgreSQL) | Development, self-hosted metadata |
| `none` | `lakehouse` | Parquet-only mode (no catalog commits) | Writing standalone Parquet datasets to object storage |

:::tip
For most deployments, a REST catalog (`type: rest` with Polaris or Nessie) is the easiest starting point and works seamlessly across Spark, Trino, and DuckDB.
:::

## Building & Running

### Feature Flags (`cargo build`)

The lakehouse subsystem is compiled into `danube` using Cargo feature flags on `danube-broker`:

```bash
# Standard build (includes REST catalog and Parquet-only export)
cargo build --release --features danube-broker/lakehouse

# AWS build (adds AWS Glue and S3 Tables catalog support)
cargo build --release --features danube-broker/lakehouse-aws
```

### Co-Located Node (`--node-role all`)

Set `DANUBE_LAKEHOUSE_CONFIG` alongside normal broker startup (when unset, `LakehouseRuntime` initializes in idle standby without starting export workers):

```bash
DANUBE_LAKEHOUSE_CONFIG=/etc/danube/lakehouse.yaml \
  danube up \
    --data-dir /var/lib/danube \
    --node-role all
```

### Dedicated Lakehouse Worker (`--node-role lakehouse`)

To run dedicated lakehouse compaction nodes that join the cluster metadata plane without serving pub/sub producers or consumers:

```bash
DANUBE_LAKEHOUSE_CONFIG=/etc/danube/lakehouse.yaml \
  danube up \
    --data-dir /var/lib/danube-lakehouse \
    --seed-nodes cluster-seed-1:7650 \
    --join \
    --node-role lakehouse
```

Nodes started with `--node-role lakehouse` auto-register in `drained` state (`lakehouse_only`), ensuring the Load Manager routes zero pub/sub topics to them.

### Container Deployment

The repository's unified `Dockerfile` compiles `/usr/local/bin/danube` with `--features danube-broker/lakehouse`. Run the same image as a co-located node or pass `--node-role lakehouse` with `DANUBE_LAKEHOUSE_CONFIG` mounted:

```bash
docker build -t danube .

docker run -d \
  -e DANUBE_LAKEHOUSE_CONFIG=/etc/danube/lakehouse.yaml \
  -v ./lakehouse.yaml:/etc/danube/lakehouse.yaml:ro \
  danube \
    up \
    --data-dir /danube-data \
    --broker-addr 0.0.0.0:6650 \
    --seed-nodes broker-0:7650 \
    --join \
    --node-role lakehouse
```

The lakehouse worker needs network access to:
1. **A cluster broker gRPC endpoint** (`broker.address`, e.g., `broker-0:6650`) for segment discovery and Schema Registry lookups
2. **Object storage** (`storage.*`) for reading sealed `.dnb1` segments and writing `.parquet` files
3. **The Iceberg catalog** (`catalog.*`) when `catalog.type` is not `none`
