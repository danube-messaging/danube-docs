Danube can write your topics straight into Apache Iceberg tables. The lakehouse runtime ships inside the `danube` binary, so you query streaming data from Spark, Trino, DuckDB, Snowflake or Athena without building a pipeline.

```bash
DANUBE_LAKEHOUSE_CONFIG=./lakehouse.yaml \
  danube up cluster --data-dir /var/lib/danube --single-node
```

## Why use it

<CardGrid>
  <Card title="Zero ETL" icon="rocket">
    No Kafka Connect, Spark Streaming or Flink jobs. Sealed segments become Iceberg tables automatically.
  </Card>
  <Card title="Isolated" icon="setting">
    Runs on its own `danube-lakehouse` thread pool (2 threads, 128 MiB memory budget), so analytics never slow down message delivery.
  </Card>
  <Card title="Schema-aware" icon="document">
    Reads schemas from the Danube Schema Registry and writes typed Parquet columns like `temperature` and `device_id`.
  </Card>
  <Card title="Open format" icon="open-book">
    Any Iceberg engine can read the tables. No vendor lock-in.
  </Card>
</CardGrid>

## Export a topic to Iceberg

<Steps>
1. **Give the cluster an object store and tier the topic.** The lakehouse runtime reads sealed segments from the cluster's durable store.

   ```bash
   danube cluster storage object-store --backend s3 --root s3://my-bucket/danube \
     --option region=us-east-1
   danube topic storage-mode /default/sensor-data --mode cloud_tiered
   ```

2. **Write a lakehouse config.** Point `storage.root` at the same location as the cluster object store.

   ```yaml title="lakehouse.yaml"
   broker:
     address: "localhost:6650"
   storage:
     backend: "s3"
     root: "s3://my-bucket/danube"
     options:
       region: "us-east-1"
   catalog:
     type: "rest"
     properties:
       uri: "http://polaris:8181/api/catalog"
       warehouse: "danube"
   topics:
     - namespace: "default"
       topic: "sensor-data"
       table_name: "sensor_data"
   ```

3. **Start a node with `DANUBE_LAKEHOUSE_CONFIG`.**

   ```bash
   DANUBE_LAKEHOUSE_CONFIG=./lakehouse.yaml \
     danube up cluster --data-dir /var/lib/danube --single-node
   ```

4. **Query the table** from any Iceberg engine connected to the same catalog.
</Steps>

Every key is documented in the [Lakehouse Configuration Reference](/reference/iceberg-configuration/).

## What happens to each segment

<Steps>
1. **Discover.** Every `polling.interval_seconds` the runtime asks the cluster for newly sealed segments of each configured topic. Active segments are never touched.

2. **Decode.** It reads the segment from object storage and decodes the messages. Topics with a JSON Schema or Avro schema get typed columns.

3. **Write Parquet.** Records are compacted into ZSTD-compressed Parquet files with per-column statistics (min/max, null counts), so engines can skip files.

4. **Commit.** New files are committed atomically to the Iceberg catalog. Readers never see half a commit.

5. **Checkpoint.** Progress is saved per topic under `<output_prefix>/checkpoints/<namespace>/<topic>.json`. After a restart the runtime resumes from the last committed segment (at-least-once).
</Steps>

Topics without a schema get a fixed envelope: `offset`, `publish_time`, `producer_name`, `routing_key`, `schema_id`, `schema_version`, `payload` and `attributes_json`.

## Choose where it runs

The `--role` flag decides which workloads a node runs:

<Tabs>
  <TabItem label="all (default)">
    The node serves producers and consumers and also runs the lakehouse runtime when `DANUBE_LAKEHOUSE_CONFIG` is set. Without the variable the runtime stays idle. Good for small clusters, dev and staging.

    ```bash
    DANUBE_LAKEHOUSE_CONFIG=/etc/danube/lakehouse.yaml \
      danube up cluster --data-dir /var/lib/danube --single-node
    ```
  </TabItem>
  <TabItem label="lakehouse">
    A dedicated worker. It joins the cluster but registers as `drained`, so the load manager never places client topics on it. Scale Parquet conversion independently of your brokers.

    ```bash
    DANUBE_LAKEHOUSE_CONFIG=/etc/danube/lakehouse.yaml \
      danube up cluster --data-dir /var/lib/danube-lakehouse --role lakehouse \
      --join --admin-listen 0.0.0.0:50051
    ```

    Then add it from any machine with `danube cluster node add --node-addr http://<worker>:50051`, as described in [Grow from one to three nodes](/getting-started/broker-modes/#grow-from-one-to-three-nodes).
  </TabItem>
  <TabItem label="broker">
    Serves producers and consumers only and never starts the lakehouse runtime, even if `DANUBE_LAKEHOUSE_CONFIG` is set. Use it for latency-critical brokers next to dedicated lakehouse workers.

    ```bash
    danube up cluster --data-dir /var/lib/danube --role broker \
      --seed-nodes broker1:7650,broker2:7650,broker3:7650
    ```
  </TabItem>
</Tabs>

A lakehouse worker needs network access to a broker (`broker.address`), to the object store and to the Iceberg catalog.

## Supported catalogs

- **`rest`**: any Iceberg REST catalog, such as Polaris, Nessie, Unity Catalog or Snowflake Open Catalog. Included in every build.
- **`glue`**: AWS Glue Data Catalog. Needs an AWS build.
- **`s3tables`**: AWS S3 Tables. Needs an AWS build.
- **`none`** (default): write Parquet files only, without a catalog.

<Aside type="note">
  Release binaries and the Docker image are built with the `lakehouse` feature, which includes the REST catalog. For Glue and S3 Tables, build from source with `cargo build --release --features danube-broker/lakehouse-aws`. A binary built without the feature ignores the lakehouse config and logs a warning for `--role lakehouse`.
</Aside>
